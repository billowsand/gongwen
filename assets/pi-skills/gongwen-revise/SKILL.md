# 修改公文

## 按需读什么

1. 读 `input/current.md` 作为本轮基准，读 `input/request.md` 确认要改什么、改到什么程度。
2. 读 `skills/gongwen-markdown/SKILL.md` 里当前文种的规则，作为标题层级、序号、附件与格式的依据。
3. 本轮有选区时，`input/request.md` 会写明选区原文：只改选区内的内容，
   选区外的文字必须逐字保持原样，否则程序会拒绝写入这份成品。
4. 读 `input/materials/index.json`。事实材料可以补充依据；写法样稿只提供表达方式，
   不能当成本次事项的事实来源。
5. 表单要素用 `doc_elements` 查看；授权类要素只读，不改、不建议、不出题。
6. 按用户要的改法选一份参考文件，只读用得上的那一份：
   - 压缩、扩写、按字数调整篇幅 → `references/condense.md`
   - 润色、理顺表达、去掉生硬或啰嗦 → `references/polish.md`
   - 调整语气、上行文 / 平行文 / 下行文的措辞 → `references/tone.md`
   - 规范标点、数字用法、用语与单位名称 → `references/normalize.md`
   - 用户点名要按某个风格档案改 → `style_list` / `style_read` 取回写法，
     风格里的单位、人员、日期、数字不得搬进正文。

## 怎么改

- 只动用户要求的部分。没有要求改的段落、公文引用（《…》（…〔…〕…号））、
  数字、日期、单位名称和人名必须原样保留。
- 需要新增事实时先检索：先用 `wiki_search` / `wiki_read` 查维基里已整编的知识，
  按其依据清单 `wiki_doc_read` 溯源原文；维基没有命中再检索知识库或稿件库；
  找不到依据就写成「【待核实：…】」，不要编造。
- 用户说「再短一点」这类要求时，以当前工作文件里的候选稿为基准继续改，
  不要重新从旧稿另写一份。
- 不要为了让稿子「更好」而顺手改事实、改口径、改结论。

## 问什么，不问什么

- 只有改法方向本身不清楚、问错了就会改错整篇时才用 `ask_user`（例如：这次是压缩全文
  还是只压缩第二部分）。要求里已经说清的不重复问。
- 不要把「先确认修改清单」当成动笔前提；直接给出完整修改稿，用户在成稿上提意见。

## 交付

- 把完整修改稿写入 `work/` 下的一个 Markdown 文件，调用
  `submit_document({path, summary})`。summary 说明改了哪几处、依据了哪些材料。
- 不要只交差异片段；提交的必须是完整正文。
- 提交前用 `check_document({path:"work/文件名.md"})` 自查，优先传路径，不重复输出全文。

## 分阶段时

宿主说分阶段时，每步只做它指定的那一小步，写完用 `record_progress` 登记；中间不提交半稿。章节标题不要手写编号，主送单位不要重复，字数上限是硬约束。

## 日期与组织背景

- 每轮以程序给出的当前日期、星期和时区为基准理解相对时间；跨日或不确定时调用 `current_date`。
  材料中的明确日期和已约定期限不自动改动；成文日期等表单授权要素仍由用户填写。
  当前日期只帮助解释相对时间，不是事项发生日期。没有材料或用户依据时，不得把今天写成会议、决定、启动、发布等事项的日期。
- 涉及单位、人员或责任分工时先用本轮组织背景，再按需 `vocab_search`：可按名称、职能、简介检索，
  按 `unit` 查所属人员/下属单位。结合职能任务和组织关系安排牵头与配合，不凭名称猜职责。
  人员优先查标准词库，同名按所属单位区分；未命中保留用户材料中的明确人名。
- 优先完整理解材料，容量不足时按大章节处理，保留全稿目的和结构。
- 本技能不做额外 AI 全面审校或事实核查。程序检查只负责格式、文字规则及技术和权限保护。
