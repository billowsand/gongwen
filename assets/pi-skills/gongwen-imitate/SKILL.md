# 仿写与风格分析

## 先分清用户要哪一种

- **仿写**：照某篇样稿的写法写一份**新的**公文 → 交完整正文（`submit_document`）。
- **只分析风格**：「看看这篇是什么写法」「总结一下它的文风」→ 交清单
  （`finish_report`），不给新正文。

## 按需读什么

1. 读 `input/request.md`，确认仿的是**写法**（语气、句式、结构）还是**版式结构**
   （章节顺序、条款组织），以及用户指定的样稿是哪一份。
2. 读 `input/materials/index.json`，用户 `@` 的样稿通常标成「写法样稿」或「结构范文」。
   标成「事实材料」「来函」的才是本次事项的依据。
3. 读样稿全文，按 `references/style-analysis.md` 拆出可复用的骨架。
4. 已有风格档案时，用 `style_list` / `style_read` 按当前文种取回；它们是**只读**档案，
   本技能不新建、不修改、也不保存风格。
5. 读 `input/current.md` 和事实材料，确定本次事项的真实内容。

## 怎么写

- **样稿只提供写法，不提供事实。** 样稿里的单位、人员、日期、数字、文件名、
  会议结论、工作成效一律不能写进新稿，除非事实材料里也有同样内容。
- 本次事项没有的事实写成「【待核实：…】」，或先检索知识库、稿件库找依据。
- 文种、标题层级、序号与附件写法仍以 `skills/gongwen-markdown/` 为准；
  样稿与技能规则冲突时按技能规则写。
- 表单要素用 `doc_elements` 查看；授权类要素只读。

## 风格库的边界（要如实说明）

- 你可以报告样稿的风格特征，也可以把学到的写法用在本次改写里；
- 你**没有**把风格学习结果保存进应用的风格库。用户要保存，得到「AI 管理 → 风格」
  里手动建或改；不要声称「已保存」「已加入风格库」。
- 风格档案与范例里的具体事实同样不是事实来源。

## 交付

- 仿写：完整新稿写入 `work/` 下的 Markdown 文件，调用
  `submit_document({path, summary})`。summary 说明仿的是哪份样稿的哪些写法。
- 只分析：`finish_report`，逐条写清特征与例子（引用样稿片段只用于说明写法）。

## 分阶段时

宿主说分阶段时，每步只做它指定的那一小步，写完用 `record_progress` 登记；中间不提交半稿。章节标题不要手写编号，主送单位不要重复，字数上限是硬约束。

## 日期与组织背景

- 每轮以程序给出的当前日期、星期和时区为基准理解相对时间；跨日或不确定时调用 `current_date`。
  材料中的明确日期和已约定期限不自动改动；成文日期等表单授权要素仍由用户填写。
  当前日期只帮助解释相对时间，不是事项发生日期。没有材料或用户依据时，不得把今天写成会议、决定、启动、发布等事项的日期。
- 涉及单位、人员或责任分工时先用本轮组织背景，再按需 `vocab_search`：可按名称、职能、简介检索，
  按 `unit` 查所属人员/下属单位。结合职能任务和组织关系安排牵头与配合，不凭名称猜职责。
  人员优先查标准词库，同名按所属单位区分；未命中保留用户材料中的明确人名。
- 优先完整理解材料，容量不足时按大章节处理，保留全稿目的和结构。
- 本技能不做额外 AI 全面审校或事实核查。程序检查只负责格式、文字规则及技术和权限保护。
