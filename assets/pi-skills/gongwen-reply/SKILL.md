# 起草复函

## 按需读什么

1. 读 `input/request.md` 和 `input/materials/index.json`，找出标成「来函」的材料。
   用户粘贴的来函正文也算来函。
2. 读 `references/incoming-letter.md`，按那里的规则认主送单位、来函标题与文号。
3. 读 `skills/gongwen-markdown/` 里公函（函）的文种规则与模板。
4. 表单要素用 `doc_elements` 看。复函的主送单位来自**来函落款**，不是来函抬头；
   授权类要素（文号、成文日期、签发人等）只读，不写、不建议、不出题。
5. 读完来函后，先在工作笔记中辨明三者：来函发出者（末尾署名）、来函接收者（抬头）、
   本次复函接收者（来函发出者）。这是自己核对，不要求用户确认。
   来函材料可以含有「收悉」等往返信函措辞，不能因此照抄其抬头作为本次主送。

## 怎么写

先按文件位置辨清方向，不能把“落款”当成收函者：

| 来函中的位置 | 代表谁 | 本次复函怎么用 |
| --- | --- | --- |
| 最前面的“甲单位：” | 接收原来这封函的单位 | 通常是本次答复的一方，不照抄为复函主送 |
| 最后日期前的“乙单位” | 发出原来这封函的单位 | 交付说明写“主送建议：乙单位；依据：来函落款” |

例如来函是“甲单位：……乙单位（日期）”，复函答复给乙单位；正文从“你单位《……》收悉”开始，不写“甲单位：”或“乙单位：”。

- 开头写「你单位《来函标题》（来函文号）收悉。」。标题、文号照来函原文；
  来函里没有就写「【待核实：来函标题】」「【待核实：来函文号】」，不要编。
- **逐项答复，顺序与来函提出的事项一致。** 每项先说来函要求什么，再说本单位的答复意见。
- 答复意见**只按用户给的意见写**。用户没给意见的事项写
  「【待核实：对……的答复意见】」，不要替用户表态（不要自己写「同意」「原则同意」
  「正在研究」这类结论）。
- 只缺部分事项意见时，仍按要求提交完整正文，用上述占位保留未知项；不要因此改交侧栏清单。
- 来函里的事实（时间、单位、事项、数据）照录，不改口径；不把来函的请求写成已经同意。
- 需要政策依据时先走维基：`wiki_search` 找已整编的知识页、`wiki_read` 读全文，
  按其依据清单用 `wiki_doc_read` 溯源原文；维基没有命中再用 `kb_search` / `kb_read` 找；
  知识库只用来查依据，
  **本单位的情况（部署范围、数量、成效）不要到知识库里找，也不要编**。
- 最后独立一段写「特此函复。」；未知意见占位不代替结语。附件按公函规则写。
- Markdown 不写主送抬头、落款、成文日期或联系人等表单要素；这些由应用表单排版。
  附件只按语法写对应内容，联系人不补进正文。识别出的主送建议放交付说明，不写表单。

## 问什么，不问什么

- 只有答复方向本身缺失、不问就会写错整篇时才用 `ask_user`：总体态度
  （同意 / 部分同意 / 不同意 / 需进一步研究）、受文单位这类。
- 具体日期、数字、文号不问；授权类要素不出题；已经写明的不重复问。
- 不要先让用户确认「来函事项清单」再动笔；直接在成稿里逐项答复，
  没有意见的用「【待核实：…】」标出。

## 交付

- 生成复函：完整 Markdown 写入 `work/`，调用 `submit_document({path, summary})`。
  summary 注明「主送建议：<来函发出单位>；依据：来函落款」，供人填写表单；这不等于已经填好。
- 只核对来函要求、只列答复要点：调用 `finish_report`，不要交正文。
- 提交前用 `check_document({path:"work/文件名.md"})` 自查，优先传路径。
- 提交前再比对交付说明中的主送建议与来函末尾署名：应向来函发出者答复，不能把来函接收者照抄为主送。
  `check_document` 不做事实核查；写复函时仍须按来函落款与本方身份判断收发方向。

## 分阶段时

宿主说分阶段时，每步只做它指定的那一小步，写完用 `record_progress` 登记；中间不提交半稿。章节标题不要手写编号，主送单位不要重复，字数上限是硬约束。

## 日期与组织背景

- 每轮以程序给出的当前日期、星期和时区为基准理解相对时间；跨日或不确定时调用 `current_date`。
  材料中的明确日期和已约定期限不自动改动；成文日期等表单授权要素仍由用户填写。
  当前日期只帮助解释相对时间，不是事项发生日期。没有材料或用户依据时，不得把今天写成会议、决定、启动、发布等事项的日期。
- 涉及单位、人员或责任分工时先用本轮组织背景，再按需 `vocab_search`：可按名称、职能、简介检索，
  按 `unit` 查所属人员/下属单位。结合职能任务和组织关系安排牵头与配合，不凭名称猜职责。
  人员优先查标准词库，同名按所属单位区分；未命中保留用户材料中的明确人名。
- 优先完整理解材料，容量不足时按大章节处理，保留全稿目的和结构。
- 本技能不做额外 AI 全面审校或事实核查。程序检查只负责格式、文字规则及技术和权限保护。
