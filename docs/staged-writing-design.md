# 分阶段公文写作设计（小参数模型）

> 2026-10-27，方案与界面已获用户确认；六阶段实现与验证进度见第十三节。
> 本文提出新增「分阶段写作」入口；保留现有智能体能力，复用底层模型、校验、审阅与恢复机制。
> 本文前十二节记录已确认的设计；具体实现差异与验收状态以第十三节为准。

## 一、目标与基本选择

让小参数模型每次只完成一项范围清楚的任务：读一块材料、提炼一种写法、拟一份提纲、写一个章节、修一处衔接。
步骤顺序、材料遍历、预算、保存与继续由程序控制，模型无需决定下一步做什么，也无需支持工具调用。

用户提出的流程保持为：

```text
素材准备：内容材料 / 风格样稿 / 结构范文
    ├─ 主题 + 全部内容材料逐块读取 → 主题素材卡
    ├─ 风格样稿 → style.md
    └─ 结构范文 → framework.md
                  ↓ 三路完成
主题 + 主题素材卡 + framework.md + style.md → 提纲 → 人工修改、确认
                  ↓
每个一级标题 + 全部原始内容材料逐块读取 → 本节素材卡
                  ↓
确认后的完整提纲 + 本节素材卡 + style.md → 分节写作
                  ↓
按提纲拼接 → 全篇结构检查 + 局部统稿（加载 style.md）
                  ↓
强制核验 → 提案审阅 → 用户接受后进入正式稿
```

这里把需求中的「版式素材」暂解作篇章结构范文：先写什么、后写什么、标题如何组织、各部分承担什么功能。
字体、字号、页边距、红头和版记仍由表单与本地 Typst / DOCX 模板控制。如果需求还包括从样稿学习视觉版式，应单列模板功能。

第 2 步三路在数据上独立；首版本机推理默认排队执行，避免同时调用同一模型拖慢整机。
后续可在端点容量允许时并发只读提炼，由主线程按固定顺序提交结果；不把并发作为首版前提。

## 二、现有框架能复用什么

以下按实际代码核查，不以旧设计文档中的计划功能代替已实现功能。

| 能力 | 现有位置 | 接入方式与缺口 |
|---|---|---|
| 模型角色、流式输出、取消、用量 | `src/agent/backend.rs`、`src/lmstudio/` | 复用 `ModelBackend`、`ModelRole::Assist / Draft`，不要求 `converse` 工具循环 |
| 实际窗口与 token 估算 | `src/lmstudio/context.rs` | 复用 `window` / `estimate_tokens`；增加每类任务的材料预算与输出预算 |
| 按标题、段落切块 | `src/agent/budget.rs` | `split_by_budget` 可作基础，但要增加原文位置、跨块上下文、表格边界和覆盖记录 |
| 风格学习与档案 | `src/agent/style.rs`、`ops/style_learn.rs` | 复用统计、样稿读取、事实混入提示；增加可编辑 MD、版本及任务内固定引用 |
| 提纲与人工修订 | `ops/prepare.rs`、`ops/confirm.rs`、`decision.rs` | 已有 `plan mode: outline` 与 `ListConfirm::outline`；扩充章节身份、职责、字数及证据关联 |
| 分节生成 | `ops/write.rs` | 已有 `generate mode: section`；补入固定风格、章节边界、去重约束和独立章节产物 |
| 证据编号与溯源 | `src/agent/evidence.rs`、`ai_panel/provenance.rs` | 复用 `[K…]` 和句子来源；新增原始快照到素材卡的来源链，不把模型摘要当原始证据 |
| 步骤恢复与会话存盘 | `agent/checkpoint.rs`、`engine.rs`、`manuscript/ai_checkpoints.rs` | 保留 `StepPath` 和唯一恢复入口；长材料另存，检查点只挂引用与游标 |
| 事实、要素、校对与人工合并 | `ai_guard`、`validator`、`proofread*`、`ai_panel/skill_job.rs`、`app/ai_proposal.rs` | 沿用最终强制闸门、提案审阅和接受后复验，不能由新流程绕过 |

现有「研究式起草」技能主要是预研检索、整稿生成、缺口补全和核验。
`retrieve` 是查找相关片段，不保证逐块读完用户指定材料；`fit_evidence` 会在预算不足时减少送入模型的证据。
这些机制适合现有检索式起草，但不能直接当成新流程的「素材已全部读完」。

## 三、素材准备：三个角色必须分开

起草页增加「分阶段写作」任务面板，侧栏继续显示进度、错误和继续操作。任务面板承载主题、三类材料、中间成果和章节列表。
材料入口复用稿件库、知识库、文档导入与粘贴；新文件经现有导入模块归一化，不由模型读本地路径。
系统文件框仍由应用层 `request_file` / `request_files` 调度。

每份材料登记：来源 ID、标题、角色、固定版本或内容指纹、导入时间、解析后的正文快照、可定位的段落或页码。
文档解析没有可靠页码时只展示章节 / 段落位置，不能编页码。

| 材料角色 | 可以影响的产物 | 事实使用边界 |
|---|---|---|
| 内容材料 | 素材卡、论证、事实与引用 | 可作事实来源，但需保留对象、时期与原文上下文 |
| 风格样稿 | 句式、语气、段落组织、表达习惯 | 其中事实不进入本文证据包 |
| 结构范文 | 章节顺序、各节功能、层级与篇幅比例 | 其中具体事实与任务要求不自动沿用 |

同一文件可以由用户赋予多个角色，内部仍按角色分流，不能因为用来学习风格就自动变为事实来源。
用户直接写明的新事实另存为「用户提供」，不能标为经过文献证实。
任务开始时固定快照；后续源文件变化提示可更新，更新后按依赖关系重算。
无法读取或解析的材料明确列出，等待用户重试或移除，不能跳过后宣称已读完全部材料。

## 四、第 2-a 步：按主题完整遍历内容材料

### 4.1 切块预算

每个请求重新计算：

```text
材料可用 token = 实际上下文窗口
               - 系统提示与本步指令
               - 主题、文种、必要上下文
               - 本步输出预留
               - 消息与估算安全余量
```

复用现有保守 token 估算，不把窗口 token 数直接当汉字数；窗口容纳量与本步适宜处理量取较小值。
小参数模型即使窗口很长，也应允许限制单块规模；具体默认值需以目标模型实测确定。
固定部分已经放不下时停止并说明原因，不能通过裁掉必要指令继续发送。

优先按章节、段落、列表和表格边界切；单块过大再细分，表格细分携带表头。
跨块添加有上限的相邻上下文，标清主块与补充上下文；抽取完成情况按主块计数。
服务端报告窗口更小时更新窗口、重切当前未完成部分，保留原文位置，防止重复和漏读。

### 4.2 素材卡与覆盖记录

每块只回答：与主题相关的观点有哪些，分别由哪些原文支持。不先要求它把整块压成摘要。

一张素材卡至少包含：观点、证据原句、来源快照、块 ID、原文位置、对象与时期、适用条件、用途（背景 / 问题 / 做法 / 成效 / 建议）、待核实项。
来源位置由程序依据当前块和引文匹配计算，不采信模型给的偏移量。
模型只需返回短记录或有界标签文本；程序转成类型化结构，不要求小模型输出复杂嵌套 JSON。
约定格式解析失败与引文不匹配均不算成功；有限重试后留下可见失败项。

引文精确匹配只能证明「原文确有这段」，不能证明观点正确概括原文，也不能证明政策仍适用。
因此要同时保留否定、条件、统计口径和上下文；冲突观点分别保留，不能让归并步骤擅自择一。
归并去重保留所有来源，不允许逐轮摘要把原始证据覆盖掉。卡片很多时分层整理观点目录，原始卡片仍可回查。

每个块登记「已提取 / 无相关内容 / 失败 / 未处理」，界面显示真实覆盖率。
只有处理成功且明确无相关内容的响应才记为「无相关内容」，超时、输出截断、格式错误不能记成无关。

## 五、第 2-b、2-c 步：风格与结构成为独立成果

`style.md` 描述总体语气、句长与句式、段落展开、标题语言、常用表达、忌用表达、开头收尾，并附少量脱敏句式示例。
避免只写「庄重、严谨、简练」；应提供可模仿的正反例与适用场合，不把风格统计变成硬性法律规则。
基于现有 `StyleProfile` 增加 MD 呈现与编辑，首版不另建第二套全局风格库。
全局档案只是起点，任务内保存独立版本；人工改动不得被后台重新学习覆盖。

`framework.md` 描述各部分的功能、顺序、建议层级、篇幅比例、必需与可选内容。
先从各篇范文抽取结构，再合成框架；长范文按其真实标题树整理，保留章节上下文，避免切块后丢掉全篇顺序。
多篇范文结构冲突时列出差异供用户选择；范文中的过时机构、具体数字和事项不能带入框架。

两份 MD 都可人工编辑，修改形成新版本。无样稿时可采用文种默认写法 / 结构，但界面明确标为默认，不能声称已经从素材学得。
第三、第五、第六步每次调用都必须加载当前确认的同一份风格版本；提纲的 AI 修订也在此列。
现有 `plan` 走 `Assist + ASSIST_SYSTEM`，仅沿用起草系统提示中的风格并不能满足这个要求，需要显式装入这些请求。
风格核心放不下时提示缩短或调整任务，不得默默删掉；可选范例缩减需可见，并记录实际输入版本。

## 六、第三步：提纲是人工控制的写作契约

输入：主题、写作目的、文种、对象、目标字数、主题素材卡目录、`framework.md`、`style.md`。
素材目录放不下时，按观点分类汇总用于规划；提纲不能只依据排在前面的几张卡。
提纲每节包含稳定章节 ID、标题、要回答的问题、必写要点、字数预算、已有证据、缺口与章节边界。

复用现有大纲确认卡，支持改标题、要点、顺序、增删章节和让 AI 按修改要求重列；确认前不能自动进入分节写作。
用户修改提纲只改变写作要求，不会把新写下的数字或判断自动变为有原文依据的事实。
短通知或函可以只有一个正文单元，不能为了流水线强行制造多个一级标题。

## 七、第四、第五步：按确认提纲重新读原始材料，再写章节

第四步用「总主题 + 当前一级标题 + 本节问题与边界」重新遍历全部原始内容材料。
不能只在第 2-a 步的提纯结果里检索，否则第一次未选中的细节永远找不回来。
复用已固定的原文快照与块清单，产出按章节隔离的素材卡；同一原文可支持多节，但需记录各节用途。
完整遍历是覆盖保证，不是相关性保证：允许用户补材料、排除卡片与指出遗漏。
本节的任何主块仍未成功处理时，不进入本节写作；到预算上限保存后继续，解析失败先重试或由用户明确移除材料。

第五步每次只写一个正文单元，输入包括：

- 总主题、确认提纲、全文篇幅分配和本节职责；
- 本节素材卡及其核准原文、缺口与必要背景；
- `style.md`、相关框架要求、统一术语表；
- 其他章节已承担的观点清单，以及相邻章节有限的衔接上下文。

章节证据过多时分组写段落再在本节内整合，不能截掉后面的卡片却宣称已经全部使用。
证据不足的要点标出缺口；计划、建议和已完成事实分开表达，不编数据来补齐篇幅。
已有章节的摘要只用于衔接与避免重复，不能充当新事实证据。
章节结果独立保存后再拼接，不在一个不断增长的 `workspace` 中追加后反复全量重写。
输出截断的章节不标为完成；重试或拆小后继续。每节可编辑、锁定、单独重写，人工改文优先保留。

## 八、第六步：统稿要照顾小窗口

先由程序按确认顺序拼接，检查标题层级、空节、顺序、编号、显著重复段落与字数。
语言通顺、语义重复和论证结构仍需模型检查与人工审阅，不能声称仅靠确定性规则解决。

全文连同风格、指令和足够输出预算都装得下时，可以整篇统稿。
装不下时采用两层统稿：

1. 全局层读完整提纲、各节论点与事实目录、术语表、篇幅统计及 `style.md`，生成具体的统稿问题清单。
2. 局部层按问题加载有关章节或相邻段落、原始证据和 `style.md`，修正重叠、跳跃、口径与衔接，再检查整稿覆盖。

全局目录也超过窗口时先分组形成带章节 ID 的目录，再合并；每条修改必须能回到实际正文核对。
统稿只调整表达、衔接与重复，不得新增无依据事实、改变数字口径、漏掉必要限定条件。
锁定或人工编辑的段落收到修改建议，由用户决定；不能被自动统稿覆盖。
局部替换沿用原文片段唯一匹配，来源链随修改更新，不能沿用已经失效的句子偏移。
统稿后重新核验事实与必写要点；自动核验有局限，最终仍需用户审阅。

## 九、工程接入与保存

### 9.1 流程与领域能力

建议把写作领域逻辑放入拟新增的 `src/agent/writing/`，按材料、切块、抽取、风格、框架、提纲、章节、统稿、状态拆分。
通过少量领域算子接入现有 `ops` 与 `engine`，由内置固定流程串联；技能文件承载可调整的提示词。
主入口是明确的「分阶段写作」界面操作，不能依赖模型从一句话中猜中技能。
新增流程不调用自主 `agent` 步骤，也不需要先完成通用图引擎、子图或多智能体。

可以复用顶层 `for_each` 的逐项检查点，但不能直接把「章节 × 材料块」套成两层循环后宣称可恢复：
当前循环子步骤不允许挂起，检查点也没有记录完整的嵌套子步骤执行位置，默认最多处理 20 项。
新流程应将有界工作单元显式规划为平铺任务，或给领域算子增加持久化游标，每块成功后保存；
用既有 `StepPath` 定位外层阶段，领域游标定位章节 / 块，不改成另一个恢复入口。
触及处理上限时必须挂起显示未完成量，不能依赖 `.take(limit)` 静默漏掉素材。

### 9.2 类型化任务与产物

建议增加 `WritingTask`、`SourceSnapshot`、`MaterialChunk`、`MaterialCard`、`WritingArtifact`、`SectionDraft`。
`Board` 只保存任务 ID、产物版本引用和当前处理游标，不能把全部原文与多份章节版本塞进弱类型 `vars`。
产物登记类型、内容、来源版本、提示词版本、实际模型、完成状态、人工编辑标志、依赖指纹。
MD 是可查看、可编辑、可导出的真实成果；程序另存结构化章节、证据与依赖元数据，不靠反复解析自由文本维护身份。

现有检查点单份目标上限 512 KiB，超限会裁减证据并标 `partial`，只保留首份与最近 5 份。
不能据此保证新流程的原文与素材卡永久可恢复。长材料和中间成果应另设任务关联存储，
与会话 / 稿件的删除生命周期一致，检查点引用的版本保留到引用消失；定期清理无引用产物。
每块产物与完成游标要在短事务中一致提交，先确认落盘再报进度。落盘失败不能继续报「可恢复」。
用户文件、材料总量、块数、卡片数和产物体积都应有上限，沿用 `file_limits` 与安全约定。
首版按本机写作任务保存，不自动把完整工作现场塞进版本快照或同步包；跨机续写需另定兼容方案。

### 9.3 修改后的失效规则

| 修改 | 需要重新计算或确认 |
|---|---|
| 主题 / 目的 | 主题提纯、提纲、分节素材、章节与统稿 |
| 内容材料 | 受影响的提纯结果；提纲提示重确认；依赖它的分节素材、章节与统稿 |
| 风格文件 | 提纲标为待复核，章节与统稿标为风格过期；不必重新读内容材料 |
| 结构框架 | 提纲重确认，受影响的章节边界、分节素材与正文重算 |
| 某节标题 / 要点 | 该节素材与正文失效；其他节边界、字数分配与统稿需复核 |
| 仅调章节顺序 | 保留各节素材与正文，重做过渡、编号与统稿 |
| 人工改某节正文 | 保留改文，重做该节核验与相关统稿；不自动重写 |

失效表示「不可当成当前成果直接交付」，不等于删除旧产物或人工改文。
恢复时重新灌入当前界面要素与正式稿，校验任务依赖指纹；不能沿用过时授权要素。
指纹或任务模式版本不兼容时，必须阻止直接续跑并标记依赖失效；不能只提示后沿新版技能步骤索引继续。

### 9.4 耗时与预算

设内容材料分为 N 块，提纲有 H 个一级正文单元；完整遍历大致需要 N × (1 + H) 次抽取请求，
另加风格、框架、提纲、写作、归并和核验。写作前显示预计块次、已完成量和实际耗时。
可复用相同快照、相同主题 / 节标题与提示词版本的已完成抽取产物，不复用输入已变的旧结果。
第四步只复用该节查询条件完全一致、原文块指纹一致且完整成功的块级产物，并报告全块覆盖；第 2-a 步结果不能代替第四步重读。
这是本次任务断点恢复，不意味着开启通用模型响应缓存。
首版需要自己的有界调用数、重试数与总时长，超限保存后可续；现有内核第 5 期全流程预算尚未完成，不能假定已具备。

## 十、交付与红线

模型只写 AI 工作稿和上述中间成果；正式稿仍只能由用户键盘或在审阅中接受提案修改。
授权类要素只读，不学习、不建议、不出题；描述类建议继续走标准词库、出处与人工采纳入口。
素材、样稿、框架均按资料包裹，不允许其中的指令改变程序流程或权限。
最终接入现有 `run_engine` 完成后的事实 / 要素 / 校对闸门与提案路径，逐块接受后对实际合并结果再核验。
新流程必须另外显式执行素材卡到正文的来源与覆盖核验；现有闸门不能替代新增的原文快照、块位置与事实单元之间的校验。
风格与框架既不能放宽文种规则，也不能成为事实出处；核验失败保留工作成果供修订，不能标为可交付。
现有 `ops/finish.rs::verify` 仅处理带引用标记的句子，默认核验 8 条、最多 30 条，不能据此宣称已经逐条核实全篇。
新流程需登记事实单元与引用覆盖；未核验、冲突和依据不足项明确展示，预算耗尽时保留为待核验，不能自动记为通过。
观点与原句分字段保存，原句定位成功只记「出处命中」；观点是否被原句支持另有核验状态，不以匹配成功冒充事实核实。

## 十一、建议分期与验收

| 阶段 | 交付范围 | 核心验收 |
|---|---|---|
| 1：材料与提纯 | 三类素材、固定快照、预算切块、主题素材卡、风格 / 框架 MD、保存继续 | 材料末尾的证据能提取；角色事实不串用；超小窗口和失败不伪装已读完 |
| 2：提纲与分节素材 | 加载风格拟纲、人工修改确认、章节身份、按节重新遍历原文 | 未确认不能写；新章节能找到第 2-a 步漏选的原文；改提纲正确标记失效 |
| 3：分节写作与统稿 | 逐节生成 / 编辑 / 锁定、短文与长文统稿、最终闸门与提案 | 每次拟纲 / 修纲 / 写节 / 统稿请求都有指定风格；保留人工改文；合并后复验 |

跨阶段必须验证：大于 20 块材料不漏处理；每块 / 每节中断后能恢复；窗口变化重切不漏读；
输出截断不标成功；检查点达到体积边界仍能取回固定原文；风格 / 框架 / 主题改变后不会误用旧成果。
用 `ScriptedModel` 检查流程契约、风格注入、来源匹配、失效与恢复；用目标低参数模型和真实中文材料验收观点相关性、语感、重复与统稿质量。
脚本测试通过不能等同于真实写作可用，参数规模小也不能替代实测。

建议先完成「素材 → 提纯 / 风格 / 框架 → 人工提纲」这段，让用户能检查中间成果，再延伸分节写作与统稿。
后续每期完成后在本文追加实际改动、与方案差异、验证记录和遗留问题；本轮没有改业务代码或执行发布操作。

## 十二、界面设计（2026-10-27 讨论稿）

### 12.1 入口与空间分配

在当前稿件的中央区增加「分阶段写作」，与「正文」切换，任务随稿件保存。
切回正文、查看其他稿件或关闭界面都不丢进度；重新打开后回到上次阶段。
既有公文要素区按需展开，预览 / 排版 / 导出沿用正式正文；避免在准备材料时同时挤进要素、编辑、预览与聊天四套界面。

中央工作区顶部显示六个阶段：素材准备 → 提炼素材 → 确认提纲 → 分节备料 → 分节写作 → 统稿审阅。
实际产品可随时回看已完成阶段；未来阶段显示未就绪原因，不允许跳过前置条件。
交互草图为便于讨论允许切换各阶段示例，不能照抄为产品的流程权限。

中间是当前阶段的主要成果，右侧是与它有关的依据、约束或待处理项。
右侧默认约 260–320 逻辑像素、可收起；窄窗口改成按需打开的依据区，优先保证中央编辑空间。
进入分阶段写作时默认收起通用 AI 聊天侧栏，需要时再打开；两个侧栏共用右侧位置，避免并排占宽。
现有审校结果抽屉也归入这一互斥规则：依据、AI 聊天、审校结果共用一个右侧位置，同时只展示一种。
底部固定在工作区内提供当前状态和一个主要推进动作，长任务中显示暂停 / 继续与实际进度。
菜单和快捷键沿用应用约定，状态更新不抢焦点，后台生成不打断人工编辑。

### 12.2 六个阶段的工作面

| 阶段 | 中央区 | 右侧依据区 | 主要动作 |
|---|---|---|---|
| 素材准备 | 主题、目标篇幅、内容材料 / 风格样稿 / 结构范文三个分组 | 当前文种、目的、材料用途说明 | 开始提炼 |
| 提炼素材 | 内容素材 / 写作风格 / 篇章框架三个成果页签 | 覆盖情况、原文出处、版本与待处理问题 | 生成提纲 |
| 确认提纲 | 每节标题、要点、字数可直接编辑；增删和排序；一句话修改要求 | 主题、结构要求、风格版本、已有线索与缺口 | 确认提纲，准备各节素材 |
| 分节备料 | 章节切换、每份原文的块进度、已提取素材与失败项 | 各节准备状态、本节问题与边界 | 全部就绪后开始分节写作 |
| 分节写作 | 章节目录、当前节工作稿、直接编辑、单节修改要求 | 本节原文证据、职责边界、风格与统一术语 | 合并全文，开始统稿 |
| 统稿审阅 | 全文、统稿修改对照、逐处排除 | 核验结果、待核对事实与原文 | 接受审阅结果，合并到正文 |

素材入口提供从文件导入、稿件库 / 知识库选择、粘贴文本；一份文件可以指定多个用途。
材料列表显示是否成功解析，移除 / 更换材料不藏在鼠标悬停按钮中。
风格、框架默认展示可读的写法描述，支持原地编辑；MD 导入导出为次级操作，不要求用户理解文件路径。
主题素材可以按观点浏览，点「查看原文」展开上下文和出处；不把所有材料全文常驻右栏。

提纲确认是主要人工关口，支持直接操作，不能强迫用户只通过聊天改提纲。
材料提纯、风格与框架可编辑，但默认不逐条弹窗确认；冲突和失败集中在当前阶段处理。
分节生成后可顺畅检查各节，不要求每写一节就弹窗确认；是否逐节停下由用户选择。

### 12.3 运行、修改与异常

- 长任务显示「第几节、哪份材料、第几块、已处理 / 总数」，不以模型思考文本替代进度。
- 暂停立即停止安排新请求，尽快取消在途请求；显示已保存的位置。关闭应用与继续沿用同一任务状态。
- 编辑后显示「保存中 / 已保存 / 保存失败」；切换阶段与稿件前先保存编辑缓冲，失败时保留缓冲并提示重试。应用正常退出前落盘；崩溃恢复只承诺最后成功保存的位置。导入中的文件标明未完成，不能计入可用素材。
- 失败项原地给出原因和重试，不把失败藏在日志里；存在未读块时明确显示无法开始写作的原因。
- 风格或框架改动后显示「哪些后续成果待更新」，操作为「保留旧成果查看 / 更新受影响部分」，不删除人工改文。
- 本节锁定与人工改文随章节保存。重写前保存当前版本；统稿对锁定部分只提建议。
- 回到已完成阶段可以编辑，但一旦改变依赖，必须重新满足后续阶段的就绪条件；阶段导航本身不触发模型调用。
- 统稿中区分「出处命中」「已核对」「依据不足」，不显示一个笼统的“全部通过”来掩盖未核验项。
- 有硬闸门问题时阻止合并，软提醒仍可审阅；用户勾选“已核对”必须绑定具体问题及修改后的事实清单，不能以一个通用复选框解除全部风险。

### 12.4 与现有界面的接点

页面切换由 `src/draft_page/page.rs` 的中央区域承接，避免把新功能塞进固定宽度的聊天卡片。
新工作稿编辑需要专门的任务成果编辑状态；当前 `src/ai_panel/workspace_ui.rs` 的 AI 工作稿是只读展示，不能直接假定已经支持原地人工修改。
复用 `decision::ListConfirm` 的确认 / 修订语义，提纲的章节化编辑界面在此基础上扩充。
最终统稿的真实差异与逐块排除复用既有审阅能力，操作仍进入 `accept_ai_proposal`，不另造直接写正文的入口。
首版可先生成整稿提案后打开现有审阅窗；草图中的中央内嵌差异审阅需适配既有组件，并非现成页面。
界面草图仅说明布局和交互，不代表已接入模型、资料解析、核验或本地任务存储。

## 十三、实施交接（2026-10-27）

### 13.1 已实现

六个阶段已接入实际任务执行，入口为起草页中央的「分阶段写作」。界面采用应用现有主题，中央编辑成果，
右侧展示依据；窄窗将依据改为折叠区。素材支持文件、稿件库、知识库、粘贴，文件框仍由应用层调度，
文件解析和模型调用在后台线程。通用 AI 侧栏与审校抽屉在写作模式收起，避免叠占空间。

主题材料逐块提纯；风格、框架和观点目录采用有界分组归纳。提纲可编辑、排序、增删、按要求重列，必须
人工确认。每节再次遍历完整原始内容材料，原句需逐字匹配，混有伪造引文的回答整块重试。失败、无关、
待处理分开计数，成功重试替换失败记录。块宽按模型窗口安排，主题块与分节块分别记录宽度，避免窗口
变化使已完成主题提纯被误判未完成。

章节可直接修改、锁定、重写，并保留历史稿。整批续写跳过有效完成稿与人工稿，显式重写会冻结修改前的
原稿。长节分组写作后按窗口逐层归并，每组保存现场，不能整篇塞回小窗口；模型无法继续缩减时保留全部
稿件并提示人工整理。对中断稿可人工编辑并确认完成。统稿先检查全局论点与章节目录，再按段生成独立
建议，保留锁定稿和人工稿。第三、第五、第六步的模型请求显式携带本任务风格，正文请求补入本地文种规则。

最终先检查来源定位与已识别事实出处，再运行现有要素、校对词表和文档规则，生成现有 AI 提案，交用户
在差异窗逐块取舍。接受后返回正文；模型执行、阶段导航和任务存盘均不改正式正文或授权类要素。
交付轮次保存实际模型用量、任务标识和风格 / 框架快照，继续沿用会话与提案留痕。

### 13.2 保存与恢复

任务位于同一 SQLite 库的 `staged_writing_tasks`，不可变原文位于 `staged_writing_sources`，均按稿件外键
级联删除。原文首次写入后不在每个块检查点重复序列化和写入；任务状态与块游标在短事务中保存。
单份原文 16 MiB、原文合计 64 MiB、任务 JSON 96 MiB；超限明确报错，不裁掉材料冒充可恢复。
读回先检查体积、任务版本和原文 SHA-256，拒绝缺失或损坏的快照。

每个动作最多 400 次模型请求、三小时；继续运行获得新一轮预算，成功块与归并分组可复用。暂停、错误和
崩溃后都从任务中保存的动作及游标继续。保存失败保留编辑缓冲并展示错误，关闭时补存；后台提前结束也
会退出运行状态，避免永久卡住。只承诺最后成功存盘的现场，未完成的文件导入需重新选择。
