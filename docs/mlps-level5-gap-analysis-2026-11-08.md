# 等保 2.0 第五级（行业俗称「专控保护级」）要求检索与本产品差距分析

- 日期：2026-11-08
- 对象：本仓库 `gongwen-assistant` v0.10.5（Rust + egui，单机离线中文公文写作桌面应用）
- 目的：回答两个问题——① 公开渠道有没有「软件 5 级等保」的指南；② 本产品按这套要求看还差什么、哪些能补、哪些补不了。
- 方法：标准原文核对（GB/T 22239-2019 等四份标准的 PDF 逐页 OCR + 官方目录页核对）+ 法规/规章原文 + 仓库代码与安全文档逐项核对。结论以代码为准，不以文档自述为准。
- 证据强度：**代码直接证明** > **文档声称** > **未验证/需真机**。本报告凡写「已具备/缺失」均尽量给 `文件:行`；涉及真机、平台、第三方库内部行为的，标注「未验证」。
- 结论性质：**这是差距分析与合规路线建议，不是等保测评结论，也不构成法律意见。**

## 0. 先给结论（给赶时间的人）

1. **公开标准里没有「第五级要求清单」，这不是没搜到，而是标准原文就写「略」。**
   GB/T 22239-2019 第 10 章「第五级安全要求」正文只有「略。」；5.2 第五级安全保护能力也是「略。」；
   范围注写明第五级「不在本标准中进行描述」。GB/T 25070-2019（设计）、GB/T 28448-2019（测评）、
   GB/T 39786-2021（密码应用）对第五级同样处理。**任何网传「第五级逐条要求」都是解读，不能当条文引用。**
2. **第五级（行业俗称「专控保护级」）：对象被破坏后会对国家安全造成特别严重危害；由「国家指定
   专门部门」专门监督检查，等级测评由运营单位依据业务特殊安全需求选择测评机构实施；没有公开的
   固定周期与通用清单。**
   行业通行类比中，最接近第五级水平的是涉密信息系统的绝密级（按 BMB17 等保密标准保护），不是 GB/T 22239。
3. **一个桌面软件本身不是等保定级对象。** GB/T 22240-2020 明确要求定级对象具有「确定的主要安全
   责任主体、承载相对独立业务应用、包含相互关联多个资源」，并注 2 明确「避免将某个单一的系统组件，
   如服务器、终端或网络设备作为定级对象」。所以「给公文助手做第五级等保测评」在制度上不成立；
   能做的是：作为某个已定级系统的组成部分，满足落到客户端的那部分要求，并按需通过密评。
4. **对本产品现实可对标的公开基线是「GB/T 22239-2019 第四级 + GB/T 39786-2021 通用要求」**，
   而不是「第五级」。原因是第四级是公开可得的最强文本，第五级条款不可得；且客户若真按第五级要求，
   要求会来自其主管部门的专控文件，需逐案响应。
5. **现有家底**：数据静态加密（SQLCipher 全库 + AES-256-GCM 文件封装 + Argon2id）、加密导出
   （Word/PDF/7z）、明文出口 fail-closed、本地双槽备份与恢复、导入体积/解包上限、依赖漏洞扫描
   （RustSec CI）、3000+ 测试与多轮安全复检。**这些在「数据保密性/完整性」和「输入校验」上已经
   接近或达到四级客户端要求的部分条款。**
6. **最大差距（按四级基线，也是客户最会追问的）**：
   - **安全审计**：没有审计子系统，只有崩溃日志和诊断日志；不满足「覆盖每个用户、字段齐全、
     防篡改、审计进程受保护」。（P0）
   - **身份鉴别**：只有单一口令因子，无失败次数限制/锁定，无双因素，无 UKey/国密证书登录；
     四级 9.1.4.1 d) 强制「两种以上组合鉴别且其中一种用密码技术」。（P0）
   - **可信验证**：无代码签名（Windows 未签名、macOS 仅可选签名/公证）、无二进制自校验、
     无更新包签名验证、无 TPM/可信根；更新检查只打开网页。（P0/P1）
   - **商用密码**：SQLCipher(AES-256)、AES-GCM、Argon2id、SHA-256 均非商用密码算法；
     若客户要求密评/国密，当前实现没有合规身份（公开条文没有「禁止 AES」，准确说法是
     「在要求使用商用密码的场景下不满足」）。（P0，视目标客户而定）
   - **集中管控/安全管理中心**：单机离线架构没有集中审计、策略下发、统一时钟、集中监测；
     只能提供外送接口，设施与制度由部署方承担。（C 类硬缺口）
   - **强制访问控制/安全标记/三员分立**：当前是「解锁后全可见」的单用户模型，密级只是排版与
     校验字段，不构成访问控制标签；无系统管理员/安全管理员/审计管理员分权。（P1）
   - **异地备份、热冗余、异地灾备**：只有本地备份，b–d) 三条是架构性缺口。（C 类）
   - **供应链证据**：有 Cargo.lock、vendor、依赖漏洞扫描、第三方清单，但无 SBOM、无可复现构建、
     无发布签名、无独立渗透测试/代码审计报告、无 CC/销售许可类认证。（P1/P2）
7. **建议的产品口径**：不承诺「本软件通过等保五级」；对外表述为「可作为已定级信息系统的
   客户端组件，提供数据加密、备份、导入校验等**现有**安全能力；身份鉴别、访问控制、安全审计
   按本报告路线图补齐后提供」，并配合系统测评与密评。
   若客户坚持五级，先索取其定级备案证明、主管部门（国家指定专门部门）的具体要求、密评要求，
   再按系统组件逐条响应——这是唯一站得住的路径。

## 1. 检索结果：为什么没有「第五级指南」

### 1.1 四份标准对第五级的处理（原文核对）

本次从公开渠道取得标准 PDF（图像型、无文本层），逐页 OCR 后用目录页与正文版式交叉核对。
关键页：GB/T 22239-2019 目录标注「10 第五级安全要求 …… 64」，正文第 64 页（PDF 第 70 页）
实际内容为：

> 10 第五级安全要求
>
> 略。

这不是孤例：

| 标准 | 对第五级的原文处理 | 核对方式 |
|---|---|---|
| GB/T 22239-2019《网络安全等级保护基本要求》 | 范围注：「第五级……有特殊的管理模式和安全要求，所以不在本标准中进行描述」；5.2「第五级安全保护能力：略」；第 10 章「略」 | 目录 + 正文 p.64 逐页核对 |
| GB/T 25070-2019《网络安全等级保护安全设计技术要求》 | 范围注同款；第 10 章「略」 | 公开 PDF 目录/正文核对 |
| GB/T 28448-2019《网络安全等级保护测评要求》 | 范围注：「第五级……有特殊的管理模式和安全测评要求，所以不在本标准中进行描述」；第 10 章「第五级测评要求：略」 | 公开 PDF 目录 + 范围注 + 第 10 章核对 |
| GB/T 39786-2021《信息系统密码应用基本要求》 | 范围注：「第五级密码应用仅在本标准中描述通用要求」；第 10 章「略」；附录 A「第五级略」 | 公开 PDF 目录/正文核对 |

**可引用的结论**：截至 2026-11-08，公开渠道不存在第五级的技术要求、设计技术要求、测评要求原文。
存在的是「第五级被排除在公开标准之外」这一事实，以及散落在法规里的定位、流程、监管条款。

### 1.2 第五级到底是什么

- **定级结果**：GB/T 22240-2020 表 1：受侵害客体为「国家安全」、侵害程度为「特别严重损害」时，
  定为第五级。GB/T 22240-2020 4.1 e)：「第五级，等级保护对象受到破坏后，会对国家安全造成
  特别严重危害。」
- **保护方式**：公通字〔2007〕43 号第八条：「第五级信息系统运营、使用单位应当依据国家管理规范、
  技术标准和**业务特殊安全需求**进行保护。国家指定专门部门对该级信息系统信息安全等级保护工作
  进行专门监督、检查。」
- **评审**：43 号文第十条：拟确定为**第四级以上**的，应请国家信息安全保护等级专家评审委员会评审。
- **测评/自查**：43 号文第十四条：三级每年至少一次、四级每半年至少一次，**第五级「应当依据特殊
  安全需求进行等级测评」**（无固定周期）。
- **检查主体**：43 号文第十八条：第五级由**国家指定的专门部门**检查。
- **测评主体**：43 号文第十四条：第五级「应当依据特殊安全需求进行等级测评」，由运营/使用单位选择
  符合第二十二条条件的测评机构实施；国家指定部门直接「测评」的说法不准确。「普通测评机构无参考
  意义」只是行业解读，不是条文。
- **与涉密系统的关系**：43 号文第二十七条：涉密信息系统按秘密、机密、绝密三级保护，「其保护水平
  总体上不低于国家信息安全等级保护第三级、第四级、第五级的水平」。即绝密级涉密系统 ≈ 等保五级
  水平，但适用 BMB17 等保密标准。

### 1.3 对「软件」的三条制度性结论

1. **软件不是定级对象**（GB/T 22240-2020 5.1.1 注 2）。等保对象是「系统」，软件是系统组件。
   行业里「某软件过了等保三级」的说法，实质通常是「软件部署所在系统过了测评，软件是范围内的
   一个测评对象」。
2. **软件产品能承担的是「安全计算环境」里落到客户端的那部分**，以及为「安全管理中心」提供
   接口/证据；物理环境、通信网络、区域边界、集中管控、管理制度/机构/人员/建设/运维的大部分，
   只能由部署方与组织承担。
3. **第五级是「逐案定制」的**（业务特殊安全需求 + 国家指定部门），不是一张可以打勾的通用清单。
   因此本报告后续用**第四级公开条文**作为「最强可得基线」，并逐项标注 A/B/C 可承担性；
   凡是写「四级」的地方，都**不是**在冒充第五级原文。

## 2. 第五级要求怎么落到软件上：A / B / C 三类

为了不让「差距」变成一句空话，把要求分成三类：

- **A 类｜软件产品可直接实现**：纯代码可控、不依赖外部基础设施，有可验证产物（配置、日志、
  算法、界面约束）。
- **B 类｜需部署方/组织实现，软件提供接口或证据**：软件做一半，另一半靠组织的制度、人员、CA、
  SOC、密码设备、备份设施；软件的责任是「能对接、能导出、能证明」。
- **C 类｜单机离线产品架构上无法满足**：需要网络、集中设施、硬件可信根、异地设施、专职组织，
  或需要操作系统/数据库/虚拟化层配合。

### 2.1 A 类（软件自己能做完的）

| 控制点（以四级公开条文为基线） | 软件侧应做到 |
|---|---|
| 9.1.4.1 a) 身份标识唯一、鉴别信息复杂度、定期更换 | 账户唯一标识、口令强度策略、改密与到期提醒 |
| 9.1.4.1 b) 登录失败处理、会话超时退出 | 失败计数/锁定/延时、闲置自动锁定、手动锁定 |
| 9.1.4.2 a)–d) 账户权限、默认账户、过期账户、最小权限与分权 | 账户体系、角色、权限最小化、默认账户处置 |
| 9.1.4.3 a)–d) 安全审计（本地部分） | 审计事件、字段完整、防篡改、审计进程保护、留存与导出 |
| 9.1.4.4 a) b) d) 最小安装、关闭不必要服务/端口、输入有效性检验 | 安装包最小化、不监听不必要端口、导入/粘贴/解包校验与上限 |
| 9.1.4.4 e) 已知漏洞发现与修补 | 依赖漏洞扫描、漏洞响应流程、补丁发布 |
| 9.1.4.6（应用自身部分）可信验证 | 安装包/二进制签名、启动自校验、组件白名单 |
| 9.1.4.7 a) b) 数据完整性 | 存储/传输的密码保护、完整性校验 |
| 9.1.4.8 a) b) 数据保密性 | 存储/传输加密、密钥管理 |
| 9.1.4.9 a) 本地备份恢复 | 本地备份、校验、恢复、演练说明 |
| 9.1.4.10 剩余信息保护 | 内存零化、临时文件清理、安全删除、剪贴板治理 |
| 9.1.4.11 个人信息保护 | 最小采集、访问控制、脱敏、出口治理 |
| 9.1.5.1–9.1.5.3（本地三员） | 系统/安全/审计管理员角色与操作入口分离（单机可做简化版） |
| 密码应用（GB/T 39786 通用要求） | 算法可替换、国密支持、密钥生命周期记录 |
| 9.1.9 / 9.1.10（产品侧证据） | SBOM、开发安全、测试验收、交付清单、漏洞响应、签名发布 |

### 2.2 B 类（软件留接口/出证据，组织落地）

| 要求 | 软件侧责任 | 组织侧责任 |
|---|---|---|
| 9.1.4.1 d) 双因素且一种用密码技术 | 支持 UKey/智能卡/SM2 证书/TOTP 登录；失败处理 | 发放 UKey、CA 证书体系、身份管理 |
| 9.1.4.2 e)–g) 访问控制策略、安全标记、强制访问控制 | 策略引擎、密级/敏感标记、按标记授权 | 密级定义、定密授权、与 OS 级 MAC 的一致性 |
| 9.1.4.3 集中审计 | 审计外送（syslog/HTTP/文件）、格式与完整性 | 集中审计平台、留存、审计员 |
| 9.1.4.5 恶意代码防范「主动免疫」 | 组件白名单、安装包签名、导入拦截 | 可信计算环境、杀毒/EDR 联动 |
| 9.1.4.6 可信验证全链 | 应用自校验、启动度量上报接口 | 可信根、TPM/TCM、安全管理中心 |
| 9.1.4.7 c) 抗抵赖 | 签名与哈希链、时间戳接口 | 证书、时间戳服务、法律责任认定流程 |
| 9.1.4.9 b)–d) 异地备份/热冗余/灾备 | 备份包导出、异地复制脚本、双机部署说明 | 备份设施、灾备中心、切换演练 |
| 9.1.5.4 集中管控 | 策略下发、日志上送、时间同步、补丁管理接口 | 安全管理中心、SOC、统一时钟 |
| 密码应用 | 密码模块抽象层、SM 算法、密钥管理接口 | 密码机/密码卡、密评、密钥管理制度 |
| 供应链 | SBOM、第三方清单、漏洞响应、签名发布 | 网络安全审查申报、采购与保密协议 |

### 2.3 C 类（单机离线架构上无法满足，只能靠部署/组织或改架构）

- 安全物理环境全部 10 个控制点（机房、门禁、消防、电力、电磁屏蔽等）。
- 安全通信网络的网络架构、通信传输中的「基于硬件密码模块」、通信网络可信验证。
- 安全区域边界的边界防护、访问控制、入侵防范、恶意代码与垃圾邮件防范、边界审计、可信验证。
- 安全管理中心的系统管理/审计管理/安全管理/集中管控（尤其集中审计、统一时钟、集中监测）。
- 数据备份恢复 b) 异地实时备份、c) 热冗余、d) 异地灾备中心与实时切换。
- 可信验证的可信根部分、恶意代码防范的「主动免疫」部分。
- 管理要求中依赖组织实体的部分：机构设置、专职安全管理员不可兼任、关键岗位多人共管、
  外部人员访问管理、跨单位联合应急、专家评审与备案。

> 结论：**即使把软件做到极致，单机离线产品也不可能单独满足第五级（或完整第四级）**。
> 差距分析的意义在于：把 A 类补齐、把 B 类接口留好、把 C 类如实写进「不适用论证 / 部署方责任」，
> 而不是假装产品能自证五级。

## 4. 差距详述（按客户追问概率排序）

### 4.1 安全审计：最硬、最容易被一票否决的缺口

**四级要求（9.1.4.3）**：启用审计、覆盖每个用户、审计重要用户行为和重要安全事件；记录日期时间、
事件类型、主体、客体、结果；审计记录保护、定期备份、防未预期删除/修改/覆盖；审计进程保护，
防未经授权中断。网络安全法还要求网络日志留存不少于六个月（条号以现行文本为准）。

**现状**：全仓库没有安全审计模块。`src/crash_log.rs` 是崩溃诊断，`src/app/data_safety.rs:577`
是给维护者看的诊断内容；可选的「印制追溯」记录编号/单位/时间/标题/哈希，但文档明确
「不是不可篡改的审计证据」（`docs/print-trace-design.md:23-25`）。两者都不是审计：没有事件模型、
没有主体/客体字段、没有防篡改、没有留存策略、没有审计员视角，用户也可以在应用内清日志/退出应用。

**审计盲区（当前均不留痕）**：解锁成功/失败、诱饵密码进入、改主密码/设清第二密码、启用/停用
应用锁、明文导出确认与结果、剪贴板复制/剪切、全量备份/恢复、密钥遗失/锁文件损坏/重置、
文件删除/擦除、模型/接口调用（只有业务运行记录，非安全审计）。

**差距**：
- 无「谁在何时对什么做了什么、结果如何」的记录；
- 无防篡改（哈希链/签名）与防删除；
- 无审计进程保护（同进程内可被 UI 操作影响）；
- 无留存期与导出（无法交给组织做集中审计）；
- 无审计员角色与只读查看入口。

**建议（P0）**：
1. 新增 `src/audit/`：事件模型（时间、主体、事件类型、客体、结果、来源、附加字段）；
   追加写 + 哈希链（每条含前一条摘要），定期锚定；密钥/口令类事件只记结果不记内容。
2. 覆盖事件：解锁成功/失败、锁定、改密、启用/停用应用锁、导出（含明文/加密选择）、打印、
   复制/剪切、备份/恢复、导入、接口与模型配置变更、密钥/密码变更、AI 写入正文、审计日志导出。
3. 审计存储：加密容器内追加写；单独文件 + 只读句柄；UI 不提供删除；保留期可配置（默认≥180 天）。
4. 审计查看：只读界面 + 过滤/导出 CSV/JSON；后续支持 syslog/HTTP 外送（B 类）。
5. 失败锁定与告警联动（见 4.2），失败事件必须留痕。
6. 验收：构造 20+ 事件脚本，验证字段完整、链校验、重启后不可否认、导出可被外部工具验链。

### 4.2 身份鉴别：单因素、无失败处理

**四级要求（9.1.4.1）**：a) 唯一标识、复杂度、定期更换；b) 登录失败处理（结束会话、限制非法
登录次数、超时退出）；d) 两种以上组合鉴别，且其中一种至少用密码技术实现。

**现状**：
- 单一口令因子；Argon2id 参数合理（`src/vault.rs:54-56`），口令策略较严（11 字符、3 类、
  拒绝常见口令/连续/重复，`src/password_policy.rs`）；
- 有闲置自动锁定与手动锁定；
- **没有失败次数限制/锁定/延时**（全仓未检索到失败计数器；`src/app/gate.rs:501-551` 解锁路径直接重试）；
- **没有第二因子**；没有 UKey/智能卡/SM2 证书/TOTP/系统生物识别；
- 无口令有效期/定期更换策略；
- **没有绑定系统会话**：不监听 OS 锁屏、切换用户、休眠/挂起、远程会话断开；闲置锁定可选「永不」；
- **高风险操作不再认证**：改主密码、设/清第二密码、停用应用锁、重置导出设置、恢复备份都只靠
  已解锁会话（`src/app/vault_settings.rs:190-300`、`src/app/export_password.rs:15-120`）；
- **双槽顺序尝试存在可测耗时差异**：真实密码约 1 次 Argon2id，错误/诱饵密码约 2 次
  （`src/vault.rs:369-398`），本机可测，削弱「诱饵不可区分」的承诺（低危但代码可证）；
- 无密码找回/受控重置（「无后门」是安全优点，但高等级场景需要组织侧的可信恢复流程）。

**差距**：四级 d) 是强制项，且明确「其中一种至少使用密码技术」；单机产品最容易被追问。
b) 的「限制非法登录次数」也没有落地。

**建议（P0）**：
1. 登录失败处理：连续失败 N 次（如 5 次）锁定 M 分钟（如 5 分钟）并指数退避；失败事件进审计；
   锁定状态在重启后保持（防绕过）；提供管理员解锁/恢复流程（离线场景需谨慎，避免拒绝服务）。
2. 消除解锁耗时旁路：无论命中哪个槽，都固定执行两次 KDF（或加固定延迟），并写测试锁定行为。
3. 第二因子：
   - 近期：TOTP（RFC 6238）或操作系统生物识别/Windows Hello/macOS Touch ID 作为第二因子；
   - 目标：UKey/智能卡 + SM2 证书（`PKCS#11`/`CSP`/`CryptoTokenKit` 抽象层），证书与 CA 由组织提供（B 类）。
4. 会话与重认证：监听 OS 锁屏/切用户/休眠事件，事件到达即锁；高风险操作（改密、停用、恢复、
   重置导出设置）要求重新输入当前主密码；高安全模式下不再提供「永不自动锁定」。
5. 口令策略补「定期更换」：到期提醒 + 强制改密（可按组织策略关闭）；保留强度校验。
6. 身份标识：即使单机，也给本机账户一个稳定标识（用于审计主体），支持多账户时再扩展。
7. 验收：错误口令连续尝试触发锁定；第二因子缺失时不能解锁；审计中有成功/失败记录；
   两种密码的解锁耗时在统计上不可区分。

### 4.3 可信验证与发布链路：没有签名，就没有「可信」起点

**四级要求（9.1.4.6）**：基于可信根对引导程序、系统程序、重要配置参数、应用程序进行可信验证，
所有执行环节动态验证，检测到破坏后报警，结果形成审计记录送安全管理中心，并动态关联感知。

**现状**：
- Windows 安装包没有 Authenticode 签名（`release.yml` 无 signtool/签名步骤）；
- macOS 仅在配置 secrets 时签名/公证（`release.yml:121-125`），CI 未配置时发布未签名包；
- Linux deb/pacman 包无签名（只有 `.sha256` 校验文件）；
- 应用内无二进制/资源自校验；
- 随包 Pi 运行时有一套 manifest 哈希自检（`src/pi_agent/runtime.rs:266-383`），但 manifest 本身
  未签名——能防意外损坏/版本错配，不能证明来源；
- 「检查更新」只请求 GitHub API 取版本号与发布页链接（`src/update_check.rs:10-12、43-71、125-158`），不下载、
  不验签、不自动安装；更新检查响应无签名；
- 无 TPM/TCM/可信根、无启动度量；`release.yml` 不跑依赖审计门禁（CI 的 RustSec 只管 push/定时）。

**差距**：A 类（应用自校验、签名发布、更新验签）与 C 类（可信根、集中上报）都缺。

**建议（P0/P1）**：
1. Windows Authenticode（EV/OV 证书）+ macOS Developer ID + 公证；Linux 发布 `.deb`/包签名或
   至少提供 minisign/GPG 签名的发布清单；所有产物附签名与校验值。
2. 更新链路：发布清单签名（minisign/GPG/SM2），客户端下载后验签再安装；在自动更新前，
   至少做到「检查更新返回签名清单 + 用户手动下载后应用内校验」。
3. 应用自校验：启动时校验自身二进制/关键资源哈希（构建时嵌入），异常告警并写审计。
4. 可信根：TPM 2.0 密封 DEK、启动度量、远程证明——列为长期项（C 类，需硬件与管理系统）。

### 4.4 商用密码与密评：不是「不安全」，是「不合规身份」

**公开要求链**：
- GB/T 39786-2021 第 5 章通用要求（适用一至五级）：算法符合法律法规和国家/行业标准；技术遵循
  国家/行业标准；密码产品、服务符合法律法规。
- 《商用密码管理条例》第九条：要求使用商用密码保护的网络与信息系统，其密码算法、密码协议、
  密钥管理机制等商用密码技术应通过国家密码管理部门审查鉴定；第三十九条（关基）：关基使用的
  商用密码产品、服务应经检测认证合格。
- 《商用密码应用安全性评估管理办法》（2023-11-01）：密评查合规性、正确性、有效性；运行前评估、
  运行后每年至少一次。
- GB/T 39786 附录 A：四级要求密码产品安全等级三级及以上（三级为二级及以上）。

**现状**：SQLCipher（AES-256）、AES-256-GCM、Argon2id、SHA-256/SHA-512、PDF/Word 的
AES 加密——都是国际算法/非国标 KDF，没有商用密码审查鉴定身份；密钥管理有工程实现，但没有
「密钥全生命周期」的可导出记录，也没有密码模块边界/认证。

**同时存在的工程性弱点**（与国密无关，但密评也会看）：
- GWA1 旧格式无 AAD，只读兼容；读取侧存在「密封名单中的文件被替换成明文会被直接接受」的
  降级路径（`docs/security-review-2026-11-07.md:120-123`）；
- DEK 不轮换：改主密码只重裹同一把 DEK，DEK 泄露后改密不能止损（`src/vault.rs:400-438`）；
- DEK 经 stdin 传给 Node host，进程内有未清零副本，且 stderr scrub 只抹模型 API key
  （`src/pi_agent/process.rs:674-686`、`:1495-1530`）；
- 7z 是「加密 + CRC32」，不是 AEAD；备份/稿件包完整性证明弱于加密强度；
- 导出密码可由取得 DEK/解锁权限的人取出（`docs/encrypted-export-design.md:33`）。

**准确表述**：公开条文里没有一句「禁止 AES」。所以不要说「违法」，要说「在要求使用商用密码
（关基、政务、密评范围）的场景下不满足算法与产品要求」。普通内部使用、非关基、非密评范围，
AES 体系在工程上是合理的。

**建议（P0，若目标客户是党政/关基）**：
1. 抽密码抽象层：加密/摘要/签名/KDF 统一 trait，提供国际算法与国密两套后端。
2. 国密后端：SM4-GCM（对称）、SM3（摘要/HMAC）、SM2（签名/密钥交换）、PBKDF2-SM3 或
   SM3 迭代 KDF；依赖需审计并登记 `THIRD_PARTY_NOTICES.md`。
3. SQLCipher 没有国密分支：要么「应用层信封加密」把敏感字段/正文用 SM4 加密后入库，
   要么迁移到支持 SM4 的加密库；**不要宣称 SQLCipher 满足密评**。
4. 密钥生命周期：产生/分发/存储/使用/更新/归档/撤销/备份/恢复/销毁的记录与导出；
   DEK/KEK、槽位、备份、停用解密的状态机输出「谁在何时对哪把密钥做了什么」。
5. 密码模块：纯软件实现很难自证 GB/T 37092 等级；现实路线是调用系统密码模块/外接密码机/密码卡
   （B 类），或做商用密码产品检测认证（长期）。
6. 密评：运行前评估 + 每年至少一次；报告 30 日内备案；提前与密评机构对齐指标。

### 4.5 访问控制与密级：现在只是「排版字段」，不是安全边界

**四级要求（9.1.4.2）**：账户与权限、默认账户、过期账户、最小权限与权限分离；策略由授权主体
配置；粒度到用户/进程、文件/库表；**对主客体设置安全标记，并依据标记和强制访问控制规则决定访问**。

**现状**：
- 解锁后所有稿件、知识库、词表全可见；没有账户/角色/权限模型；
- `security_level`（密级）只用于排版、校验、列表着色、提示词（`src/models/security.rs:10-30`、`src/models/draft.rs:287-300`、
  `src/validator.rs:654`、`src/pi_agent/tools.rs:1404`），**不限制任何访问**；
- 授权类公文要素「AI 只读」是产品红线（`src/element_fields.rs:1-12`），是业务规则，不是安全访问控制；
- 无三员分立、无审批流；设置页所有解锁用户都能改主密码、设/清第二密码、停用、恢复备份；
- Unix 有 0700/0600，**Windows 没有显式 ACL**，依赖配置目录继承（`src/storage.rs:425-435`）。

**差距**：a)–g) 基本全缺；g) 在单机 + 单用户下需要 OS 配合（B/C 类），但软件至少应做
「文档密级 + 用户 clearance + 导出/打印审批」的应用层 MAC。

**建议（P1）**：
1. 多账户/角色：普通用户、系统管理员、安全管理员、审计管理员（至少审计员只读）；角色权限矩阵。
2. 密级访问控制：文稿密级 + 用户密级/知悉范围；低密级用户看不到高密级稿件；导出/打印高密级
   需二次确认或审批（可先做本地审批记录）。
3. 安全标记：在数据库/资源层记录标记，读取路径统一鉴权；与 OS 级 MAC（SELinux/AppArmor/
   Windows 完整性级别）的一致性由部署方论证。
4. 默认账户：首次启用强制设密码；无内置默认口令；账户过期/停用清理。
5. 验收：低权限账户无法读取高密级稿件；审计员不能改数据；导出高密级有审批记录。

### 4.6 集中管控与安全管理中心：单机架构的硬缺口

**四级要求（9.1.5）**：系统管理员/审计管理员/安全管理员身份鉴别与限定入口；集中管控（管理区域、
安全传输路径、集中监测、集中审计留存、策略/恶意代码/补丁集中管理、事件分析、统一时钟）。

**现状**：单机离线，无管理端、无中心、无统一时钟、无策略下发、无日志上送；只有本机 UI。

**差距**：9.1.5.4 全部 C 类；9.1.5.1–9.1.5.3 可用本地三员部分满足。

**建议（P1）**：
1. 审计外送：syslog（RFC 5424）/HTTP/文件导出，支持 TLS 与签名，字段与中心对齐。
2. 时间同步：检测系统时钟偏差并在审计中记录时间源；支持 NTP 状态展示（不在应用内改系统时间）。
3. 策略文件：可导入组织下发的安全策略（口令策略、保留期、出口管控），带签名与版本号。
4. 补丁/版本：提供版本清单与离线升级包验签；支持集中分发（B 类）。
5. 文档：逐条写「不适用论证/部署方责任」，这是测评现场最常用的过关方式。

### 4.7 数据备份恢复：本地合格，异地/热冗余是架构问题

**现状**：加密 7z 全量备份、双槽快照、恢复隔离暂存、校验；但**手动**、无计划任务、无异地、
无热冗余、无恢复演练记录。

**建议（P1/P2）**：
- P1：备份计划提醒、备份完整性自动校验、恢复演练脚本与记录模板、RPO/RTO 文档；
- P2：支持备份到网络共享/对象存储（加密后上传）、双机部署说明、异地灾备方案（部署方）。

### 4.8 剩余信息保护：做了密钥，没做完「空间」

**现状**：密钥/口令 zeroize；临时文件与明文缓存清理；旧图片覆写删除；但 SQLite 页在内存中
明文（设计如此，文档已声明）；无 mlock/防交换、无 core dump 关闭、正文/PDF/DOCX 字节/模型
请求与响应不 zeroize、剪贴板不主动清空；崩溃日志注释明确「有路径、正文片段与系统信息」
（`src/crash_log.rs:34-36`，加密但解锁后可读）。

**建议（P1）**：
1. 敏感缓冲区 mlock（Unix `mlock`/Windows `VirtualLock`）+ 启动时关闭 core dump/降低可转储性；
2. 文档缓冲区在关闭/锁定后显式零化（需要改造持有类型）；SQLite 连接关闭时清理页缓存（能做的部分）；
3. 剪贴板：复制敏感内容后定时清空/提示；打印队列与临时副本的清理路径写入文档；
4. 安全删除：文件覆写 + 删除，并在文档中说明 SSD/日志文件系统/快照的不可保证边界；
5. 在帮助/部署手册中明确全盘加密（BitLocker/FileVault/LUKS）与 swap/hibernate 要求。

### 4.9 数据出口与个人信息：本地无采集，但模型/接口是出口

**现状**：无遥测、无云同步；但写作模型/知识库/数据接口可把正文、材料、表单要素、人员/单位
信息发送到用户配置的 OpenAI 兼容端点（可能是外部服务），**不按密级/个人信息脱敏**；接口密钥
加密保存；无出口审批、无 DLP、无外发审计；「检查更新」会在用户点击时连 GitHub（暴露 IP、
User-Agent、版本号，不含正文）；API 导入（cURL/文档 → 接口定义）会对密钥类字段先脱敏再交模型，
是少数有脱敏的链路。

**差距**：四级 9.1.4.11 b)「禁止未授权访问和非法使用」在「模型外发」这条链上缺少控制与证据；
个保法/数据安全法要求的最小必要、告知、加密、审计也需要落地。

**建议（P1）**：
1. 数据出口清单：明确哪些功能会把什么数据发到哪里（模型、接口、更新检查、发布页）；
2. 出口策略：模型/接口地址白名单（内网/本机优先）、外部地址二次确认、敏感内容提示/脱敏；
3. 出口审计：每次外发记录目标、用途、数据类别、结果（不含正文）；
4. 告知文本：使用帮助中的数据处理说明与「不上传」承诺边界。

### 4.10 供应链与建设管理：有基础，缺证据链

**现状**：Cargo.lock（`--locked`）、4 个 vendor 补丁、`THIRD_PARTY_NOTICES.md`、RustSec CI、
Dependabot、fmt/clippy/test 三平台门禁、多轮安全复检文档；**缺**：SBOM（CycloneDX/SPDX）、
可复现构建、发布签名、独立渗透测试/代码审计报告、fuzz、SAST/CodeQL/Semgrep、secret scanning、
cargo-deny（许可证/来源/禁用依赖）、CC/EAL 或销售许可、供应商安全评估记录、漏洞披露政策；
`release.yml` 不跑 `cargo audit`，新公告不会挡住发版。
另外，外部命令按 `PATH` 查找（`lp`、`fc-match`、`xdg-open`、`wl-copy`/`xclip`），
无哈希/签名白名单，存在 PATH 劫持/同用户替换风险（文档已列为已知取舍）。

**建议（P1/P2）**：
1. CI 生成 SBOM 与依赖清单，随 release 发布；记录构建环境与哈希（可复现构建目标）。
2. 每年一次独立渗透测试/代码审计（至少对加密、导入、导出、IPC 四条链）。
3. 建立漏洞披露与响应流程（`SECURITY.md`、邮箱、SLA、公告）；关键漏洞 7/30 天修复目标。
4. `release.yml` 增加依赖审计门禁；CI 增加 cargo-deny、SBOM、SAST、secret scanning。
5. 外部命令改绝对路径 + 哈希校验（或随包携带），消除 PATH 劫持面。
6. 对 vendor 补丁与自定义 crate 做来源与维护性登记；供应链安全评估表。
7. 长期：CC/EAL 或商用密码产品认证（视客户要求）。

### 4.11 管理要求：产品只能「配合」，不能「满足」

四级 9.1.6–9.1.8（制度、机构、人员）、9.1.9（建设管理）、9.1.10（运维管理）的大部分是组织
责任。产品侧可提供：安全策略模板、配置基线、交付清单、SBOM、漏洞响应流程、运维手册、
应急演练脚本。**不要在投标/交付材料里把这些写成「本软件已满足」。**

## 6. 架构性硬缺口（必须如实告知客户）

| 缺口 | 为什么单机离线做不到 | 替代方案 |
|---|---|---|
| 物理环境 10 项 | 是机房/设施要求 | 部署方按 GB/T 22239 物理要求建设；产品提供终端加固基线 |
| 网络架构/边界防护/入侵防范 | 无网络边界可守 | 由单位网络与安全设备承担；产品不监听端口、收敛出站 |
| 通信传输硬件密码模块 | 无硬件密码模块 | 外接密码机/USB 密码卡（B 类）或部署方链路加密 |
| 安全管理中心/集中管控 | 无中心、无统一时钟、无集中审计 | 提供审计外送、策略导入、时间状态接口；中心由单位建设 |
| 异地实时备份/热冗余/灾备 | 单机单点 | 备份包导出 + 单位备份系统/双机方案；RPO/RTO 由单位定 |
| 可信验证可信根/主动免疫 | 无 TPM/可信计算环境 | 签名发布 + 自校验（A 类）先行；TPM 长期项 |
| 管理制度/机构/人员/建设/运维 | 组织实体要求 | 单位制度与三员；产品提供模板、证据与培训材料 |

**结论**：如果客户要求「整个系统过五级」，软件只能承担其中一小部分；如果客户要求「软件产品
本身过五级」，应先纠正概念——等保没有「软件产品等级」这种证书，只有系统定级备案与测评。

## 8. 如果客户坚持「五级」，怎么答

建议按以下顺序回应，避免被带进「自证五级」的陷阱：

1. **先问定级**：请提供系统定级备案证明（备案号、等级）、主管部门核准/专家评审意见。
   没有定级，就没有「五级」这个对象。
2. **再问依据**：第五级的技术要求不在 GB/T 22239 公开文本中（第 10 章「略」），请提供
   国家指定专门部门/主管部门对本系统的特殊安全需求文件、测评机构与测评依据。
3. **再问密码**：是否要求商用密码？是否在密评范围？如要求，请提供密码应用方案要求与
   密评机构名单；当前产品使用国际算法，需按国密改造后才能满足。
4. **明确边界**：本产品是客户端组件，物理、网络、边界、集中管控、异地灾备、制度机构人员
   由系统/单位承担；产品负责客户端侧可承担的部分（数据加密、备份、输入校验、供应链证据等），
   身份鉴别、访问控制、安全审计按整改路线补齐，并提供对接接口。
5. **给替代承诺**：可承诺「按 GB/T 22239-2019 第四级安全计算环境中客户端适用条款进行
   差距整改，并配合系统测评与密评」，而不是「产品通过五级等保」。
6. **留证据**：每次沟通形成书面《适用性说明》，把「不适用条款 + 理由 + 替代措施」写清楚，
   这是测评现场最有效的材料。

## 附录 B：术语

- **等保 2.0**：网络安全等级保护制度 2.0 系列标准（GB/T 22239/22240/25070/28448 等）。
- **专控保护级**：行业俗称，不是 GB/T 22239/22240 或 43 号文的正式术语（正式表述只写「第五级」）；
  GB 17859-1999 第五级称「访问验证保护级」，与等保第五级不是同一套标准。
- **定级对象**：具有确定责任主体、相对独立业务、多个关联资源的系统；单一组件不作定级对象。
- **密评**：商用密码应用安全性评估，查合规性、正确性、有效性。
- **A/B/C 类**：本报告的可承担性划分（软件可实现 / 部署方实现+软件接口 / 单机架构难满足）。
- **不适用论证**：测评中对确实不适用的条款，说明理由与替代措施的材料。
