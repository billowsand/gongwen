# 数据接口工作台：以 OpenAPI 为中心的重新设计

> 2026-10-06。第一、二、三期已实现（见第十二节），待真机验收。同日与用户重新对齐需求后改写第二、三期（见第二节）：
> 不做类 Postman 的调试台界面，围绕「调通、用测试集证明可用、大模型正确调用」三个结果来做，
> 界面只在现有数据接口页上局部加。替代 `http-skill-design.md` 第一节起的「接口类技能」方案；
> 该文第〇节（文档识别、接入循环、页面改版、多组样例）的成果继续使用。
> 实施后同步 `ai-agent-workbench.md` 16.8 / 16.9 节，并在本文末尾的「进度与交接」记录各期情况。

## 一、为什么重做

数据接口目前能用：能从文档识别接口、多轮试调、问人补密钥，技能也能经 `http.call:<id>` 调用。
但用户的评价是「整个设计思路不清晰」，原因有三条：

1. **先做了最难的一步，最基础的一步没做。** `api_import/` 有一万多行，全在解决「从任意
   文档猜出接口」（cURL、请求行、参数表、Mintlify 标签……）。可 OpenAPI / Swagger / Postman
   这类**本来就是结构化的标准文件**反而不能导入（旧文档写着「后续再支持」）。
2. **没有「标准接口文件」这个东西。** 接口存在自定义的 `ApiEndpoint`（`apis.json`）里，
   只有 GET / POST、请求体只能是 JSON 模板。它把三件不同的事揉在一个结构里：
   - 接口是什么：地址、参数、请求体、返回；
   - AI 怎么用返回：返回映射成「标题 / 正文 / 出处」、返回去处；
   - 在哪台机器上跑：完整地址、`{secret:名字}`。
   要「生成标准接口文件」，但现在没有标准可对齐，也就没有「生成对了」的判据。
3. **给模型的工具规格很弱。** `ToolSpec` 的参数只有「名字 / 必填 / 说明」，**不带类型**
   （`toolcall.rs` 里明写「参数不标类型」），对象、数组、枚举全靠说明文字和样例让模型猜；
   中文接口 id 转工具名时全变下划线，`http.call:省统计` 与任何三个字的中文 id 都撞成
   `http_call_____`。

## 二、目标：三个结果，一个中心

用户要的是三个结果，界面已经够用，不另做调试台：

| 结果 | 怎么算做到 | 在哪一期 |
|---|---|---|
| **调通** | 拿到接口文档（标准文件或 Word / PDF），生成接口说明，实测能调通 | 第一期（标准文件）+ 已有的「从文档添加」与接入助手 |
| **用测试集证明接口可用** | 每个接口有一组用例，每条写明期望；一键跑完，记下几条过、哪条没过、什么时候跑的，随文件导出 | 第二期 |
| **大模型正确调用** | 给一句实际问题，模型选对接口、填对写明的参数，调用成功；一组 AI 用例跑出正确率与错例 | 第三期 |

```
 标准文件导入（OpenAPI · Swagger · Postman · cURL）   文档识别（Word · PDF · Markdown + 模型）
                  │ 确定性转换                                   │ 识别 → 试调 → 修到调通
                  ▼                                              ▼
        ┌────────────────────────────────────────────────────────────┐
        │   标准接口文件：OpenAPI 3.0 + x-gongwen（用例、AI 用例都在里面）   │
        └────────────────────────────────────────────────────────────┘
                  │                                              │
                  ▼                                              ▼
     「试一下」· 手填参数 → 接口用例                    「试一下」· 说一句话让 AI 调 → AI 用例
       证明接口可用（第二期）                             证明模型调得对（第三期）
```

**「试一下」与「用例」的关系**：「试一下」是调试，看这一次返回了什么，调通就算过，结果看完就算；
「用例」是证明，每条写着期望，对上了才算过，结果留记录。两者放在同一页：现在「试一下」的样例组
升级成用例，「全部 N 组试一遍」就是跑用例。不另开「测试」页，详情仍是「接口说明 / 试一下 / 技术配置」三页。

## 三、中心格式：OpenAPI 3.0 + `x-gongwen-*` 扩展

### 3.1 为什么是 OpenAPI

- 行业通用：Postman、Apifox、YApi、Swagger UI、各类网关都能导入导出；内网系统给的接口
  文档，有相当一部分本来就是 Swagger / Apifox 导出的。
- **参数用 JSON Schema 描述，和大模型原生工具调用的参数格式是同一种东西。** 一个
  operation 几乎一对一变成一个工具：`operationId` → 工具名，`summary` / `description` →
  工具说明，参数与请求体的 schema → 工具的 `parameters`。
- Postman Collection 记的是一次次具体请求（例子），没有参数结构；作为**来源**导入，不作中心。

存储与导出都用 **OpenAPI 3.0.3**（3.1 导入时降级：`type: [x, "null"]` → `nullable`，
`examples` 数组取第一个作 `example`）。理由是兼容面最广，Apifox 与内网老平台对 3.1 支持参差。
文件在内存里按 `serde_json::Value` 保存，**认识的字段编译成运行时结构，不认识的原样保留**，
保证「导入 → 导出」不丢东西。

### 3.2 扩展字段

我们自己需要、OpenAPI 没有的，全部放在 `x-gongwen-*` 扩展里。别的工具会忽略这些字段，
但导入导出都不会把它们弄丢。

| 字段 | 位置 | 含义 | 默认 |
|---|---|---|---|
| `x-gongwen-readonly` | operation | 只查询、不改变外部系统状态 | GET / HEAD → 是；地址带 delete、update 等字样或其余方法 → 否 |
| `x-gongwen-ai` | operation | 给 AI 用（前提是只读） | 只读的为是 |
| `x-gongwen-success` | 根 / operation | 业务成功判据 `{pointer: /code, equals: [0, 200]}`，operation 级覆盖根级 | 无 |
| `x-gongwen-evidence` | operation | 返回怎么进证据包：`{list, title, text, source, id}`，语义同现在的 `ApiMapping` | 无（按通用规则进证据包，见 6.6） |
| `x-gongwen-timeout` | 根 / operation | 超时秒数 | 30 |
| `x-gongwen-tests` | operation | 接口用例：参数 + 期望（见 5.2） | 无 |
| `x-gongwen-ai-tests` | operation | AI 用例：一句问题 + 期望的参数（见 6.2），存在期望被调用的接口上 | 无 |
| `x-gongwen-secret` | `securitySchemes` 下每项 | 这个鉴权方式用本机哪把密钥 | 方案名按 `redact::secret_name` 规整 |
| `x-gongwen-id` | operation | 本机接口 id（技能里 `http.call:<id>` 用）；迁移来的旧 id、改过的 id 记在这里 | `<服务 id>.<operationId>` |
| `x-gongwen-destination` | operation | `variable`：结果只放变量、不进证据包（旧版「返回去处」） | 证据包 |
| `x-gongwen-name` | 参数 / 请求体属性 / `requestBody` | 输入变量名与 OpenAPI 名字不同时（`q` 对应变量 `kw`、`X-Token` 这类不合标识符的） | 名字按标识符规整 |
| `x-gongwen-inputs` | operation | 输入变量的先后（与编译出来的自然顺序不同时才写） | 无 |
| `x-gongwen-template` | operation | 拆不成标准写法的部分原样留着：`path`、`query`（数组）、`headers`（数组）、`body` + `form`、`inputs`（没用上的变量） | 无 |

只读判定是红线相关字段：**导入器与模型只能把它从「是」改成「否」**；POST 接口要标成只读
（内网很多查询接口是 POST），必须人在界面上勾。

### 3.3 存储布局

| 文件（都在配置目录） | 内容 | 导出 / 分享 |
|---|---|---|
| `apis/<服务 id>.openapi.json` | 一个服务一份 OpenAPI：路径、参数、请求体、返回结构、样例、测试 | 是 |
| `api-envs.json`（新增） | 每个服务的环境：名字、实际服务器地址、变量；当前用哪个 | 否 |
| `api-secrets.json`（沿用） | 密钥名 → 值 | 否 |
| `api-tests.json`（沿用） | 测试结论与配置指纹，不存返回内容 | 否 |

- 一个「服务」= 一份 OpenAPI 文件，对应界面上的一个分组，通常就是一个内网系统。
- 文件里的 `servers` 照文档原样写（可能是示例地址）；**实际发请求的地址来自环境**，像
  Postman 的环境一样可以切「测试 / 正式」。没配环境时用 `servers` 的第一个。
- 鉴权按 OpenAPI 的 `securitySchemes` 写（`apiKey` 放请求头 / 查询参数 / Cookie，`http`
  的 bearer / basic）。值不进文件，由 `x-gongwen-secret` 指到 `api-secrets.json`。
  不再在请求头模板里写 `{secret:名字}`（迁移时自动转换）。

## 四、标准文件导入与导出（第一期，已实现）

导入、导出都是确定性转换，不用模型。界面在数据接口页的菜单里：「导入接口文件…」「导出为 OpenAPI…」。

### 4.1 支持的来源

| 来源 | 认法 | 转换要点 |
|---|---|---|
| OpenAPI 3.0 / 3.1（JSON / YAML） | `openapi` 字段 | 3.1 降级到 3.0.3；只解析文件内的 `$ref`，**不联网取外部引用**，导入文件夹时解析相对引用以后再做 |
| Swagger 2.0 | `swagger: "2.0"` | `host + basePath + schemes` → `servers`；`in: body` → `requestBody`；`definitions` → `components/schemas`；`securityDefinitions` → `securitySchemes` |
| Postman Collection v2.0 / v2.1 | `info.schema` 含 `postman` | 文件夹 → `tags`；`{{baseUrl}}/a/:id` → 环境变量 + 路径 `/a/{id}`；raw JSON 请求体 → 从例子推断 schema 并存为 `example`；保存的响应 → 返回样例并推断返回 schema；集合级与请求级 auth → `securitySchemes`；集合变量 → 环境 |
| Postman 环境文件 | `_postman_variable_scope: environment` | 变量进环境；`type: secret` 或名字像 token / key 的进密钥表 |
| cURL | `curl ` 开头 | 复用 `api_import::scan` 现有的 cURL 解析，一条命令 → 一个 operation |
| HAR（浏览器 F12 导出，**以后**） | `log.entries` | 只取 XHR / fetch 且返回 JSON 的请求；路径里的数字、UUID 段归并成 `{id}`；同一方法 + 路径合并，多次请求的取值作样例；Cookie、Authorization 提成密钥 |
| Apifox / YApi | — | 这两个平台都能导出 OpenAPI，引导用户导出 OpenAPI 再导入；YApi 原生 JSON 以后再说 |

**不支持、但会写进导入报告**的内容：Postman 的 pre-request / test 脚本（不执行，原文作为说明
保留）、OAuth2 授权流程（只能粘贴令牌）、callbacks、webhooks、links。

每次导入都出一份**导入报告**：新增几个 operation，哪些字段丢了或降级了、为什么，哪些接口
被判定为会改数据。

**再次导入同一个服务（以后）**时按 `operationId`（没有就用「方法 + 路径」）比对，列出新增、变化、
消失的接口，由用户逐项决定。用户自己设过的 `x-gongwen-*` 字段（只读勾选、证据映射、测试）
在更新时保留。

### 4.2 请求能力（第一期已实现，multipart 除外）

- 方法：GET / POST / PUT / PATCH / DELETE / HEAD（现在只有 GET / POST）。
- 参数位置：path / query / header / cookie；query 数组按 OpenAPI 的 `style` / `explode` 序列化。
- 请求体：`application/json`（按 schema 整段给，**不再用字符串模板替换**）、
  `application/x-www-form-urlencoded`、`multipart/form-data`（只发文本字段，第一版不传文件）。
- 返回：JSON 正常解析；文本原样显示；二进制只显示类型和大小，不交给模型。返回体上限
  仍是 4 MB。
- 执行层沿用 `api.rs` 的 `send` / `check_status` / `check_success` / `Trial`，扩展方法与请求体
  类型即可。

### 4.3 导出

- 导出一个或多个服务，得到 OpenAPI 3.0.3 的 JSON 或 YAML，带上 `x-gongwen-*`（用例、AI 用例都在
  里面，所以「证明」随文件走）；**不带环境和密钥**。
- 「导出为 Postman Collection」「把当前环境地址写进 `servers`」以后有人要再做。

## 五、接口用例：证明接口可用（第二期）

### 5.1 界面：「试一下」里的样例组升级成用例

现在的「试一下」：顶上一排样例标签（试过的标 ✓ / ✗），点一下填入参数，「全部 N 组试一遍」逐组发、
汇报调通几组，「存为样例」「AI 编几组样例」。第二期在这一页上加三样，布局不变：

1. **每个用例可以写期望。** 选中一个用例时，参数下面多一个「期望」小区，列出这条用例的期望，
   可增删。不写期望就是默认期望（见 5.3）。
2. **「存为用例」时建议期望。** 调通以后点「存为用例」，程序按这次的真实返回列出几条候选期望
   （见 5.4），人勾选确认后存下。
3. **结果留记录。** 「全部 N 组试一遍」跑完，每条用例的通过 / 失败、没满足的那条期望、运行时间
   记进 `api-tests.json`；「接口说明」页顶和左栏状态点的悬停说明显示「用例 6/6 通过 · 10-06 21:30」。
   接口配置改过（指纹变了）就显示「需重测」，沿用现在的规则。

另外两处小改动：

- **参数输入按类型出控件**（导入的 OpenAPI 带了类型）：枚举出下拉框，是否出勾选框，JSON 类仍是
  多行框。只换输入控件，不改布局。
- **会改数据的接口人可以手动发**：「试一下」的发送按钮弹二次确认，写明方法、完整地址和请求体
  摘要；这类接口的用例不参加「全部试一遍」，只能单条手动运行并确认。永远不给 AI 调。

### 5.2 用例格式

存在操作的 `x-gongwen-tests` 里（第一期已经在用，样例组就存在这里），第二期加上 `expect`：

```json
"x-gongwen-tests": [
  {
    "name": "按地区和年份查",
    "note": "最常用的查法",
    "args": {"region": "全省", "year": 2025},
    "expect": [
      {"kind": "min_items", "pointer": "/data/items", "value": 1},
      {"kind": "equals", "pointer": "/data/items/0/region", "value": "全省"}
    ]
  }
]
```

- `args` 用编译后的输入变量名（就是现在样例组的写法），所以用例同时也是给模型看的用法示例
  （`spec_of` 已经把前 3 组写进工具说明）。
- 没有 `expect` 或为空：只用默认期望。

### 5.3 期望的种类

每条用例都先过**默认期望**：发得出去、HTTP 2xx、业务成功判据成立（配了的话）、不是网页（登录页）。
这就是现在「试一下」判调通的那一套（`api::trial`），不另写。在此之上可以加：

| 种类 | 写法 | 含义 |
|---|---|---|
| 不为空 | `{"kind": "not_empty", "pointer": "/data/items"}` | 指针处有值，且不是空数组、空对象、空字符串 |
| 至少几条 | `{"kind": "min_items", "pointer": "/data/items", "value": 1}` | 指针处是数组，长度不少于 N |
| 等于 | `{"kind": "equals", "pointer": "/data/total", "value": 3}` | 取值相等（数字按数值、文字去首尾空白比） |
| 包含 | `{"kind": "contains", "pointer": "/data/items/0/title", "value": "防火"}` | 取值的文字里含这段 |
| 有字段 | `{"kind": "exists", "pointer": "/data/items/0/count"}` | 返回里有这个字段（值可以是 0、空） |

指针为空表示整个返回。只做这五种，够证明「接口按条件返回了对的东西」；不做脚本、不做正则。
失败时说清是哪一条：「期望 /data/items 至少 1 条，实际 0 条」。

### 5.4 用例从哪来

| 来源 | 参数 | 期望 |
|---|---|---|
| 「试一下」调通后「存为用例」 | 当前填的参数 | 程序按真实返回建议，人勾选：列表位置有数据的建议「至少 1 条」；成功判据字段建议「等于」当前值；参数值出现在返回里的（查「全省」返回里有「全省」），建议对应字段「包含」它；`/data/total` 这类计数建议「有字段」 |
| 文档里的请求示例、OpenAPI 的 `examples` | 导入时已转成用例 | 无（默认期望），跑通后可以补 |
| 「AI 编几组样例」（已有，改名「AI 编几条用例」） | 模型按说明编，覆盖各个枚举与分支 | 无；先跑一遍，跑通的再按真实返回补期望 |

程序建议的期望只是候选，**人勾了才存**；模型不直接写期望（它没见过真实返回，写了也是猜）。

### 5.5 运行与记录

- `api-tests.json` 的 `TestRecord` 加 `cases`：每条用例的名称、通过与否、没满足的期望（一句话）。
  仍不存返回内容与参数值。
- 「接口说明」页顶显示通过情况；左栏状态点：全部通过绿、有失败红、没跑过或需重测灰。
- 服务页「全部重测」改为跑这个服务所有接口的全部用例。

### 5.6 第二期验收

- 第一期的夹具与一份内网真实 Swagger：每个只查询接口至少一条带期望的用例，全部跑通；
  改一个期望值让它失败，界面写清哪条没满足。
- 会改数据的接口：手动发送弹确认；「全部试一遍」跳过它。
- 用例随「导出为 OpenAPI」导出，再导入后用例与期望不变。

## 六、AI 调用：证明大模型调得对（第三期）

### 6.1 界面：「试一下」的第二种试法「说一句话让 AI 调」

「试一下」顶上加一个切换：「手填参数」（现在的方式）/「说一句话让 AI 调」。后者：

1. 输入一句问题，例如「2025 年全省森林火灾多少起」；
2. 程序把**这个服务里给 AI 用的接口**编成工具交给模型（工具说明与正式运行完全一致，见 6.3），
   用「模型服务」里起草用的模型（与技能运行时一致），走自主步骤同一套调用协议（原生工具调用，
   不支持时文本兜底，`ops/agent.rs`、`toolcall.rs`）；
3. 界面显示模型**选了哪个接口、填了什么参数**、参数校验过没过，然后实际调用一次，显示返回；
4. 选得对就点「存为 AI 用例」：记下「这句话 → 应该调这个接口、这几个参数取这些值」。
   参数期望默认勾上模型填的全部参数，人可以去掉不需要锁定的（比如页码）、改错的值。

只对「只查询且给 AI 用」的接口开放（只查询，所以实际调用是安全的）。

### 6.2 AI 用例格式与判定

存在**期望被调用的那个接口**的操作上：

```json
"x-gongwen-ai-tests": [
  {
    "question": "2025年全省森林火灾多少起",
    "expect": {"args": {"region": "全省", "year": 2025}}
  }
]
```

判定「调对了」（已与用户确认）：

1. **接口选对**：模型调用的是这个接口；
2. **写明的参数对**：`expect.args` 里列出的参数，模型给的值一致（文字去首尾空白比、数字按数值比、
   对象数组按 JSON 比）；没列出的参数模型可以自由发挥；
3. **调用成功**：参数过了调用前校验（6.4），实际调用满足这个接口的默认期望。

失败分四类，界面与记录里写明：选错接口（选了哪个）/ 没调接口 / 参数不对（哪个参数、期望与实际）/
调用失败（校验没过或接口报错）。

### 6.3 让模型拿到准确的工具说明

AI 用例跑不过，多数是工具说明不够。这一期把第一期留下的弱点补上：

- **工具名**：`api__<服务>__<operationId>`，只用 ASCII 字母、数字和下划线，长度不超过 64
  （超长截短加哈希），编译时检查全局唯一；顺带修掉 `wire_name` 的中文撞名（`http.call:省统计`
  与任何三个字的中文 id 都撞成 `http_call_____`）。
- **工具说明**：`summary` + `description` + 前 3 条用例的参数（沿用 `spec_of`）+ 返回的顶层字段。
- **参数带完整 JSON Schema**：`ToolSpec` 加 `schema: Option<Value>`，原生工具调用直接发 schema
  （类型、枚举、嵌套、必填）；文本兜底把 schema 渲染成紧凑签名，如
  `region: 文字（必填）, year: 整数, level: "省"|"市"|"县"`。schema 取自 OpenAPI 原文
  （`ApiInput.schema`，第一期已在编译时带上）。
- 鉴权参数不出现在工具里。

错例的修法就是改接口说明、参数说明、补枚举，改完在同一页再跑 AI 用例——「改说明 → 测 → 再改」的
闭环全在「试一下」里完成。

### 6.4 调用前校验

模型给的参数**先按 schema 校验，不合格不发请求**：必填缺了、类型不对、不在枚举里、对象或数组的
嵌套结构不对，错误原样回给模型，让它自己改（正式运行时同样如此）。校验先自己写一个子集（必填、
类型、枚举、数组 / 对象嵌套、`format` 只认 date / date-time），不引入新依赖。

### 6.5 AI 用例从哪来、怎么跑

- 来源：「存为 AI 用例」；或「AI 出几个问法」——模型按接口说明出几句不同问法的问题并给出它认为
  的参数，**人逐条确认参数期望后才存**（期望不能由模型说了算）。
- 运行：「全部试一遍」旁边单列「AI 用例 N 条」按钮（要调模型，慢，和接口用例分开跑），跑完给出
  正确率和错例；记录写明用的哪个模型，换模型可以对比（内网 MiniMax 2.7 / DeepSeek v4 flash）。
- 记录同样进 `api-tests.json`，不存模型输出全文与返回内容，只存结论与一句话原因。

### 6.6 返回怎么给模型

- **每次调用都进证据包**，否则红线三的「来源不明的数字」会把用到接口数据的稿子全挡掉：
  - 配了 `x-gongwen-evidence` 的，按映射拆成条目（就是现在的行为）；
  - 没配的，一次调用算一条证据：标题是「接口名 + 参数」，正文把 JSON 平铺成
    「字段路径：值」一行一条，方便事实比对按原文查找。
  - **待验证**：`ai_guard` 认的数量是「数字 + 单位」，JSON 里的数通常不带单位。第三期要
    确认平铺正文能不能让关键事实溯源成功，必要时从 schema 的 `description` 里取单位一起写。
- 交给模型的内容按结构裁剪：数组超过 N 条截断，并说明「共 M 条，只给了前 N 条」；长字符串
  截断；整体受 `agent/budget.rs` 的上下文预算约束。

### 6.7 接口多时分两级

一个服务动辄上百个接口，全部编成工具会撑爆内网小模型的上下文，也会降低选对接口的概率。
技能能调用的接口超过阈值（暂定 12 个）时，不再逐个给工具，只给两个：

- `api.search(query)`：在技能允许范围内按名称、说明、标签搜索，返回前 k 个接口的工具名、
  说明和参数签名；
- `api.call(api, args)`：调用一个接口。`api` 必须在技能白名单里，否则程序拒绝。

兜底技能「自由任务」通过 `api.search` 使用全部「只读且给 AI 用」的接口（已定）。

### 6.8 第三期验收

- 第一期夹具里的服务各写 5 条以上 AI 用例（含枚举参数、对象参数），DeepSeek-V4-Flash 与
  MiniMax-M2.7 跑出正确率；把一个参数说明故意写含糊，看到错例，改好后再跑通过。
- 50+ 接口的服务上（触发 6.7 的两级访问），AI 用例仍能选对接口。
- 接口数据进稿后，事实溯源通过（6.6 的待验证项）。

## 八、迁移（第一期，已实现）

首次启动时，如果 `apis.json` 存在而 `apis/` 目录为空：

1. 按服务器（现有的 `host_of`）把旧接口分组，每组生成一个服务；
2. 每个 `ApiEndpoint` 转成一个 operation：
   - 地址模板拆成 server + path，路径里的 `{var}` 变成 path 参数；
   - 查询串里的 `a={var}` 变成 query 参数，写死的值变成单值枚举加默认值；
   - 含 `{secret:x}` 的请求头变成 `apiKey` 鉴权方案（`x-gongwen-secret: x`），Authorization
     Bearer 的变成 `http bearer`；
   - `InputKind` 转 schema 类型（文字 → string，数字 → number，是否 → boolean，JSON → 不限类型）；
   - 请求体模板能拆成「顶层属性 = 变量或常量」的转成 schema；拆不了的（变量嵌在深层、或
     拼在字符串里）保留在 `x-gongwen-template.body`，编译器对它走旧的模板替换；混着变量的
     查询参数、请求头同理；
   - `mapping` → `x-gongwen-evidence`，`success` → `x-gongwen-success`，样例 → 测试用例，
     旧 id → `x-gongwen-id`；
   - 同一地址同一方法有几个（旧版按请求体里写死的字段分成几个接口）：OpenAPI 放不下，
     后面的放进同一服务器的副本服务（`<服务 id>-2`，标题加序号）；
3. `apis.json` 改名为 `apis.json.bak`，不删除；`api-tests.json` 不改，指纹变了的显示「需重测」。

迁移有单元测试（`apidef/tests.rs` 的 `legacy_endpoints_migrate_without_changing_requests`）：
六种旧写法迁移后，id、名称、说明、变量、映射、判据、样例不变，同一组参数组出的请求（方法、
地址、请求头、请求体）相同，再存一次文件一字不差。

## 十二、进度与交接

### 第一期：中心格式、标准文件导入导出、迁移（2026-10-06，已完成）

**做了什么**

- 接口的真身改成 `配置目录/apis/<服务 id>.openapi.json`（OpenAPI 3.0.3），环境在 `api-envs.json`。
  `ApiStore::load()` 读服务文件并编译成 `endpoints`；`ApiStore::save()` 把界面改过的接口写回
  （`apidef::absorb`）再落盘。只有旧版 `apis.json` 时第一次读就迁移，原文件改名 `.bak`。
- 导入（AI 管理页「数据接口」→ 菜单「导入接口文件…」，可多选）：OpenAPI 3.0 / 3.1（JSON、YAML）、
  Swagger 2.0、Postman 集合 v2.0 / v2.1（同时选环境文件时变量取环境的值，标成 secret 的与鉴权里的
  凭据进密钥表）、cURL（走 `api_import::analyze` 的程序解析）、旧版接口配置。导入后出报告：
  几个接口、几个按会改数据处理、几个发不了及原因、丢掉或降级了什么。
- 导出：菜单「导出为 OpenAPI…」，一个服务存一个文件（JSON 或 YAML 看扩展名），几个服务选文件夹。
  先把没存的修改写回一份副本再导出；不带环境与密钥。
- 运行层（`api.rs`）：方法加 PUT / PATCH / DELETE / HEAD；请求体可以是表单
  （`BodyKind::Form`）；没给的可选变量，整段只是它的查询参数、请求头、请求体字段**不发**；
  数组查询参数逐个重复（`ids=1&ids=2`），`explode: false` 的连成 `ids=1,2`。
- `ApiEndpoint` 加了 `readonly`（只查询）、`ai`（给 AI 用）、`body_kind`、`unsupported`（发不了的
  原因，`problems()` 会报）、`origin`（来自哪个操作，不序列化）；`ApiInput` 加了 `comma`、
  `schema`、`wire`（后两个不序列化）。
- 红线落地：`http.call` 拒绝不是只查询或没开放给 AI 的接口；`api::trial` 不试调会改数据的接口
  （人工发送等第二期的二次确认）；`skill::missing_apis` 把这两类也列出来并注明原因。
- 界面（改动最小）：「技术配置」方法改下拉、加「只查询，不改数据」「给 AI 用」两个勾、请求体可选
  JSON / 表单；方法标签给 PUT / PATCH / DELETE 配色。
- 测试：`apidef/tests.rs` 11 个（迁移、四种格式、写回不走样、改地址、导出再导入、只读闸门、
  cURL、读写与迁移落盘），另有 `schema`、`postman` 的单元测试；全量 1735 个通过，clippy 零警告。
  本机真实 `apis.json`（1 个接口）用副本试迁移通过。

**与方案的出入**

1. **没有另起一套运行时结构**：方案写的是「`ApiEndpoint` 在调用方换掉后删除」。实际做法是
   `ApiEndpoint` 就当编译产物，再加一个写回（`raise.rs`）：界面、接入助手、`http.call`、技能检查
   都不用改就能跑在 OpenAPI 上。写回按三种情况处理：和文件一样的不动；只改了名称、说明、映射、
   样例、只读这类的只改操作上的这些字段（`$ref`、标签、返回结构都留着）；改了请求的按模板重新
   拆（这时参数 schema 会内联，原 schema 若类型没变则沿用）。第二期的调试台直接在 OpenAPI 上做，
   写回仍然给接入助手（第四期）用。
2. 扩展字段：`x-gongwen-legacy-id` 改名 `x-gongwen-id`（不只迁移用，改过 id 也记这里）；
   `x-gongwen-body-template` 泛化成 `x-gongwen-template`；新增 `x-gongwen-destination`、
   `x-gongwen-name`、`x-gongwen-inputs`。见 3.2。
3. **行为变化**：没给的可选变量以前会发空值（`region=`、`"page": null`），现在整项不发。
   符合 OpenAPI 语义，但万一有内网接口必须收到空参数，要在模板里写成固定值。
4. 改了某个接口地址里的服务器部分：若对得上别的服务就挪过去；否则改的是**整个服务**的环境地址
   （同一服务的接口都跟着换），文件里的 `servers` 不动。
5. `x-gongwen-tests` 的 `expect` 还不执行（第二期），写回时按用例名原样保留、不看格式；第二期定为数组（5.2）。
6. 项目的 `serde_json` 经依赖开了 `preserve_order`，对象键保持原顺序；导出的文件顺序与原文一致。

**已知坑 / 没做的**

- 只解析文件内引用；指向别的文件的 `$ref` 只在报告里列出，相关 schema 按任意值处理（方案里
  「导入文件夹时解析相对引用」挪到「以后」）。
- multipart 请求体、`deepObject` 等查询参数写法、digest 鉴权：导入时标「暂时发不了」，原文保留。
- Basic 鉴权的密钥值要放 `base64(用户名:密码)`；Postman 导入时程序已编码，手填的要自己编码。
- Postman：同一路径同一方法的请求只收第一个（报告里列出）；前置 / 测试脚本不执行。
- 环境只有「当前地址」能改（改接口地址时自动记），多环境切换界面挪到「以后」。
- 工具调试台选中 `http.call` 时每帧 `ApiStore::load()` 一次（旧代码就这样），接口多了要改成缓存。

**待真机验收**：用一份内网真实的 Swagger / Apifox 导出导入、调通，导出的文件在 Apifox 里打开。

### 第二期：接口用例（2026-10-06，已完成）

**做了什么**

  `detail/header.rs`（顶部与密钥条）、`doc.rs`（接口说明）、`try_tab.rs`（试一下）、`config.rs`

  `ExpectKind::build`（界面表单 → 期望，指针与值的校验）、`judge`（先过默认期望即 `trial` 调通，
  再逐条检查，失败说「期望……，实际……」）、`run`（跑一条用例）、`suggest`（按真实返回建议：
  列表至少 1 条、成功判据字段等于这次的值、参数值出现的字段包含它、total / count 一类有字段，
  最多 6 条）。

  `ApiTestLog.suites` 存最近一次整组用例的结论。状态优先看配置没改过的整组结论，其次单次试调，
  都改过了显示「需重测」。左栏、顶部的状态片显示「用例 5/6 通过 · 时间」。
- 「试一下」：样例改叫用例；选中用例时下面是期望区（列出、删掉、按种类 / 位置 / 值加一条、
  「按这次的返回建议」一键加）；「全部 N 条用例跑一遍」逐条判并记录（会改数据的接口不显示这个
  按钮）；「存为用例」存下当前参数，这次调通过的直接算 ✓ 并给出建议期望；「AI 编几条用例」只编
  参数，期望要跑通后人加。选着用例「发送请求」时，响应区说明这条用例过没过、没满足哪条。
- 参数输入：有枚举的、是否类的出下拉框（可选参数多一个「不填」）。
- 会改数据的接口：请求区标明；「发送请求」先弹确认框（`crate::modal::dialog`），列出要发出的请求
  （密钥打码），确认后走 `api::trial_by_hand`；`api::trial` 仍然不发（自动试调、全部跑一遍、AI 都
  碰不到）。
- 「接口说明」页「用例」一节：每条用例的期望、最近一次整组结论（✓ / ✗ 与原因）。
- 测试：`cases.rs` 3 个；`apidef/tests.rs` 加了人工发送、期望随 OpenAPI 往返与导出、状态优先级 3 个；
  界面测试按新文案更新并检查整组结论与建议期望。全量 1741 个通过，clippy 零警告。

**与方案的出入**

1. 服务页「全部重测」与换 Key 后的自动重测仍是每个接口用第一组参数单次试调（快，用来确认 Key），
   没有改成跑全部用例；整组用例在接口的「试一下」里跑。
2. 用例的期望在「试一下」左栏选中用例时编辑，没有单独的期望编辑页。
3. 建议期望按「这次的返回」给：选中用例显示的是它最近一次的结果；改过参数再发，建议就按新返回算。

**已知坑**

- 期望只认 JSON 返回；返回不是 JSON 时写了期望的用例一律不过（只要求调通的不受影响）。
- 「等于」对数字与数字样的文字（`0` 与 `"0"`）视为相等，文字去首尾空白比；要严格类型比较的场景
  目前没有。
- 界面没在桌面上目视过（只有渲染文字的界面测试），期望区在窄窗口下的排版待真机看。


**待真机验收（第二期）**：选一个内网接口，存两三条用例、加期望、全部跑一遍；改一个期望值看失败
原因是否说得清；会改数据的接口点发送时确认框是否列清请求。

### 第三期：AI 调用（2026-10-06，已完成）

**做了什么**

- `apidef/tooling.rs`：接口编成模型工具。参数是完整 JSON Schema（类型、枚举、嵌套、必填，取自编译时
  带上的 OpenAPI 原 schema，去掉 `nullable`、`example`、`x-*` 这类 OpenAPI 专有字段）；说明是用途 +
  前 3 条用例的参数；调用前 `validate`（必填、多余参数、类型、枚举、数组元素与对象必填各一层，
  对象写成 JSON 字符串的先读出来），不合格不发请求，把错在哪、参数签名与正确示例回给模型。
  一次能用的接口超过 12 个时改成 `api_search` / `api_call` 两级（`ApiTools::Search`）。
  （2026-10-07：自主步骤里这两个并进内置工具共用的 `tool_search` / `tool_call`，见
  `docs/agent-kernel-hardening.md` 3.3；「说一句话让 AI 调」仍用 `api_search` / `api_call`。）
- `ToolSpec` 加 `schema: Option<Value>`，原生协议有就原样发；内置工具仍为 `None`，留给
  `docs/agent-kernel-hardening.md` 第 1 期逐个补，两边不冲突。`wire_name` 遇到中文或超过 64 字符时
  截短加 id 的哈希，中文接口 id 不再撞名。
- 自主步骤（`ops/agent.rs`）的接口工具改由 `tooling` 生成；`http.call` 工具先校验再调；白名单认
  `http.call:<服务>.*` 与 `http.call:*`（只展开只查询且给 AI 用的接口，`tooling::expand` / `allowed`）；
  只写 `http.call` 的等于 `http.call:*`。「自由任务」开放了 `http.call:*`，正文写了数据接口的用法。
- `apidef/ai_cases.rs`：`attempt`（说一句话让 AI 调：给模型这个服务里给 AI 用的全部接口，最多 4 轮，
  参数不合格回给模型改一次，合格后实际调用）、`judge`（接口对 + 写明的参数对 + 调用成功；失败分
  没调接口 / 选错接口 / 参数不对 / 校验没过 / 调用失败）、`propose`（模型出 4 个问法与参数，参数过了
  校验才作候选）、`expect_from`（按输入类型规整期望值）。
- `ApiEndpoint.ai_cases`（`x-gongwen-ai-tests`，不进配置指纹）；`ApiTestLog.ai_suites` 记最近一次整组
  AI 用例的结论与模型名（`TestRecord.model`），不参与接口状态。
- 界面：「试一下」顶上切换「手填参数 / 说一句话让 AI 调」。AI 那页（`detail/ai_try.rs`）左边是 AI 用例
  标签、提问框、「让 AI 调」「全部 N 条 AI 用例跑一遍」「AI 出几个问法」与候选（加进 / 不要）；右边是
  模型先搜了什么、调了哪个接口（不是这个接口时提示多半是用途写得不够分明）、填了什么、改过一次的
  原因、校验与调用结果；选对了勾选要锁定的参数，「存为 AI 用例」。不给 AI 用的接口、没选起草模型时
  说清原因。「接口说明」页加「AI 用例」一节，显示期望与最近一次结论（悬停看模型）。
- 测试：`tooling` 4 个、`ai_cases` 3 个（脚本模型：选对与判定、参数回给模型改一次、不调接口、出问法
  只收合格参数）、`apidef/tests.rs` 加 AI 用例往返；界面测试 1 个。全量 1755 个通过，clippy 零警告。

**与方案的出入**

1. 技能写法没有新增 `api:<服务>.<operationId>`，沿用 `http.call:<接口 id>`（接口 id 默认就是
   `<服务>.<operationId>`），只加了 `http.call:<服务>.*` 与 `http.call:*` 两种通配。少一套写法，旧技能不用改。
2. 6.6「返回进证据」没有改：`http.call` 本来就把每次返回按映射（没配映射按常见字段名猜）整理成条目并入
   证据包。方案里的「待验证：JSON 里的数不带单位，事实溯源能不能对上」仍待真机验证。
3. AI 试调的系统提示是一段中性的「帮用户查内网数据」，不是某个技能的提示；工具说明与自主步骤完全一致。
4. 工具调试台没有改：它对 `http.call` 仍按旧方式列接口 id（每帧读一次接口清单的老问题也还在）。

**已知坑**

- AI 试调、全部跑一遍、出问法都用起草模型，每条要调一次模型，跑得慢、有费用；没有停止按钮，切到别的
  接口时后台线程会跑完再丢结果。
- `propose` 的期望参数来自模型，**人确认前不进用例**；界面上候选只给「加进 / 不要」，要改期望值得先加进
  再删了重存（或在 AI 试调里存）。
- 判定「参数对」时数字与数字样的文字视为相等（`2025` 与 `"2025"`），对象与数组按 JSON 比。

**待真机验收（第三期）**：拿一个内网服务（最好 3 个以上相近接口），每个接口存 3–5 条 AI 用例，分别用
DeepSeek-V4-Flash 与 MiniMax-M2.7 全部跑一遍看正确率；把一个参数说明故意写含糊，看错例能不能说清、改好后
能不能跑对；接口超过 12 个时看两级访问能不能找对接口。
