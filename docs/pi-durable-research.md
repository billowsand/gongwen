# Pi Durable 接入公文助手的调研

调研日期：2026-11-01。项目基线：`main` / `e5115c3`。
本文是选型建议，未修改现有架构决定，也未实现或实测 Pi 接入。
已有的 `docs/table-ime.md`、`src/ime/candidates.rs` 工作区改动不在本次范围内。

## 一、结论

**可以将 Pi 作为随应用分发的本地智能体运行内核，值得做有边界的替代试点。优先考察 Pi Durable，保留 Rust 的公文领域工具、证据与审阅合并。**

这能把通用的模型循环、对话状态与恢复机制交给上游维护，但不能免去领域开发。真正需要减少的是公文助手自己承担的通用运行时职责；词库约束、事实来源、要素建议和正式稿合并仍属于产品核心。

不能承诺“换上 Pi 就写得好”。Durable 改善运行可靠性；写作质量还取决于模型、材料组织、检索结果、提示词与修改方式。本次没有真实任务对照数据，质量提升只是待验证假设。

## 二、核实到的 Pi 现状

截至调研时，官方 GitHub 最新 Release 标记为 **v1.4.0**。下文以该 tag 为评估基线，不把 `main` 上未发布的 API 算入可用承诺。[官方 Release](https://github.com/earendil-works/pi/releases/tag/v1.4.0)

需要区分三个层次：

| 层次 | 用途 | 对本项目的意义 |
| --- | --- | --- |
| Pi Coding Agent | 面向终端用户的产品，也提供 SDK | 快速验证技能与交互；不是 Durable 的另一个名字 |
| Pi AI | 模型与供应商访问层 | 可减少模型协议维护，仍要适配本项目配置与端点差异 |
| Pi Durable | 面向应用的持久化智能体内核 | 本次主要候选 |

官方明确说明 Durable 是独立的应用框架，不是 Coding Agent 的替代版本，也不要求部署到云上。[发布说明](https://earendil.com/posts/pi-durable/)

v1.4.0 的 Durable 文档确认：支持本地存储、模型和工具任务恢复、扩展注册、上下文压缩、用量统计；工具中断后是否重跑取决于 replay 策略。它仍标为 **Experimental**。这些能力与本项目通用内核职责重合。[固定版本文档](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/README.md)

该包是 JavaScript/TypeScript 模块，声明 Node.js `>=22.19.0`，许可证 MIT。因此，Rust 项目最自然的集成是携带 JS 运行时和一个后台进程；不能当作 Rust crate 直接链接。[包定义](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/package.json)

## 三、项目实际已经有什么

本次读取了架构与加固文档，以及流程引擎、自主算子、工具、技能、检查点、分阶段写作与提案接受的实现。

| 能力 | 代码落点 | 调研判断 |
| --- | --- | --- |
| 声明式技能流程、条件、逐项执行 | `src/agent/engine.rs`、`skill.rs` | 已是自研运行时，不只是几段提示词 |
| 原生工具调用、文本协议兜底、循环与收尾 | `src/agent/ops/agent.rs`、`toolcall.rs` | 与 Pi 有较大替代空间 |
| 检查点、挂起与恢复 | `src/agent/checkpoint.rs`、`src/ai_panel/checkpoint.rs` | 已有流程步骤级恢复，迁移不应说成从零补能力 |
| 知识库与稿件库 | `src/agent/tools/store.rs`、`tools/mod.rs` | 可复用现有 Rust 实现 |
| 工作稿读写 | `src/agent/tools/workspace.rs` | 适合做工具桥接，但需要补跨进程恢复契约 |
| 要素建议、人工决策 | `element_fields`、`agent/decision`、`clarify`、侧栏卡片 | 属于领域能力，不能交给通用框架自行决定 |
| 提案与正式稿合并 | `src/app/ai_proposal.rs` | 必须保留人工入口、事实确认和正文过期检查 |
| 素材—提纲—分节写作—统稿 | `src/agent/writing/`、`src/draft_page/writing/` | 当前还有一条独立写作执行链，不宜在首轮一起重写 |

### 能解释部分体验问题的结构性线索

以下是代码推断，不是已经验证的故障归因：

1. “研究式起草”技能先走澄清、预研、检索、生成、缺口循环、核验、提问。步骤固定，简单任务也可能经历较多调度；复杂任务则受预设算子的能力限制。
2. 自主算子的 `ask_user` 当前采用“提问结束本轮，答完从头重跑该步骤”，仅带回进度摘要，而不是原工具对话完整续接（见 `ops/agent.rs` 文件头及 `SuspendAgain` 路径）。这可能造成重复判断或上下文损失。
3. 自主循环的工具结果上限为 6000 字符，并有较早工具结果压缩。这样有助于控制窗口，但也可能让细节密集的修改任务缺信息。
4. 智能体流程与固定阶段写作并存，分别维护执行、保存和上下文逻辑；后续通用增强容易重复建设。

Pi 能提供更统一的运行底座，但不能直接消除检索不准、提示词不足、材料缺失或模型工具能力弱等问题。

## 四、哪些能复用，哪些需要转换

### 4.1 外部公文技能包：内容复用程度高

`skills/gongwen-markdown/` 包含标准形式的 SKILL.md、文种说明、语法、模板和自检脚本。它最适合成为 Pi 使用的公文写作知识。

Coding Agent 已有技能发现和按需读取机制。Durable 的扩展体系可以承载技能目录与读取，但不能把 Coding Agent 的技能加载器、插件和 CLI 行为默认视为 Durable 已有的同一套功能。[Pi 技能说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)、[Durable 扩展示例规范](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/docs/spec.md)

建议实现一个范围很小的技能适配：列出技能 → 读取已打包的技能正文与 references/templates。用户明确点选技能时直接加载，避免再花一次模型调用猜技能。自检脚本不必开放任意 Python 执行，可由 Rust 校验工具提供对应能力。

### 4.2 应用内技能：不是复制目录就完成迁移

`assets/agent-skills/` 当前登记了 15 个内置技能。它们使用 `flow`、`params`、`when`、`references` 和算子名；这些字段由公文助手解释，Pi 不会自动执行相同语义。

建议分两类迁移：

- 润色、压缩、审查、自由任务：转为自然语言技能，由模型选择工具与步骤。
- 要素抽取、引用核验、受控确认：保留确定性工具或显式的人机交互协议。

首轮不要开发一个“在 Pi 上解释原 flow DSL”的兼容引擎，否则只是给原有框架再套一层。旧技能继续由旧引擎执行，新试点独立加载转换后的技能。

### 4.3 知识库、词库、接口：复用 Rust 工具

知识库已经通过 `KnowledgeSearch` / `RagSearch` 复用 `rag::retrieve`，还有全文读取和列表入口。Pi 只需调用桥接工具，不需要迁移向量、重建索引或让 JS 直接访问业务数据库。

工具应返回来源 ID、文档版本/内容哈希、摘录及截断标志。证据台账由程序保存，不能只依赖压缩后的对话记忆。标准词库与要素建议继续由 Rust 检查；内网 HTTP 工具继续复用已配置端点、schema 与权限限制。

## 五、建议集成边界

建议结构：

```text
egui 界面 / 稿件与审阅
          │ 请求、增量、决策、提案
Rust 领域服务与桥接层
          │ 双向 JSON 消息（后台线程读写）
随包携带的 Pi host + Node.js
          │
Pi Durable + 技能适配 + 模型供应商
          │ 工具调用回到 Rust
知识库 / 稿件库 / 工作稿 / 校验 / 词库 / 内网接口
```

这是产品内部集成；用户不需要另装 Pi、Node 或在终端操作。不需要 Cloudflare、Temporal 等额外平台。首版用私有 stdio 协议即可，不必为接入再建设通用 MCP 服务。

Rust 的 UI 主线程只消费事件和执行用户采纳；读写管道、模型与工具等待在后台运行。Pi host 的标准输出专用于协议，日志走标准错误；消息包含稿件、会话、任务、调用 ID 与协议版本。

### 三条红线的执行位置

1. **正式稿**：不给 Pi 注册直接写正式稿的工具。Pi 只能提交工作稿/提案，最终走现有人工审阅接受入口。
2. **要素**：授权类只读，不出建议和题目。描述类仅生成有出处的候选，由 Rust 校验、由用户采纳，再通过 `element_fields::apply_field` 写值。
3. **闸门**：可以注册校验工具供模型自查；交付与接受前的强制检查留在 Rust 主程序中。技能、hook 或模型声明“已检查”均不能替代强制关卡。

不注册 CodingTools 的任意文件写入和 shell 工具。技能读取用受限工具；知识库访问也只经工具白名单。技能里的 `tools`/`allowed-tools` 文本不能充当权限控制。

## 六、durable 最容易低估的接入工作

### 6.1 两个进程的状态不自动成为一个事务

Pi 记录“工具运行完成”和 Rust 记录“工作稿已修改”之间存在崩溃窗口。不能给所有写工具直接标记 replay-safe。

建议 Rust 工具写入采用 `operation_id + expected_workspace_revision`，在同一事务中保存操作回执与工作稿版本；重复调用返回原回执。整篇替换也需要版本检查，追加/插入尤其需要去重。跨进程超时不能直接当成未执行。

对于提案提交与用户答题也要使用稳定 ID；恢复时先对账，而不是根据最后一段对话猜测是否已经完成。Pi 的提交去重不等于外部工具副作用恰好执行一次。

### 6.2 工作稿必须只有一个权威来源

推荐由 Rust 工作稿存储持有正式的 AI 工作稿版本，Pi 保存其引用、版本与运行状态。首轮只做短任务时可以先保持会话内工具状态，但那只能验证调用链，不能声称实现了跨崩溃恢复。

不建议让 Pi Documents 和旧 Board 同时各自成为工作稿真相。也不能每个模型回合把整个旧 Board 来回序列化，形成新的耦合与复制成本。

### 6.3 人工决策需要应用自己的协议

工具调用 hook 可以阻止调用，但这不自动等于现有的多选、清单修订、证据取舍与要素建议卡。建议将决策作为有 ID 的持久化待办：保存问题 → UI 展示 → 用户回答 → 校验 → 去重恢复。

首轮可让提问结束本轮、回答后提交下一轮，先跑通完整用户体验；若要承诺真正的持久化挂起，需要再用 Durable task/document 设计恢复状态，不应保留一个跨重启就丢失的内存 Promise。

### 6.4 生命周期和旧会话

Pi 存储由一个 host 独占。项目支持多窗口，不能只依赖现有的窗口转交机制：还需明确一个后台 host、多窗口客户端，或严格隔离各窗口存储与会话所有权。

建议试点用独立 `pi-agent.sqlite`，保持业务 SQLite 不动。旧会话与旧检查点仍交旧引擎读取，新建试点会话才用 Pi。稿件复制、删除、同步与历史清理需定义 Pi 数据的对应行为，不能默认独立库会自动随稿件流转。

恢复时读取当前正文与要素；正文版本发生变化时使旧提案过期，不能把旧任务快照静默覆盖回来。

### 6.5 上游升级与离线分发

v1.4.0 已包含破坏性 API 变更，并把 SQLite 升到 schema 2；迁移后旧版 1.3.0 无法打开。必须锁定依赖、升级前备份，按运行时和存储一起回退。[固定版本变更记录](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/CHANGELOG.md)

Node 22 的官方平台表涵盖 Linux ARM64 / glibc 2.28，与项目发布目标有对齐基础，但仍须检查实际分发的 Node、依赖及其动态库，并在干净 Ubuntu 20.04 ARM64 / 目标麒麟机器启动整条链。不能仅凭 Rust 主程序现有检查认定兼容。[Node 构建与平台要求](https://github.com/nodejs/node/blob/v22.x/BUILDING.md)

安装包要包含运行时、依赖、技能资源与许可证；运行时不走 npm 下载。实际安装包增量、内存和启动耗时尚未测量。模型目录更新、遥测适配与联网行为也要明确配置，以断网试运行验证只访问用户配置的模型/数据端点。

## 七、模型兼容性与收益边界

Pi AI 文档提供本地 Ollama、自定义 OpenAI 兼容 provider 和兼容字段配置。这说明现有本地/内网模型有接入路径，不代表所有端点原样可用。[模型接入文档](https://github.com/earendil-works/pi/blob/v1.4.0/packages/ai/README.md)

项目已有拒收 tools 后的文本兜底、可选参数降级、角色与备用模型行为。这些都要逐项比对：模型 ID 与窗口、thinking、SSE 结束、空 tool 结果、参数 schema、取消、限流重试和备用切换。对不稳定支持 function calling 的小模型，Pi 不能凭框架消除能力短板。

| 预期收益 | 判断 |
| --- | --- |
| 少维护模型—工具循环、对话与恢复底座 | 较可信，是主要选型理由 |
| 长任务中断后更细粒度续跑 | 有潜力，但取决于工具幂等和状态桥接 |
| 技能灵活组合、自然追问 | 有潜力，需要改写流程式技能并验证 |
| 公文质量、局部修改准确性 | 尚无对照证据 |
| RAG 检索准确率与速度 | 复用现有检索时不会因换内核自然提高 |
| 完全不再维护智能体相关代码 | 不成立，仍需维护 host、桥接和领域契约 |

为了真正节省维护，建议新内核上线稳定后逐步退出重复的通用循环与恢复实现；不长期保留两套覆盖相同场景的完整运行时。

## 八、最小试点与验收

推荐首轮只覆盖两个场景：**根据材料起草普通公文**、**限定选区修改且保护事实**。保留旧入口和旧会话，转换少量技能；复杂分阶段写作、人机比选、多智能体和 Code Mode 不作为首轮前提。

| 顺序 | 交付与停止条件 |
| --- | --- |
| 1. 运行验证 | 固定 v1.4.0 与 Node，验证本机/内网模型、Windows 及 Linux ARM64 目标能启动 |
| 2. 领域闭环 | 接通受限技能读取、正文只读、知识库、工作稿、检查和提案；通过现有人工接受入口落地 |
| 3. 决策与恢复 | 验证答题去重、写工具回执、杀进程恢复、正文变化导致提案过期 |
| 4. 效果比较 | 同模型、同材料、同检索配置，对比旧流程与 Pi；再决定是否迁移默认入口 |

建议一次性建立约 20 个真实样例，覆盖起草、局部修改、跨段修改、追问、知识库引用及中断。每例记录：是否完成、人工返工量、事实错误、Markdown 合规、无关改动、耗时、模型调用和 token。生成存在波动，关键样例重复运行并盲评。

单独做故障用例：模型流中断、Rust 已写入但回执未送达、Pi 收到结果但未提交、等待答题时退出、重复提交、运行时升级、磁盘写失败、多窗口抢占。必须验证不会双重插入、丢人工修改或绕过要素与闸门。

这是一项迁移决策所需的有限验证，用户本次调研请求足以讨论其必要性；并不自动更改旧设计中“不建设长期通用评测平台”的决定。

本次未运行上述验证，未估算无依据的收益百分比或工期。通过后再给实施计划；若模型工具兼容、离线打包或写作效果没有过关，可以停止，不影响旧功能。

## 九、需要复议的既有决定

`docs/ai-agent-workbench.md` D5 与 `docs/agent-kernel-hardening.md` 明确采用自研内核并限制外部框架、通用代码执行等。本次正是在用户要求下重新评估这项取舍，旧决定不是不能调研的理由；但正式实施时要更新决定记录，写明替换边界与保留的三条红线。

最终建议：**用 Pi Durable 承担可复用的运行基础设施，让公文助手集中维护公文能力。先验证两个完整用户场景，再按收益迁移；不一次替换整套 AI 工作台，也不把 Pi 当成写作效果的保证。**
