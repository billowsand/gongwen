# 审校自动更正与人工确认清单（2026-11-22）

> 目的：先把「哪些能自动改、哪些必须人看、自动改完怎么让人知道」拆清楚，暂不改代码。
> 范围：起草页「审校」链路——校对词表 `src/proofread.rs`、文档规则
> `src/proofread_rules.rs`、修订总线 `src/revision.rs` 与审校抽屉
> `src/draft_page/revise.rs`。导入清洗与要素校验只在相关处单列，不混入统计。
> 标点的现状、缺口与代码改动另见 [标点处理现状与改造建议](proofread-punctuation-design.md)。

## 一、结论先说

1. **现在不是「不能自动改」，而是「能改的没有自动通道」。** 词表已经把
   「必错 + 非正则 + 建议写法是纯词」标成可一键替换，但每一处都要用户点一次
   「采纳」；没有「确定项自动落地、疑似项留给人」的分流。
2. 当前 155 条词表里，**73 条**满足 `Entry::is_replaceable()`，可以直接替换；
   另有 **2 条文档格式规则**（公文引用文号、发文字号年份括号）已经带确定改法。
   这 **75 项**是自动更正的候选池；去掉 7 条需先补边界的、再扣掉 6 条异形词，
   第一期先开 **62 条**。
3. 但 73 条不能全部无脑全局替换：**7 条**的「错误写法」会出现在正常词或人名里
   （会报／年会报告、关健／人名、规化／正规化、按排／按排班、近一步／接近一步、
   的的／的的确确、延用／延长使用）。这 7 条要么加前后文边界，要么只做人工确认。
4. 真正需要人判断的，是 **21 条人工改写项**（6 条句型正则 + 3 条并列改法 +
   12 条文档规则），外加 **79 条只提示项**（40 条疑似 + 33 条提示 + 6 条文档提示）。
5. 推荐四档，而不是「自动 / 不自动」两档：
   - **A 自动更正**：确定、可逆、不需要判断，预览/导出自动应用，源码在显式保存时写回；
   - **B 人工确认后一键改**：改法确定，但要看一眼（如段末补句号）；
   - **C 人工改写**：程序给不出唯一替换，必须由人改；
   - **D 只提示**：风格、结构、事实、版式，改了反而可能错。
6. 自动更正要分三处落地：**预览与导出改显示/输出，源码只在显式保存时写回**。
   预览里直接改字、导出时顺手改源文，都会让「屏幕上的、存下来的、导出去的」
   三份互相打架；保存键是用户明确的落点，适合把更正写进源码。
7. 自动更正**不能静默**：每次批量更正后，状态栏报数、审校抽屉留「本次已自动更正」
   清单、支持整批撤销；保存时如果有更正，报数并给一次撤销。
8. 标点先做：半角→全角、引号、列表标记 `1。`→`1.` 这类「一进一出」的字符替换，
   预览/导出/保存都能直接做；空格、重复标点、省略号要改字符数，预览需要偏移映射，
   可以放到第二期。详见标点专篇。

**如果只做一件事**：先做「预览和导出自动规范 62 条确定项 + 标点 1:1；源码只在
`Ctrl+S` 时一次写回并可撤销」。不做逐键、不在写的过程中改源码、不碰 A2 的 7 条边界项。

## 二、现状：一条提示现在怎么走

### 2.1 词表

- `Lexicon::check(text)` 扫正文，产出 `ProofNote { entry_id, group, level, message,
  span, replacement }`。
- `Level` 分三档：`MustFix`（必错）、`Suspect`（疑似）、`Hint`（提示）。
  其中 `Suspect` 的注释已经写明「需要人判断的近义混淆，只提示，绝不自动改」。
- `Entry::is_replaceable()` 的判据是：**必错 + 非正则 + 建议写法非空 + 不含
  「」／（(…**。满足才给 `replacement`，界面才显示「采纳」按钮。
- 这带来一个口径混用：`MustFix` 本意是「确定的错误」，但代码又拿它当
  「可一键替换」。结果是 82 条必错里只有 73 条可替换，另外 9 条（句型正则与
  并列改法）虽然必错，却只能人工改写。自动更正要把「严重度」和「处理方式」分开。

### 2.2 修订总线

- `revalidate()` 把词表命中与文档规则命中一并送进 `RevisionSet`，转成
  `Revision { span, anchor, after, source, group, severity, confidence, state }`。
- 只有 `after` 有值的条目才能「采纳」；`after` 为空时卡片显示「需人工改写」。
- 当前按钮：
  - 单条「采纳」；
  - 「采纳全部必错」——逐条走 `accept_revision`，逐条过闸门；
  - 「忽略」「不再提示」；
  - 「撤销上一处」。
- 落地有两道闸门：
  1. `RevisionSet::apply` 采纳前按锚点重新定位，锚不上就拒绝；
  2. `verify_no_new_mustfix` 改完复扫，出现新的必错就整条回滚。
  另外 `document_reference::ensure_preserved` 保证公文引用不被改动。
- 这三道保护是现成的，自动更正可以直接复用，不需要另造一套。

### 2.3 触发时机

`revalidate()` 不是每次击键都跑，而是在打开/切换稿件、粘贴、导入、AI 写入、
接受修订、恢复版本、导出结束等落点触发。这个节奏正好适合「预览/导出自动、保存时写回」，
而不是「逐键自动改」。

### 2.4 审校抽屉

- 顶部计数是「待确认修订 + 要素/版式提示」之和。
- 修订建议按正文位置排，卡片显示来源（词表/规则/模型）、级别、改法、理由。
- 「本次已采纳 N」只有计数和「撤销上一处」，没有逐条清单。
- 没有「已自动更正」分区，也没有「哪些是程序改的、哪些是我改的」区分。

## 三、分档口径

| 档位 | 判据 | 程序行为 | 用户看到什么 |
| --- | --- | --- | --- |
| **A 自动更正** | 改法唯一、上下文足够确定、可逆 | 预览/导出自动应用；显式保存时写回源码 | 状态栏报数 + 抽屉「自动更正」清单 + 可撤销 |
| **B 一键确认** | 改法确定，但可能因文体/位置不适用 | 不自动改，给「采纳」按钮 | 卡片上「采纳」，可定位、可忽略 |
| **C 人工改写** | 程序只知道「这里有问题」，给不出唯一改法 | 只给位置与理由 | 卡片上「需人工改写」，点「定位」跳过去 |
| **D 只提示** | 风格、结构、事实、版式，改了反而可能错 | 只列提示，不提供改法 | 抽屉里的提示列表，可整组关闭 |

> 注：A 不是「永不误报」，而是「误报代价低、可一眼撤销」。所以 A 也必须
> 有保护区和撤销，不能变成静默改写。

新增一条规则时，用四个问题决定它进哪一档：

1. 程序有没有**唯一**的替换文本？没有 → C 或 D。
2. 替换是否只依赖命中处前后的字面，**不依赖语义、事实、行文关系**？不是 → B/C。
3. 错误写法会不会是正常词、人名、单位名、固定搭配的一部分？会 → A2 或 B。
4. 改错了，用户能不能在上百字里一眼发现并撤销？不能 → B，不要自动。

四个都过，才进 A1/A3；有一条拿不准，就低一档。

这两条已经产出 `replacement`，且替换完全由原文决定，适合自动更正：

| 规则 | 内容 | 级别 | 保护 |

### 4.5 A 类的共同前提

- 只改正文，不改标题里的引用名称、不改文号代字；
- 跳过直接引语、公文引用、代码围栏/行内代码、图片与链接地址；
- 跳过词库里已有的人名、单位名；
- 同一位置多条命中时取最长写法，只改一次；
- 批量改完复扫，出现新的必错就回滚这一条；
- 整批记成一次可撤销的编辑，而不是几十次碎撤销。

## 八、自动更正放在哪里：三处落地

| 落点 | 做什么 | 写不写源码 | 备注 |
| --- | --- | --- | --- |
| **预览（版式 / 实时 PDF）** | 用更正后的副本排版 | 不写 | 用户先看到成品样子；源码仍是自己敲的字 |
| **导出（PDF / Word / Markdown / Typst 包）** | 用更正后的副本生成 | 不写 | 所有格式共用同一份更正结果，不能各算一遍 |
| **显式保存**（Ctrl+S、标题栏、保存并关闭、提交版本） | 把更正写回源码 | 写 | 一次可撤销；状态栏报数 |
| 自动保存 / 切标签 / 首次输入 / 复制全文 | 原样保存或复制 | 不写 | 不在写的过程中改字 |

### 为什么预览要自动改显示

- 用户要看的是「排出来是什么样」，不是「源码里现在是什么样」。半角逗号、直引号
  在版式里本来就不该出现，预览先规范，才能判断版式。
- 源码不动，用户不会在打字时看到字自己变；保存时再一次性写回，心理模型清楚。
- 代价是预览的点击定位、选区、查找都按源码偏移算。**1:1 的字符替换**（半角→全角、
  引号）可以在 `inline_atoms` 里做，源码范围不变；`1。`→`1.` 属于列表结构，留在
  输入层和保存 pass，不在 `inline_atoms` 里改；**改字符数的替换**（空格、重复标点、
  省略号）需要给预览加一张源码偏移映射表，放到第二期。

### 为什么不在写的过程中改源码

- 光标会跳：替换位置在光标之前时，输入焦点和撤销栈都会乱。
- 用户会迷茫：明明敲的是 `。`，屏幕上变成 `.`；明明没按保存，源码却变了。
- 现有失焦/自动保存/复制全文的改动还绕过了撤销栈，撤不回来。
- 所以只在显式保存时改源码，而且整批算一次编辑，`Ctrl+Z` 一次退回。

### 提醒长什么样（建议文案）

- **预览状态栏（有更正时）**：
  「预览已按标点规范显示 3 处；按 Ctrl+S 写回源码」
- **显式保存后**：
  「已保存；规范标点 5 处（半角 3、引号 1、重复 1）· 撤销」
- **导出完成后**：
  「已导出；成品内自动规范 4 处（不影响源码）· 查看清单」
- **正文内（第三期再做）**：
  保存写回后，刚改过的几个字短暂淡绿底纹，悬停显示「已自动更正：布署 → 部署」；
  下一次编辑或撤销后消失。不要长期留着，否则正文像打了补丁。

## 九、推荐落地顺序

### 第一期：A1 + A3 + A4 + 标点 1:1，低风险自动更正

- 新建一个纯文本的 `autofix` / `punctuation` 通道：输入
  `(markdown, lexicon, rules, protections)`，输出 `(corrected, Vec<AppliedChange>)`；
  不碰 egui，能单测；标点部分见[标点专篇](proofread-punctuation-design.md)。
- 先处理 A1 的 54 条硬错、A3、A4 和标点 1:1（半角→全角、引号、`1。`→`1.`）；
  A2 和 6 条异形词暂不自动。
- **预览**：只改显示，不改源码。选「一步到位」就同时做源码偏移映射，等长/不等长
  替换都能显示；选「先小步」则预览只显示等长替换，不等长的等保存/导出。这个取舍
  见标点专篇 5.4。
- **导出 / 实时 PDF**：用更正后的副本生成，所有格式共用一份；源码不动。
- **显式保存**：把更正写回源码，整批一次撤销；自动保存、切标签、首次输入、
  复制全文都不改源码。
- 每批结果：
  - 预览/导出只在状态栏报「成品内自动规范 N 处（不影响源码）」；
  - 保存写回时在 `RevisionSet` 记 `AppliedRevision`（带 `auto: true`），
    状态栏报「已保存；规范 N 处」；
  - 抽屉顶部新增「自动更正 N」，可看清单、可整批撤销（只对已写回源码的那批）。
- 保护：引文、公文引用、代码、图片/链接、词库人名单位、A2 边界。
- 设置：全局「自动更正确定项」默认开；「预览显示更正」默认开。

### 第二期：B 与 A2

- 把 `RULE-SENTENCE-END` 留在 B，优化「采纳」后的定位与撤销。
- A2 的 7 条逐条补边界条件，先在词表页做「试规则」样本验证，再放开自动；
  `TYP-028 关健`、`TYP-068 延用` 建议长期留在人工确认。
- 词表条目增加「处理方式」：自动 / 确认 / 仅提示，与「级别」分开。
  内置默认按本清单给，用户可逐条改；自定义条目默认「确认」，用户显式勾选才自动。
- 埋点增加 `auto_fixed` / `auto_undone`，用真实撤销率决定某条该不该继续自动。

### 第三期：提示体验与格式清洗

- 正文里对刚自动更正的位置做短暂（如 10 秒）淡色底纹/下划线，悬停显示
  「已自动更正：布署 → 部署」；下一次编辑或撤销后消失。
- 审校徽章拆成「待确认 5」与「已自动更正 3」，不再混成一个总数。
- 「清洗」分区里确定性的文本卫生（汉字间空格、全角数字、零宽字符、中文语境
  半角标点）进入预览/导出/保存的自动 pass；结构性清洗（编号→标题、列表、
  表格补分隔行）仍然只走手动命令，不能静默改。
- 需要审计时，导出旁路一份「更正记录.txt」或写进版本说明；不放进正式 PDF。

## 十、自动更正的硬保护

1. **保护区**：直接引语（“…”/「…」）、公文引用（名称与文号）、代码围栏与行内
   代码、图片/链接地址、Markdown 标记、词库里的人名与单位名。落在保护区里的
   命中，一律不自动改。
2. **词边界**：A2 的 7 条先加前后文条件；其余条目用「最长匹配 + 前后汉字检查」
   兜底，拿不准就跳过，留给人工。
3. **一次一处**：同一 span 多条命中取最长写法；同长度的按级别、编号定序，只改一次。
4. **级联控制**：批量改完复扫；出现新的必错就回滚该条；最多 2～3 轮，不收敛就停。
5. **整批可撤销**：一批替换合成一次编辑，撤销一次回到改前；逐条撤销从
   `AppliedRevision` 走，正文被用户改过就拒绝，不覆盖用户的手改。
6. **引用保护**：复用 `document_reference::ensure_preserved`；公文引用的名称、
   文号一个字都不能动。
7. **保存前留痕**：写回源码前先落一次可撤销编辑；需要版本历史时按现有版本规则提交，
   不另造一种「自动更正版本」。
8. **失败即不改**：任何一步算不出确定结果，就退回「待确认」，不猜。

### 与三条红线的关系

自动更正会新增一个「程序替用户改写正文」的入口，必须按 `AGENTS.md` 红线 1 的口径
处理，不能做成后台线程偷偷改：

- **预览与导出不改源码**，只排/只生成更正后的副本，所以不触红线 1；
- **列表末尾句号/分号是整篇判断**，只在显式保存做；预览/导出在保存前不重判，
  保存后自然随源文一致；
- **只有显式保存**才在界面线程把更正写进 `generated_markdown`，沿用
  `replace_with_undo` / 版本机制；自动保存、失焦、切标签、复制全文都不写；
- 写回的那一批要有用户动作作为授权（`Ctrl+S`、标题栏保存、保存并关闭、提交版本），
  不能开后台任务扫到就改；
- 每批记录改前/改后文本与来源（`auto: true` + 规则编号），支持整批撤销；
- 自动更正不是 AI 交付通道，AI 工具不能借它绕过提案/采纳；Pi 写入后如果需要
  再跑一遍，`PiWrite.before/after` 必须记最终实际文本，撤销仍然只撤销这一整次写入。

## 十一、需要拍板的问题

1. **预览做到哪一步**：一步到位做源码偏移映射（词条不等长替换 + 标点 N:M 都能在
   预览里看到），还是先做等长替换 + 标点 1:1？前者体验完整，后者改动小但预览会
   「有的改了、有的没改」。我倾向一步到位。
2. **源码只在显式保存时改**：自动保存、切标签、首次输入、失焦、复制全文都不改——
   是否同意？
3. **列表末尾标点的判断范围**：明确只在显式保存时整篇判断；剩下的是按每个列表组
   分别判，还是全篇统一一种风格。我倾向按组判（各章列表可以不同），但要修掉
   `……`/`——` 被当普通末尾标点吃掉的 bug。
4. **标题标点**：`、` 必须允许；内部 `，`/`；`/`：` 只提示删除，还是自动删？
   我建议先提示，等规则在真实稿上跑一轮。
5. **保护范围**：直接引语、路径/文件名、裸域名、邮箱是否一律不自动改？
   我建议一律不自动改，最多提示。
6. **特殊括号接受范围**：发文字号除 `[]`、`【】`、`（）`、`{}`、`〈〉` 外，
   要不要连 `「」`、`『』`、`《》` 也认？我建议前五类，`《》` 不碰。
