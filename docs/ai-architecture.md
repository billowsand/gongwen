# 公文 AI 能力架构与演进路线

> 面向「严谨、可确认、小步修饰」的公文 AI 设计。本文定契约与顺序，不描述具体
> 界面像素。读者：继续开发本仓库 AI 功能的人。

---

## 一、三条不可逾越的红线

公文场景对 AI 的要求与通用写作助手根本不同：**错一个字、改一个日期，是行政事故**。
所以先立三条红线，后面所有设计都从它们推导：

1. **AI 永远不直接写入正文。** 模型的产物只能是「修订建议」，落地必须经过用户
   动作。`generated_markdown` 只允许被两种操作改写：用户键盘输入，以及用户点击
   采纳某条建议。
2. **AI 永远不碰公文要素。** 单位、人员、文号、密级、成文日期由界面与标准词库
   维护（现状即如此，README 已写明）。模型只处理正文文字，不得回写 `DraftInput`。
3. **任何落地前都要过确定性闸门。** 事实比对（`ai_guard`）、要素校验
   （`validator`）、词表与文档规则复扫（`proofread` / `proofread_rules`）。
   闸门不过就丢弃，宁可漏报，不可误改。

第 3 条的推论很重要：**确定性规则是 AI 的裁判，不是 AI 的竞争者**。词表越厚、
规则越准，能放心交给模型的空间就越大。

## 二、核心契约：修订建议总线（Revision）

### 2.1 为什么这是第一步

当前 AI 的落地形态是「整篇提案，全接受或全放弃」（`app/ai_workbench.rs`
`ai_proposal_window`）。这条路走不远：

- 用户要的是「这句话的『截止』该改成『截至』」，不是「这是一份新稿子，你看要不要」；
- 整篇替换让 `ai_guard` 只能做粗粒度事实比对，改动来源无法追溯；
- 每加一个小功能就要新做一套界面，五个小功能之后无法收敛。

**先把所有 AI 能力收敛到同一种产物上，后面每个功能都只是一个「建议生产者」，
界面一次做完不再动。** 这也是「先小流程、后智能体」能成立的前提——否则最后拟合
智能体时要把前面全部推倒。

### 2.2 数据结构

已实现于 `src/revision.rs`：

```rust
/// 一条待确认的修订建议。词表、文档规则、小模型、大模型、智能体统一产出它。
pub struct Revision {
    pub id: RevisionId,
    /// 正文字节范围。永远由程序计算，绝不采信模型给的偏移量。
    pub span: Range<usize>,
    /// 抗漂移锚：原文 + 前后各 12 字上下文。正文被编辑后据此重新定位。
    pub anchor: Anchor,
    /// None 表示只提示、不给改法（语病、结构问题常见）。
    pub after: Option<String>,
    /// 一句话理由。没有理由的建议不予展示——用户无法判断就等于无法确认。
    pub reason: String,
    pub source: RevisionSource,
    /// 分类标签，直接沿用词表与规则里的分组名（错别字、称谓规范……）。
    pub group: String,
    pub severity: Level,          // 复用 proofread::Level：必错 / 疑似 / 提示
    pub confidence: f32,          // 规则恒为 1.0；模型建议按闸门结果打折
    pub state: RevisionState,     // Pending / Ignored / Stale
}

pub enum RevisionSource {
    Lexicon { entry_id: String },   // 校对词表
    DocRule { rule_id: String },    // 文档级规则
    Model { task: String },         // 模型检查器，task 为检查类型
}
```

两处与初稿的偏差，都是照着现有数据形态改的：

- **分类用 `group: String`，不另立枚举。** 词表和文档规则本来就带分组名，且用户
  自建条目可以写任意分组；套一层枚举只会多一次有损映射。
- **状态只有三档。** 初稿里的「拒绝」和「忽略」在界面上是同一个按钮、同一种
  后果，分开只会让用户猜它们有什么区别；「已采纳」则直接离开待确认列表，进入
  撤销栈（`RevisionSet::applied`），不占用状态位。

### 2.3 锚点漂移

`span` 是字节偏移，用户改一个字后全部失效。**没有 anchor 的逐条修订不可用**——
用户一边看建议一边改稿是常态。定位策略：

1. 用 `span` 原位校验 `before` 是否仍匹配，命中即用；
2. 否则全篇搜 `before`：只有一处就认它；多处则按前后各 12 字的上下文打分
   （各吻合记 1 分），取唯一最高分的那处；
3. 最高分并列且不满分 → 放弃；并列且满分（正文里真有一模一样的重复段落）
   → 取离原位最近的一处；
4. 都不成立 → `state = Stale`，界面置灰并标「原文已改动」，不可采纳也不可定位。

第 3 条是分水岭：**并列即视为无法判定**。猜错的代价是把正文改坏，而且改坏的
地方未必在用户视野里。

### 2.4 采纳即自检（闭环挡幻觉）

每采纳一条建议，立即对被改动段落重跑词表 + 文档规则：

- 若引入了**新的**必错命中或规则报错 → 自动回滚，提示「该建议引入新问题，已撤销」；
- 若通过 → 落地，记入 undo 栈，状态栏累计「已采纳 N 处」。

这一步让小模型的幻觉在闭环里被确定性规则自动挡掉，是敢用小模型的底气。

### 2.5 忽略与记忆

`ProofNote.entry_id` 的注释已经预留了「忽略记录按它存」，但未实现。补上两档：

- **本篇忽略**：随稿件存，换稿即失效；
- **永久忽略**：按 `entry_id`（规则类）或 `before` 文本（模型类）存进配置。

没有忽略机制，误报一次用户就会把整个检查关掉——这比没有这个检查更糟
（`proofread_rules.rs` 开头已经写明这个取舍原则，此处一致）。

## 三、确认的分级

「每个功能都要用户确认」是对的，但**如果每个错别字都弹模态框，人会关掉整个功能**。
确认成本要与风险匹配，分三档：

| 档位 | 形态 | 适用 | 撤销 |
|---|---|---|---|
| 一键确认 | 建议条上点「采纳」 | 错别字、标点、数字、称谓、单句改写 | Ctrl+Z |
| 批量确认 | 「采纳全部必错（12 处）」+ 采纳后逐条可撤 | 同类高置信建议 | 整批撤销 |
| 闸门确认 | 模态 + 勾选声明 | 关键事实变化、整篇替换、正式导出 | 不适用 |

现有的 `fact_changes_confirmed` 勾选就是第三档，保留。严谨性的保证不在弹窗次数，
而在第一节的三条红线。

## 四、大小模型分工

### 4.1 模型角色化

当前 `LmStudioConfig` 是单个对话模型实例（`models.rs`），没有安放「小模型」的位置。
改成按角色配置，各自独立地址与模型名（与 embedding / rerank 已有的独立配置同构）：

| 角色 | 典型模型 | 采样 | 用途 |
|---|---|---|---|
| `draft` | 14B~32B | temp 0.25 | 起草、仿写、篇章级改写 |
| `revise` | Qwen3 4B/8B | temp 0.0 | 单句判定与受限改写 |
| `extract` | Qwen3 4B/8B | temp 0.0 | 材料抽事实、字段抽取 |
| `embed` / `rerank` | 现状 | — | 知识库 |

未配置 `revise` 时回落到 `draft`，不阻断功能。

### 4.2 路由表

| 任务 | 承担者 | 输入粒度 | 输出 |
|---|---|---|---|
| 错别字、固定搭配 | 词表（无模型） | 全文扫描 | 替换文本 |
| 标题规范、文种越界、序号层级、附件一致 | 文档规则（无模型） | 全文 | 提示 + 定位 |
| 标点、数字、量词用法 | 规则为主，小模型兜底 | 句 | 改后句 |
| 语病、搭配不当 | 小模型判定 + 改写 | 句 | `OK` 或改后句 |
| 称谓与公文用语得体 | 小模型（注入词库上下文） | 句 / 段 | 改后句 |
| 去套话、精简 | 小模型 | 段 | 改后段 |
| 篇章结构诊断 | 大模型 | 全文大纲 | **只出清单，不改正文** |
| 起草初稿 / 仿写 | 大模型 | 事实单 + 要素 | 全文（走现有提案窗 + 事实闸门）|
| 材料 → 事实单 | 小模型抽取 + 规则复核 | 材料分段 | 字段列表，逐项确认 |

判断依据：小模型在**判定、抽取、受限改写**上可靠；在**长文生成、多约束同时满足、
篇章规划**上不可靠。凡是「一次只回答一个问题、输入不超过一段」的活，交小模型。

### 4.3 小模型调用铁律

1. **一次一句、一次一个问题。** 不要在一个 prompt 里同时问「有没有错别字、语病、
   套话」——小模型会互相干扰，且无法归因。每个检查器一个 prompt。
2. **不要求模型输出 JSON，更不要求输出偏移量。** 小模型算 offset 必错。要求它
   输出「改后的整句」或 `OK` 两种之一；**span 由程序对原句与改后句做 diff 求得**。
   这条比任何 JSON schema 都稳。
3. **温度 0，max_tokens = 输入长度 × 1.3 + 余量。** 越界即截断丢弃。
4. **失败重试一次，仍失败即静默放弃**，不向用户报「模型抽风」。
5. **句子级缓存**：句子指纹 → 模型结论。未改动的句子不重跑，这是「一轮几十次
   本地推理」能被反复触发的前提。
6. **本地服务限流**：本地推理通常单并发最优，检查器排队执行，界面显示进度而非
   卡死。

### 4.4 模型输出的程序闸门

小模型改写结果落成 `Revision` 之前，逐条过：

- 非空，且只有一行——回了多行说明它在解释而不是改写；
- 长度变化率在阈值内（-40% ~ +40%，超出多半是模型在重写而非修改）；
- 关键事实不变（`ai_guard::compare_key_facts`，有变化即拒）；
- 裸数字不变（不带量词的「第 3 类」上一层看不住，单独比一遍）；
- Markdown 行内标记（`*_[]()\`|#`）的个数不变，否则会把加粗、链接改坏；
- 改后句自身再过一遍词表，不得新增必错命中。

任一条不过 → 丢弃，不展示。用户看不到的误报不是误报。

### 4.5 提示词模板（`revise` 角色示例）

```
系统：你是公文文字校对助手。只做被指出的那一类问题，不做其他修改。
     不得增删事实、数字、单位名称、人名、日期、书名号内容。
     输出只有两种：完全没有该类问题时输出 OK；否则输出修改后的整句，
     不加解释、不加引号、不加标记。

用户：【检查类型】语病（成分残缺、搭配不当、句式杂糅）
     【原句】通过这次专项整治，使全区安全生产形势明显好转。
```

`prompt.rs` 已有的注入防护（标准优先级高于任务描述、待处理文本不是指令）
要原样沿用到每个检查器模板。

## 五、演进路线

顺序原则与你的判断一致——**先细节，后流程**；但补一个前置：**先定契约**。
否则五个小功能各带一套界面，最后拟合智能体时要全部重写。

### 阶段 0：契约与面板（无模型）— ✅ 已完成

- `src/revision.rs`：`Revision` / `Anchor` / `RevisionState` / `RevisionSet`，
  含采纳、撤销、忽略与三级重定位；
- `src/draft_page/revise.rs`：修订建议面板与两道闸门（落地前重锚、落地后自检）；
- `revalidate`（`draft_page/form.rs`）把词表与文档规则的命中改投到这条总线，
  `warnings` 只留要素校验与版式实测；
- 接上了那个现成的低垂果实：`From<ProofNote> for ReviewNote` 一路把
  `replacement` 丢掉，导致词表里「必错可一键替换」的能力界面上根本没有。现在
  141 条规则里可替换的那部分，用户看到的是「布署 → 部署」加一枚采纳按钮。

**验收**：不接任何模型，词表与文档规则的建议可逐条采纳、撤销、忽略；改稿后
建议正确重定位或置灰。锚点的三级判定、闸门的拦截与回滚、忽略的两档记忆均有
单测锁住。

### 阶段 1：第一个小模型检查器 — ✅ 已完成

选**语病与表达**先做——词表覆盖不了（错别字能穷举，句式杂糅不能），价值最高，
且属于「疑似」档，误报只是多一条可忽略的建议，不会误改正文。

- `models.rs` `ReviseModelConfig`：复核模型独立配置，地址与密钥留空则沿用起草
  模型；温度固定 0，不给用户调——复核要的是可复现，不是发挥；
- `lmstudio::generate_retrying`：失败重试一次，不做退避；
- `src/revise_model.rs`：句子切分、最小改动区间、闸门、提示词、回复清洗，
  全是纯函数可单测，只有 `review` 碰网络；
- `revision::RevisionSet::replace_model`：一轮复核整批替换模型来源的建议；
- 句子指纹缓存挂在 `DraftSession::revise_cache`，改了别处的句子不重问。

模型建议一律记「疑似」档，界面上另标「需人工判断」。**不给「必错」是刻意的**：
必错会进「采纳全部必错」的批量口子，那是不该交给模型的权限。

**验收**：闸门的六条拦截（空句/多行、长度、关键事实、裸数字、行内标记、新增
必错命中）各有单测；模型服务没配或连不上时入口置灰并说明原因，不报错弹窗。

关于「`revalidate` 防抖 + 只跑脏段」：核对后发现前提不成立——`revalidate` 只在
显式动作时跑（重新校验、生成完成、导入、切版本），不是每帧或每次击键，纯规则
扫描在这个频率下没有优化价值。真正需要缓存的是模型复核，已按句子指纹做在
`revise_cache` 里。等将来真做成边打字边校对，再回来补防抖。

### 阶段 2：铺开检查器

称谓规范、标点数字、去套话、版式复核，逐个加。每个都是独立的
`Checker` 实现，产出 `Revision`，不碰界面。

**验收**：新增一个检查器的改动量 ≈ 一个 prompt 模板 + 一段闸门配置。

### 阶段 3：起草侧改造 — ✅ 已完成

大模型起草改成**大纲优先**：先出骨架（用户增删改序）→ 逐节生成 → 合稿。
事实单确认前置不变。核心在 `src/outline.rs` 与 `src/app/outline_ui.rs`。

三条实现上的取舍：

- **让模型用 `#`/`##` 输出而不是 JSON。** 这是它最熟的格式，出错率最低，而解析
  对程序毫无难度。为几十字的骨架去要 JSON 只会平白增加跑偏机会。
- **逐节提示词要给模型看完整大纲**并标出当前这节。不给全貌它会把邻节内容也写
  进来，合稿之后满篇重复——这是分节生成最容易踩的坑。
- **「生成剩余 N 节」一次只发起一节。** 一口气排队全跑，等于把「随时能停下来改
  大纲」这个好处又还回去了。

已知限制：合稿只在正文为空时写入，已有正文时不覆盖。

### 阶段 4：SOP 编排层（智能体）— ✅ 已完成

**不是让大模型自由调工具。** 公文 SOP 落成一台确定性状态机（`src/sop.rs`），
七步各有可计算的通过判据：

| 步 | 通过判据 |
|---|---|
| 拟稿 | 正文非空 |
| 要素齐备 | `validator::mustfix_issues` 为空（只报状态，不挡导出编译） |
| 文字校对 | 待确认的必错级建议为 0（疑似项只报数，不卡流程）|
| 表达复核 | 复核跑过且模型建议均已处理；未配置模型时不适用 |
| 存疑清零 | 正文无「【待核实…】」占位 |
| 版式验证 | 导出编译成功过，且最近一次没失败 |
| 入库送审 | 已存库、已固化版本、且之后没再改动 |

两处与初稿的偏差，都值得写下来：

**一、「让大模型生成诊断摘要」这一半取消了。** 上面七条全都可计算——用模型去
生成一份程序算得出的结论，只会更慢、更不准，而且它根本看不到 `validator` 的
输出。**能算的就不要猜。** 结果是模型在阶段 4 里一点参与都没有：它只在步内当
检查器（阶段 1–2 的产物），流程本身与它无关。

**二、这是一张状态表，不是向导。** 不强制顺序、不禁用任何操作。真实写公文并不
线性——先润色后填要素是常事，等排版出了问题再回头改正文也是常事。强行排序只会
让工具变难用，而用户真正缺的从来不是流程约束，是**一眼看清还差什么**。

「智能体」因此是可预期、可审计、可复现的：谁在第几步改了哪一句、依据哪条规则、
用户是否确认——全部可回放，这正是公文场景需要而通用 Agent 给不了的东西。

## 七、埋点 — ✅ 已完成（`src/metrics.rs`）

不度量就无法判断某个检查器该留还是该关。公文场景里一个天天误报的规则，用户的
反应不是忽略它，是把整个校对关掉——那比没有这条规则更糟。

**只记用户的动作，不记「出现过多少条」。** 出现数会被每轮重新校验反复累加，
去重成本高，含义还模糊——用户没处理不等于不认可，可能只是没看完。采纳与忽略是
明确的表态，且一条建议只会表态一次。所以：

    采纳率 = 采纳 / (采纳 + 忽略)

三条实现上的取舍：

- **撤销会把 `accepted` 减回去。** 那次采纳最终没有留下，算成「采纳过」只会让
  采纳率虚高，而这个指标存在的意义正是别骗自己。同时单独记一笔 `undone`：
  「点下去才发现不对」比直接忽略更能说明这条规则误导人。
- **样本不足 8 次只报次数，不报比例。** 三次里忽略两次不是证据，显示「33%」
  会让用户误杀一条好规则。
- **闸门拦截单独记，不算表态。** 它衡量的是模型合不合用，与规则本身好不好是
  两件事；混在一起两个信号都读不出来。

判据：表态 ≥ 8 次且采纳率 < 30% 即标记「建议停用」，在校对词表页和设置页
直接提示，而不是等用户自己去翻统计。数据存 `metrics.json`，与配置同目录但
**不进 `config.json`**——埋点每点一次就变，塞进配置会让配置版本历史被这类
噪音淹没。

## 八、语言层：借鉴 gongwen-skill

前面七节管的全是**事实、要素、版式**。「像不像公文」这一层——句长、并列、
标点、力度词、开头收尾、归因分寸——此前一个字都没管。
[gongwen-skill](https://github.com/billowsand/gongwen-skill) 对上百万字真实公文做了
全量统计，把这一层变成了可数的参数；它与本项目正好互补：它覆盖的七种事务性
材料（调研报告、领导讲话、工作意见……）本项目一种都没有，本项目的六种法定公文
它明确不做。所以借的不是文种参数，是**跨文种成立的语感规则**，分三处落地。

### 8.1 起草提示词：`prompt::style_guide`

一段「【行文规范——公文语感】」，起草、仿写、逐节生成共用，会议议程除外。
六条：并列堆叠（附一对句子对照）、标点不做修辞、强制词配额、开头收尾、
归因分寸、不编数据。力度词按行文方向切换：函是平行文用「请贵单位」，呈批件是
上行文用「建议」，通知是下行文用「要」——**用词由权力关系决定，不由礼貌决定**。

两处取舍：

- **摆句子，不讲道理。** 「句长 53 字」模型听不懂，「短句版 / 公文版」一对
  句子它就懂。skill 的 `句子对照库.md` 证明了这一点，这里只带一组，几百 token。
- **占位符不另起体系。** skill 用三类占位（待补 / 示意·待核 / 待核对原文），
  本项目校验、SOP、高亮全靠「【待核实」前缀识别，改体系要动四个模块。折中：
  语义上采纳三类，写法上全部收在「【待核实：…】」里——参考量级写
  「【待核实：示意约××，须核实替换】」。「示意」这一档值得单独要：它给模型一个
  不编造也能把话说圆的合法出口。`the_style_guide_never_breaks_the_placeholder_convention`
  锁住这条。

### 8.2 文档规则：`proofread_rules::check_language_style`

提示词只约束意图，兜不住，所以能数的都用程序复查一遍：

| 规则 | 判据 | 档 |
|---|---|---|
| `RULE-PUNCT-DASH` | 正文破折号 > 1 处 | 提示 |
| `RULE-PUNCT-COLON` | 「是/有/即/包括：」直接接正文（冒号揭晓） | 提示 |
| `RULE-FORCE-QUOTA` | 「必须/严禁」> 5 处，引号内不计 | 提示 |
| `RULE-WORD-JINYIBU` | 「进一步」> 3 次 | 提示 |
| `RULE-OPEN-CLICHE` | 首段前 45 字含「高度重视」 | 提示 |
| `RULE-TONE-PARALLEL` | 函里「要求贵局」式命令 | 疑似 |
| `RULE-TONE-UPWARD` | 请示里「要求市政府」式命令 | 疑似 |

只看正文段落，不看标题、表格、附件——副标题里的破折号是合法的，附件多是
表单。**没有一条进「必错」**：风格偏离不是错误，进了必错就会被「采纳全部必错」
批量处理，那是不该给风格规则的权限。

一处与 skill 的偏离要记下来：**强制词只数「必须」「严禁」，不数「应当」「不得」。**
skill 四个都数，配额 0–2。但那是事务性材料的统计；法定公文里的报送要求、
条例办法用的是法律语体，「应当一并核实」「不得自行推测」是中性表述——
仓库的规范样例函件一篇就有三十多处，照搬配额会天天误报，而误报一次用户就会
关掉整组。加重语气的只有「必须」「严禁」，数这两个才是在数「力度」。

### 8.3 校对词表

「套话虚词」组加了六条模糊主体、模糊时限与空洞程度词（非常、尽快、相关部门……），
随组默认关闭；「公文用语」组加了八条第一人称判断与元评论（我认为、其实是、
说到底、综上所述……），默认开启，全是提示档。

### 8.4 没搬的，以及为什么

- **文种参数表**（字数、句长、层级配比、身份证参数）：七个文种本项目一个没有，
  搬来没处用。等哪天开事务性材料文种族，`check_params.py` 的 `analyze()` 可以
  1:1 移植成纯函数，用 skill 的 22 篇范文当 fixture 对齐——标题层级要改按
  `##`/`###` 数。
- **「读完整篇范文」**：给前沿模型 50k 上下文准备的做法，本地模型装不下；
  真要用范文，按文种整篇挂载给仿写，不要切块进 RAG。
- **并列不足 / 过度的模型改写器**：改写幅度远超复核闸门 ±40% 的长度约束
  （对照里 27 字→47 字），要么单独一套闸门，要么只提示不给改法。留到阶段 2。
