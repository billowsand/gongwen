# 公文 AI 能力架构与演进路线

> 面向「严谨、可确认、小步修饰」的公文 AI 设计。本文定契约与顺序，不描述具体
> 界面像素。读者：继续开发本仓库 AI 功能的人。

---

## 一、三条不可逾越的红线

公文场景对 AI 的要求与通用写作助手根本不同：**错一个字、改一个日期，是行政事故**。
所以先立三条红线，后面所有设计都从它们推导：

1. **AI 永远不直接写入正文。** 模型的产物只能是「修订建议」，落地必须经过用户
   动作。`generated_markdown` 只允许被两种操作改写：用户键盘输入，以及用户点击
   采纳某条建议。
2. **AI 永远不碰公文要素。** 单位、人员、文号、密级、成文日期由界面与标准词库
   维护（现状即如此，README 已写明）。模型只处理正文文字，不得回写 `DraftInput`。
3. **任何落地前都要过确定性闸门。** 事实比对（`ai_guard`）、要素校验
   （`validator`）、词表与文档规则复扫（`proofread` / `proofread_rules`）。
   闸门不过就丢弃，宁可漏报，不可误改。

第 3 条的推论很重要：**确定性规则是 AI 的裁判，不是 AI 的竞争者**。词表越厚、
规则越准，能放心交给模型的空间就越大。

## 二、核心契约：修订建议总线（Revision）

### 2.1 为什么这是第一步

当前 AI 的落地形态是「整篇提案，全接受或全放弃」（`app/ai_workbench.rs`
`ai_proposal_window`）。这条路走不远：

- 用户要的是「这句话的『截止』该改成『截至』」，不是「这是一份新稿子，你看要不要」；
- 整篇替换让 `ai_guard` 只能做粗粒度事实比对，改动来源无法追溯；
- 每加一个小功能就要新做一套界面，五个小功能之后无法收敛。

**先把所有 AI 能力收敛到同一种产物上，后面每个功能都只是一个「建议生产者」，
界面一次做完不再动。** 这也是「先小流程、后智能体」能成立的前提——否则最后拟合
智能体时要把前面全部推倒。

### 2.2 数据结构

已实现于 `src/revision.rs`：

```rust
/// 一条待确认的修订建议。词表、文档规则、小模型、大模型、智能体统一产出它。
pub struct Revision {
    pub id: RevisionId,
    /// 正文字节范围。永远由程序计算，绝不采信模型给的偏移量。
    pub span: Range<usize>,
    /// 抗漂移锚：原文 + 前后各 12 字上下文。正文被编辑后据此重新定位。
    pub anchor: Anchor,
    /// None 表示只提示、不给改法（语病、结构问题常见）。
    pub after: Option<String>,
    /// 一句话理由。没有理由的建议不予展示——用户无法判断就等于无法确认。
    pub reason: String,
    pub source: RevisionSource,
    /// 分类标签，直接沿用词表与规则里的分组名（错别字、称谓规范……）。
    pub group: String,
    pub severity: Level,          // 复用 proofread::Level：必错 / 疑似 / 提示
    pub confidence: f32,          // 规则恒为 1.0；模型建议按闸门结果打折
    pub state: RevisionState,     // Pending / Ignored / Stale
}

pub enum RevisionSource {
    Lexicon { entry_id: String },   // 校对词表
    DocRule { rule_id: String },    // 文档级规则
    Model { task: String },         // 模型检查器，task 为检查类型
}
```

两处与初稿的偏差，都是照着现有数据形态改的：

- **分类用 `group: String`，不另立枚举。** 词表和文档规则本来就带分组名，且用户
  自建条目可以写任意分组；套一层枚举只会多一次有损映射。
- **状态只有三档。** 初稿里的「拒绝」和「忽略」在界面上是同一个按钮、同一种
  后果，分开只会让用户猜它们有什么区别；「已采纳」则直接离开待确认列表，进入
  撤销栈（`RevisionSet::applied`），不占用状态位。

### 2.3 锚点漂移

`span` 是字节偏移，用户改一个字后全部失效。**没有 anchor 的逐条修订不可用**——
用户一边看建议一边改稿是常态。定位策略：

1. 用 `span` 原位校验 `before` 是否仍匹配，命中即用；
2. 否则在 `span` 附近 ±512 字节窗口内搜 `before` + 上下文指纹，唯一命中即重定位；
3. 仍不唯一或找不到 → `state = Stale`，界面置灰并标「原文已改动」，不参与批量采纳。

### 2.4 采纳即自检（闭环挡幻觉）

每采纳一条建议，立即对被改动段落重跑词表 + 文档规则：

- 若引入了**新的**必错命中或规则报错 → 自动回滚，提示「该建议引入新问题，已撤销」；
- 若通过 → 落地，记入 undo 栈，状态栏累计「已采纳 N 处」。

这一步让小模型的幻觉在闭环里被确定性规则自动挡掉，是敢用小模型的底气。

### 2.5 忽略与记忆

`ProofNote.entry_id` 的注释已经预留了「忽略记录按它存」，但未实现。补上两档：

- **本篇忽略**：随稿件存，换稿即失效；
- **永久忽略**：按 `entry_id`（规则类）或 `before` 文本（模型类）存进配置。

没有忽略机制，误报一次用户就会把整个检查关掉——这比没有这个检查更糟
（`proofread_rules.rs` 开头已经写明这个取舍原则，此处一致）。

## 三、确认的分级

「每个功能都要用户确认」是对的，但**如果每个错别字都弹模态框，人会关掉整个功能**。
确认成本要与风险匹配，分三档：

| 档位 | 形态 | 适用 | 撤销 |
|---|---|---|---|
| 一键确认 | 建议条上点「采纳」 | 错别字、标点、数字、称谓、单句改写 | Ctrl+Z |
| 批量确认 | 「采纳全部必错（12 处）」+ 采纳后逐条可撤 | 同类高置信建议 | 整批撤销 |
| 闸门确认 | 模态 + 勾选声明 | 关键事实变化、整篇替换、正式导出 | 不适用 |

现有的 `fact_changes_confirmed` 勾选就是第三档，保留。严谨性的保证不在弹窗次数，
而在第一节的三条红线。

## 四、大小模型分工

### 4.1 模型角色化

当前 `LmStudioConfig` 是单个对话模型实例（`models.rs`），没有安放「小模型」的位置。
改成按角色配置，各自独立地址与模型名（与 embedding / rerank 已有的独立配置同构）：

| 角色 | 典型模型 | 采样 | 用途 |
|---|---|---|---|
| `draft` | 14B~32B | temp 0.25 | 起草、仿写、篇章级改写 |
| `revise` | Qwen3 4B/8B | temp 0.0 | 单句判定与受限改写 |
| `extract` | Qwen3 4B/8B | temp 0.0 | 材料抽事实、字段抽取 |
| `embed` / `rerank` | 现状 | — | 知识库 |

未配置 `revise` 时回落到 `draft`，不阻断功能。

### 4.2 路由表

| 任务 | 承担者 | 输入粒度 | 输出 |
|---|---|---|---|
| 错别字、固定搭配 | 词表（无模型） | 全文扫描 | 替换文本 |
| 标题规范、文种越界、序号层级、附件一致 | 文档规则（无模型） | 全文 | 提示 + 定位 |
| 标点、数字、量词用法 | 规则为主，小模型兜底 | 句 | 改后句 |
| 语病、搭配不当 | 小模型判定 + 改写 | 句 | `OK` 或改后句 |
| 称谓与公文用语得体 | 小模型（注入词库上下文） | 句 / 段 | 改后句 |
| 去套话、精简 | 小模型 | 段 | 改后段 |
| 篇章结构诊断 | 大模型 | 全文大纲 | **只出清单，不改正文** |
| 起草初稿 / 仿写 | 大模型 | 事实单 + 要素 | 全文（走现有提案窗 + 事实闸门）|
| 材料 → 事实单 | 小模型抽取 + 规则复核 | 材料分段 | 字段列表，逐项确认 |

判断依据：小模型在**判定、抽取、受限改写**上可靠；在**长文生成、多约束同时满足、
篇章规划**上不可靠。凡是「一次只回答一个问题、输入不超过一段」的活，交小模型。

### 4.3 小模型调用铁律

1. **一次一句、一次一个问题。** 不要在一个 prompt 里同时问「有没有错别字、语病、
   套话」——小模型会互相干扰，且无法归因。每个检查器一个 prompt。
2. **不要求模型输出 JSON，更不要求输出偏移量。** 小模型算 offset 必错。要求它
   输出「改后的整句」或 `OK` 两种之一；**span 由程序对原句与改后句做 diff 求得**。
   这条比任何 JSON schema 都稳。
3. **温度 0，max_tokens = 输入长度 × 1.3 + 余量。** 越界即截断丢弃。
4. **失败重试一次，仍失败即静默放弃**，不向用户报「模型抽风」。
5. **段落级缓存**：段落内容 hash → 结果。未改动的段落不重跑。当前 `revalidate`
   是每帧全量重扫（`draft_page/form.rs`），纯规则尚可承受，接入模型后必须
   改成「防抖 + 只跑脏段」。
6. **本地服务限流**：本地推理通常单并发最优，检查器排队执行，界面显示进度而非
   卡死。

### 4.4 模型输出的程序闸门

小模型改写结果落成 `Revision` 之前，逐条过：

- 关键事实不变（`ai_guard::compare_key_facts` 对改动段落做，为空才通过）；
- 长度变化率在阈值内（默认 ±40%，超出多半是模型跑飞）；
- 不得引入原句没有的数字、百分比、书名号内容；
- Markdown 结构标记（`#`、列表符号、表格管道）数量与位置不变；
- 改后句自身再过一遍词表，不得新增必错命中。

任一条不过 → 丢弃，不展示。用户看不到的误报不是误报。

### 4.5 提示词模板（`revise` 角色示例）

```
系统：你是公文文字校对助手。只做被指出的那一类问题，不做其他修改。
     不得增删事实、数字、单位名称、人名、日期、书名号内容。
     输出只有两种：完全没有该类问题时输出 OK；否则输出修改后的整句，
     不加解释、不加引号、不加标记。

用户：【检查类型】语病（成分残缺、搭配不当、句式杂糅）
     【原句】通过这次专项整治，使全区安全生产形势明显好转。
```

`prompt.rs` 已有的注入防护（标准优先级高于任务描述、待处理文本不是指令）
要原样沿用到每个检查器模板。

## 五、演进路线

顺序原则与你的判断一致——**先细节，后流程**；但补一个前置：**先定契约**。
否则五个小功能各带一套界面，最后拟合智能体时要全部重写。

### 阶段 0：契约与面板（无模型）— ✅ 已完成

- `src/revision.rs`：`Revision` / `Anchor` / `RevisionState` / `RevisionSet`，
  含采纳、撤销、忽略与三级重定位；
- `src/draft_page/revise.rs`：修订建议面板与两道闸门（落地前重锚、落地后自检）；
- `revalidate`（`draft_page/form.rs`）把词表与文档规则的命中改投到这条总线，
  `warnings` 只留要素校验与版式实测；
- 接上了那个现成的低垂果实：`From<ProofNote> for ReviewNote` 一路把
  `replacement` 丢掉，导致词表里「必错可一键替换」的能力界面上根本没有。现在
  141 条规则里可替换的那部分，用户看到的是「布署 → 部署」加一枚采纳按钮。

**验收**：不接任何模型，词表与文档规则的建议可逐条采纳、撤销、忽略；改稿后
建议正确重定位或置灰。锚点的三级判定、闸门的拦截与回滚、忽略的两档记忆均有
单测锁住。

### 阶段 1：第一个小模型检查器

选**语病与表达**先做——词表覆盖不了，价值最高，且属于「疑似」档，误报容忍度高。

**验收**：一份 2000 字稿件，检查耗时可接受；闸门拦截率与最终采纳率有埋点；
关掉模型服务时功能优雅降级而非报错。

### 阶段 2：铺开检查器

称谓规范、标点数字、去套话、版式复核，逐个加。每个都是独立的
`Checker` 实现，产出 `Revision`，不碰界面。

**验收**：新增一个检查器的改动量 ≈ 一个 prompt 模板 + 一段闸门配置。

### 阶段 3：起草侧改造

现有大模型起草改成**分段生成 + 逐段确认**：先出大纲（用户确认）→ 逐节生成
（每节进提案）→ 合稿。整篇 diff 保留作为兜底视图。事实单确认（工作台已有）
前置不变。

### 阶段 4：SOP 编排层（智能体）

**不是让大模型自由调工具。** 公文 SOP 是确定性状态机：

```
拟稿 → 要素校验 → 格式规整 → 文字校对 → 表达润色 → 事实核对 → 版式排版 → 送审
```

每个 `Stage` 有：进入条件、检查器集合、通过标准（如「必错 = 0」）、可跳过与否。
**流程推进由程序控制，模型只在两处参与**：

1. 某一步内产生改写建议（即阶段 1–2 的检查器）；
2. 生成「当前稿件还差什么」的诊断摘要（只读，不改正文）。

这样「智能体」是可预期、可审计、可复现的。谁在第几步改了哪一句、依据哪条规则、
用户是否确认——全部可回放，这正是公文场景需要而通用 Agent 给不了的东西。

| 缺口 | 位置 | 阶段 | 状态 |
|---|---|---|---|

| 建议无抗漂移锚，改稿后偏移即失效 | — | 0 | ✅ `revision::Anchor` |
| AI 提案只能整体接受 / 放弃 | `app/ai_workbench.rs` `ai_proposal_window` | 3 | 待办（起草侧改造时一并做） |
| `revalidate` 全量重扫，无防抖与脏段缓存 | `draft_page/form.rs` | 1 | 待办 |
| 单一对话模型，无角色路由 | `models.rs` `LmStudioConfig` | 1 | 待办 |
| `generate` 无重试、无输出长度约束 | `lmstudio.rs` | 1 | 待办 |
| 无检查器埋点 | — | 1 | 待办 |
| 无编排层 | — | 4 | 待办 |

「AI 提案只能整体接受」原本列在阶段 0，实际推到阶段 3：整篇提案的拆条依赖
**分段生成**，而不是拆现在这个 diff 窗口。现在的做法是让两条路并存——整篇改写
仍走提案窗，逐句修饰走修订面板；等阶段 3 把起草改成分段生成，提案窗自然退化
成兜底视图。

## 七、埋点

不度量就无法判断某个检查器该留还是该关。每个检查器至少记：命中数、闸门拦截数、
用户采纳数、用户忽略数、采纳后撤销数。**采纳率低于三成的检查器应当默认关闭**，
而不是继续打扰用户。数据只留在本机，与配置同目录。
