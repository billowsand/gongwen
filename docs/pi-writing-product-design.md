# 双路径写作与 Pi 文件工作区方案（讨论稿）

日期：2026-11-01。基于当前项目 `main` / `e5115c3` 与用户第二轮产品讨论。
这是规划建议，未实现、未替换既有架构决定，模型效果与平台兼容仍待试点。

本文细化并调整 `pi-durable-research.md`：大模型路径允许在专属工作区自由读写多个中间文件，最终提交一个 Markdown 成品；不再建议为了接入而让 Rust 的旧 Board 持有每次写稿状态。

## 一、产品定位

| 路径 | 主要用户条件 | 产品行为 | 编排归属 |
| --- | --- | --- | --- |
| 分阶段写作 | 本地小模型，如用户拟用的 Qwen 9B；也适合希望逐步控制的用户 | 素材准备、提炼、提纲、各节素材、成文、统稿审阅 | 程序控制阶段与输入输出 |
| 智能写作 | 工具调用与长任务能力较强的模型，如用户拟用的 MiniMax M2.7、DeepSeek 4.1 Flash | 用户描述目标、提供材料，智能体检索、起草、拆分、修改并提交结果 | Pi + 标准技能 |

这里按工作方式区分，不按模型名称或参数量硬编码路由。模型名称是产品目标举例，不代表本次已测试这些端点。设置提供两条路径各自的默认模型，用户可以更换。

两个入口共用稿件、材料来源、词库、公文规则、审阅与导出。大模型路径不是把旧流程藏到 Pi 后面；小模型路径也不依赖 Pi 运行。

当前分阶段写作并不支持所有文种：`agent::writing::supports` 排除了电话记录单、会议议程、会议纪要。保留现状，不在本次暗中承诺扩大全文种支持。

## 二、核心边界：过程自由，交付明确

Pi 的任务是围绕当前稿件完成写作。它可以建立提纲、摘录、章节稿、核对记录和多个方案，自行决定先写哪一部分、是否重新检索、如何合并。

程序只要求一个稳定的交付接口：

```text
当前正文 + 写作要求 + 材料/知识工具
                  ↓
       Pi 在任务工作区里读写、修改、合并
                  ↓
       submit_document(path, summary)
                  ↓
       固定版本 Markdown → 交付检查（阻止项 / 提示项）
                  ↓
       直接写入正文（保留修改前版本）→ 现有导出
                  ↓
       卡片「已写入」：撤销本次写入 / 查看差异（都可选）
```

**多文件合并是 Pi 的写作工作。** Rust 不根据文件名排序拼章节，不猜哪个文件最像终稿，不从聊天回复中提取代码块，也不重新统稿。`submit_document` 是产品交付动作，不是新的流程引擎。

问答、找资料和审查也应允许不提交新文稿，结果留在侧栏；只有生成/修改正文任务必须提交 Markdown。这样“帮我看看这段有什么问题”不会被迫产生一份新正文。

## 三、工作区设计

示例结构（应用内部，用户无需管理目录）：

```text
workspace/<稿件UUID>/<会话UUID>/
  input/
    current.md          当前轮正文快照，只读
    request.md          本轮要求与选区信息，只读
    materials/          已导入材料快照，只读
  work/
    outline.md
    notes.md
    sections/...
    final.md            初始候选稿，可以反复编辑
  resources/            导出的插图等只读资源
```

目录只是示例，`work` 内部结构不做硬约束，提交路径也不强制叫 `final.md`。修改现稿时可先将当前正文复制为 `work/final.md`；空白起草不必生成空文件。

只读技能目录作为另一项可见资源。上下文给出当前文种、系统日期、正文/选区、材料角色与可用技能和工具；长材料放文件，避免每轮把全部正文、材料、历史重新拼进一个大提示词。

**工作区是持久目录，不是随任务结束即删除的系统临时目录。** 会话续跑沿用它，新的用户轮次刷新输入快照时保留历史版本。提交后的成品快照另行保存，不再从可变的 `work/final.md` 读取已展示的提案。

路径限制由文件执行环境实施，`cwd` 本身不是沙箱。读写边界应包含绝对路径、`..`、符号链接/Windows junction 等解析；工作区不放数据库和密钥。初期复用 Pi 的文件工具，按需包装执行环境，不重建一套公文专用编辑指令。

多文件合并可由读/写/编辑工具完成；若需要批量摘录和机械拼接，可使用 Pi 的 Code Mode 调用同一组受限工具。是否开放额外命令执行另行按需求决定，不作为基本写作链的前提。

依据：Pi Durable 的 ExecutionEnv 可由宿主提供，文件工具经该环境访问文件；Code Mode 可组合工具调用。[固定版本文档](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/README.md)、[环境接口](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/src/env/index.ts)

## 四、接回文本框：复用现有交付闭环

> **2026-11-02 修订（实现与验收见 `docs/pi-implementation/pi-direct-write-task.md`）。**
> 用户确认了「Pi 成品直接进入正文并可撤销」：Pi 提交成功后不再装待审提案，普通流程
> 也不弹人工校订窗、不勾事实。下面的第 3、4 步按这一条重写；第 1、2 步不变。
> 小模型分阶段写作与旧提案接受（`install_ai_proposal` / `accept_ai_proposal`）原样保留，
> 只是 Pi 不再走它们。

项目已有独立的分阶段写作交付函数 `deliver_writing_proposal`（`src/draft_page/writing/pages/mod.rs`），它没有经过旧 skill engine 就能安装提案；Pi **不再**沿用它，改为复用编辑器那一条统一写值与撤销路径：

1. host 读取提交文件的完整内容，将内容与本轮 ID、基准正文版本、内容哈希一并交给 Rust。
2. Rust 保存这份不可变成品，执行交付检查（`DeliveryReport`：阻止项 / 提示项），再过一遍 `reviewed_draft` 的清理、文种规整、validator 与版式估算，并对规整后的稿件再查一次。
3. 写入前先确认能保留修改前基线：有库稿件把撤销记录（前文、后文、运行标识）写进 AI 会话，存不下就不写；非入库稿件靠本轮工作区的 `input/current.md` 快照（交付前在 `pi_agent::process` 里核对它确实在盘上）。
4. 界面线程直接换 `generated_markdown`：经 `draft_page::replace_with_undo` 记一个撤销点（一次 Ctrl+Z 撤回整次写入），编辑器状态按稿件隔离；非活动标签暂时绑定自己的状态记撤销点，再恢复当前标签状态，不把别的稿子塞进当前撤销栈。校对与预览状态按新正文重算。
5. 卡片显示「已写入正文」，提供可选的「撤销本次写入」与「查看差异」；正文写入后又被改过时卡片撤销禁用并说明可用 Ctrl+Z。运行期间用户改过正文则不自动覆盖：成品连同一句提示留在这一轮里，可显式取回（同样留撤销记录）或按当前正文重做。
6. 运行记录标成已写入（`Accepted`，旧语义相同），同一份回执不会被自动应用第二次，撤销后重启也不会被它盖回来。

`reviewed_draft` 不单独等于全部来源检查：来源检查已抽成共享的交付关卡（`pi_agent::delivery`），与本轮输入材料、当前正文和工具证据一起执行。**事实来源疑点现在只作提示**（写在结果卡与审校抽屉里），不再阻止写入；技术问题（空稿、选区外被改、公文引用被删改、工作区路径泄漏、哈希 / 体积）仍拒绝交付。

智能体可调用 `check_document` 自查，提交时程序再强制检查。提示词明确告诉模型：事实疑点只提示、不会锁住交付，不要为了「解锁」反复重交。失败重试受宿主预算限制，不另写缺口循环算子。

来源登记由工具与材料导入过程产生，不能采信 Pi 自写“这条事实已经确认”。风格样稿和结构范文仍不能当作本次事项的事实来源。

### 流式展示

- 侧栏显示模型说明、工具进度与提问。
- 主工作稿区显示当前候选 Markdown；可在一次文件写入/编辑完成后刷新，没必要从模型 token 里实时拼文稿。
- `work/final.md` 的更新只是草稿预览，不自动写入正文。
- 只有明确提交并通过交付检查的快照才写进正文；终稿还没准备好时可显示“正在整理章节”。

这样延用现有 `workspace_ui.rs` 的“正文 / AI 工作稿”和逐块排除能力。第一版无需多文件 IDE；可以只加一个可折叠的中间文件列表，供有需要的人查看。

### “只改选区”的处理

不要求模型返回字符偏移。最终仍提交完整 Markdown，程序对照本轮快照检查选区外是否变化；严格限定模式下越界就返回问题，模型修正后重交。写入时再检查正文基线，保留「运行期间正文改过就不自动覆盖」的防护。

### 资源引用

最终主要产物是一个 Markdown 文件。若使用图片，提交时把实际引用的工作区资源导入现有图片库并改写路径，不能把会被清理的内部绝对路径留进正文。附件全文、Mermaid 和公式继续遵守现有 Markdown 规则；不在接入层扩充新语法。

## 五、标准技能怎么组织

外部技能包 `skills/gongwen-markdown/` 作为所有写稿任务共用的语法和文种知识来源。保留参考文件与模板，避免另复制一套长期分叉的规则。

应用内技能改为标准 frontmatter + 操作说明，例如：

```text
gongwen-draft       根据材料起草，必要时先检索或问清目的
gongwen-revise      按要求局部或整体修改，保护无关内容和事实
gongwen-review      审核正文并列出问题，需要改稿时提交修订成品
gongwen-imitate     学习样稿的表达或结构，不照搬其具体事实
gongwen-research    检索、论证、分节起草研究报告并整合
```

精简、调整语气等可作为修改技能的常用要求，未必继续维持一个算子/一个技能。技能数量按用户任务与测试效果决定，不机械映射当前 15 个内置条目。

技能可以说明推荐做法和自检标准，但去掉旧 `flow`、算子名、程序变量插值等执行语言。大模型自行决定先后、回退和检索次数；公文规范、权限与交付闸门依然由程序执行。

Pi Coding Agent 自带标准技能加载；Durable 是独立内核，仍需一层技能目录与读取适配。该适配只负责发现和提供文件，不能扩大成新 DSL 解释器。[Pi 技能说明](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/skills.md)、[Durable 扩展规范](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/docs/spec.md)

## 六、给 Pi 的产品工具

| 工具组 | 责任 |
| --- | --- |
| 文件工具 | 在允许范围读取技能/材料，建立、编辑与合并工作文件 |
| 知识与稿件 | 检索、读全文、查版本，返回可追溯的证据编号 |
| 词库与规则 | 查标准词条、校验文种和正文，返回结构化问题 |
| 内网接口 | 复用现有已配置服务及 schema、参数校验和权限 |
| 人机交互 | `ask_user` 展示必要问题；要素建议仅生成候选卡 |
| 成品交付 | `submit_document(path, summary)` 提交一个固定版本 Markdown |

Pi 可以选查什么、如何修改，宿主决定能访问什么与何时允许交付。无须为了接入而对外发布通用 MCP 服务，也不必复制整个旧 `ToolCtx`。

## 七、可以裁什么，必须留下什么

| 处理 | 当前模块与理由 |
| --- | --- |
| 退役旧通用编排 | `engine`、`router`、`skill` 的 flow 解释、`ops/agent` 与固定起草/检索/缺口编排；标准技能替代其流程职责 |
| 退役对应桥接 | `ai_panel/skill_job.rs` 的旧流程调度、旧流程检查点 UI；先处理旧会话兼容再删除 |
| 保留分阶段写作 | `agent/writing/`、`draft_page/writing/` 与独立任务持久化 |
| 保留并解耦模型基础 | `backend`、`budget`、部分 `toolcall` 仍给分阶段写作、API 工作台与风格管理使用 |
| 保留接口产品 | `api`、`api_import`、`apidef` 和接口管理/测试 UI，不随旧引擎删除 |
| 提取领域服务 | `tools` 中知识库、词库、检查、HTTP 的实现；移除对 Board/Skill/engine::Event 的依赖 |
| 保留共享规范 | `evidence` 的引用清理、事实来源、风格档案、要素登记、validator、proofread 与审阅合并 |
| 搬走小型通用依赖 | 如 `board::value_to_text`、`tools::short`、`gaps::sentence_spans`；不为几个辅助函数保留整套引擎 |

目标是最终只有两条执行路径：固定分阶段写作与 Pi 智能写作。旧引擎仅作为迁移过渡，不成为永久第三条产品线。

旧会话正文、聊天与已交付提案继续可读；进行中的旧 DSL 检查点可提供旧版过渡续跑或明确转换为重新发起，不承诺把检查点无损转换成 Pi 内部状态。

## 八、轻量适配仍要做好的契约

1. **基准与追问**：运行任务绑定正文快照。未采纳时的“再短一点”默认继续改上一份候选稿；明确引用当前正式稿时才改基准。部分采纳后，下轮以实际采纳结果重新同步，不能沿用被排除改动的旧终稿。
2. **提交快照**：提交文件被复制为不可变版本，哈希与回执持久化；Pi 后续写文件不能改变已经展示的提案。同一调用重试返回原提交结果。
3. **文件恢复**：Durable 记录对话/任务不代表文件系统自动成为同一事务。文件写入须原子替换；中断编辑后读取当前文件确认状态，不盲目重复插入。Pi 自带 write/edit 在 v1.4.0 源码中没有声明 replay-safe，不能宣传为任意文件变更都会自动恰好恢复一次。[write 实现](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/src/tools/write.ts)、[edit 实现](https://github.com/earendil-works/pi/blob/v1.4.0/packages/durable/src/tools/edit.ts)
4. **停止与交付**：停止后保留工作区，未提交或未通过检查的内容只能看草稿，不能误当完成。取消和超时均不等于文件一定未写入。
5. **生命周期**：明确一个会话的存储所有者，处理多窗口；清理与同步时关联会话、工作文件和成品快照，不能只保存聊天丢掉文件。

这些是产物桥接的边界，不需要升级成自研编排平台。应避免把整个 Pi 任务图映射回 Rust Board，也不为每种写作动作再设计一套状态机。

## 九、选型与实施顺序

优先以 Pi Durable 做验证：它适合应用宿主持久化运行；代价是技能发现、UI 和工作区连接需要薄适配。Coding Agent SDK 更快获得现成技能与会话，但不等于 Durable 恢复语义，不能同时常驻两套 Pi 内核来掩盖取舍。若验证发现 Durable 适配已接近重建框架，应重新比较 SDK 方案。

| 阶段 | 必须交付的用户能力 |
| --- | --- |
| 1. 打通成品出口 | Pi 读取正文，修改工作文件，提交后直接写进正文（保留修改前版本与撤销） |
| 2. 做成写作产品 | 标准技能、材料与知识库、选区保护、必要提问、继续修改已写入的稿子、按当前正文重做 |
| 3. 验证持续使用 | 文件中断恢复、提交去重、会话/稿件生命周期、多窗口与离线安装；比较目标模型的真实任务效果 |
| 4. 收缩旧框架 | 抽出小模型与 API 工作台仍依赖的共享能力，默认入口切换到 Pi，删除旧通用流程与对应编辑界面 |

过程中的试点开关只用于验证与回退；完成迁移后，用户面对“分阶段写作”和“智能写作”两个清晰入口，不面对若干引擎和兼容模式。

本次只读检查了实际交付代码，并由一个只读子代理复核裁剪依赖，未实现上述接口，未运行模型或恢复试验。原有“不引入外部框架”等决定应在实施前按本方案复议记录，三条红线保持。

> **2026-11-02 实现补充。** 上面第 1–2 阶段的交付形态已按用户确认改写：Pi 提交即写入正文（保留修改前版本与撤销），不再经过提案接受；小模型分阶段写作与 API 工作台仍走原有路径。

## 十、离线部署是交付前提

新增用户约束：安装和使用环境不访问公网。方案必须做到目标机不运行 npm/pip、不下载模型目录或执行运行时更新。模型推理可以使用本机或可达的内网服务；如果只有公网模型端点，则该模型不能用于隔离环境。Pi 本身不提供模型权重，也不消除大模型服务器的硬件要求。

### 随包分发

建议第一版采用独立 Node + 完整生产依赖目录，先保证可复现，再考虑打成少量 bundle：

```text
runtime/pi/
  node.exe 或 bin/node
  host/dist/host.mjs
  host/package.json
  host/node_modules/       锁定的直接与传递生产依赖
  skills/                 技能、模板、参考文档
  licenses/
  manifest.json           运行时/依赖/协议版本及资源清单
```

Node 只供应用通过绝对路径启动，不安装到系统、不改 PATH。工作区、SQLite 和日志写用户数据目录，不能写安装目录。npm、TypeScript 编译器和构建工具只在开发/CI 使用，不是目标机前提。

联网构建阶段固定 Pi、Node 和所有传递依赖版本，用 lockfile 安装并构建 host，裁去开发依赖；把 JS、JSON、WASM、worker 入口等实际运行资源一起装箱。按 Windows x64、Linux ARM64、Linux x64 分别组装和验证，不盲目跨平台复制 node_modules。有离线构建需求时另准备完整依赖缓存/镜像；这与目标机离线安装是两个问题。

Pi v1.4.0 的 Durable SQLite 适配使用 Node 内置 `node:sqlite`，无需为此另装 SQLite 服务或 Python 编译环境；Code Mode 使用 QuickJS WASM，相关文件必须随生产依赖携带。[SQLite 适配源码](https://github.com/earendil-works/pi/blob/v1.4.0/packages/chord/src/sqlite/node.ts)、[Code Mode 包定义](https://github.com/earendil-works/pi/blob/v1.4.0/packages/codemode/package.json)

运行时采用应用已有端点配置和静态模型参数，不依赖公网模型目录、npm/git 技能安装或 OAuth 登录。模型目录刷新是 Pi AI 的显式接口，host 不应触发公网刷新。[模型目录文档](https://github.com/earendil-works/pi/blob/v1.4.0/packages/ai/README.md)

### 接入当前打包链

`package-portable.ps1` 已按 runtime 清单校验、复制文件，并生成整包 SHA256SUMS。新增按平台组装的 Pi runtime 清单或复制步骤，再复用 Windows Inno、deb、pacman 的 staging；`package-upgrade.ps1` 的清单差分机制可继续用于变化的 Node、host、依赖和技能资源。用户数据目录不得纳入升级删除清单。

Linux 仍须处理系统动态库。当前 `verify-deb-install.sh` 使用 apt 联网补齐依赖，且仅对 Rust 主程序做 ldd，不能作为完整的离线安装证明。需要增加 Node 及实际依赖的检查，并在预装所需系统库的离线基线镜像中安装、启动；对缺库的机器，提供匹配发行版/架构的系统依赖离线包或内网软件源。GLIBC、GLIBCXX 与内核要求必须按具体 Node 版本检查。

最终验收要在无 Node/npm/Python 开发环境、无公网、无用户缓存的干净目标机上完成：安装 → 启动 Pi host → 连接本机/内网模型 → 读取技能与知识库 → 编辑多文件并提交 → 重启恢复 → 离线升级。此验收尚未执行；安装包体积与启动内存也尚未测量。
