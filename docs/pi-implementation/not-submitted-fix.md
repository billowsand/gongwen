# 实测缺陷：写出文件后长度截断导致未交付

2026-11-02，用户反馈 `run-20261102-070844-c5c62880` 出现 `not_submitted`。
只读检查该轮次的工作文件与 Durable 库，没有修改用户工作区、配置或调用外部模型。

## 确认原因

`workspace/work/draft.md` 已写出（6832 字节），无交付回执。模型先用占位文字调用检查工具，
后尝试重传整篇正文作为检查参数。最后一条助手消息的 `stopReason` 为 `length`，
检查工具参数未完成。Durable 将该 input 标为 done，host 发现没有显式提交即返回 `not_submitted`。
这不表示正式稿或材料丢失，也不是已经提交后界面漏显示。

## 修复

- `check_document` 新增 `path` 参数，仅能指向工作区 `work/` 内普通、非空、有效 UTF-8 文件，
  复用提交读取器的路径、符号链接与大小限制。host 读取全文后按原有 `text` 契约交 Rust 检查，
  不要求模型再次输出全文。`path` / `text` 同传报错；省略仍检查开始时的正文。
- 更新系统提示，明确检查工作稿优先传路径，省略参数不表示检查最近工作稿。
- 模型结束但没有回执时，原任务内最多续跑两次，要求读实际文件、按路径检查、显式提交。
  不自动选择候选稿，不把聊天文本当成正文，不跳过 Rust 强制闸门和人工接受。
- 使用固定的补交 submission ID，数据库重开不重置补交额度；共享原有取消、提问、超时和工具次数限制。
  额度用完继续明确报错并保留文件，不无限循环。

## 第二次实测修正：上下文预算根因

后续 `run-20261102-072701-8b017463` 仍失败，已确认前一修复不完整：最后三次输出分别只有
10、1、1 token，均为 `length`，并非用户设置的最大输出过小。host 收到的默认 32k 窗口在
约 28.7k 历史加 SDK 的 4096 安全余量后，输出被压到 1。旧 Durable 保留最近 20000 token 的
策略又使本轮找不到压缩切点，两次提醒未能解围。

实际修复与新验证见 `pi-budget-fix.md`；以上第一轮结果作为历史保留，不再建议用户调整输出长度或从头写。
