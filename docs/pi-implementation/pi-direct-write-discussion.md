## 当前重复点

Pi 提交文件后，程序先检查工作区/快照、来源与选区，再规整 Markdown、跑文种及词表规则，
随后创建提案。安装提案又按新旧正文的关键事实变化要求用户核对、勾选和接受。
即使资料中的数字已经通过来源检查，仍可能因为相对旧正文是新增而要求人工再次确认。

## 用户已确认的方案（2026-11-02）

用户回复：“按此方案，直接写入并保留撤销记录（推荐）”。以下方案已获授权，4C 完成后按独立任务实施；不是继续等待确认。

- Pi 成功交付后直接更新当前编辑稿，普通流程不再出现事实勾选和接受提案。
- 修改前内容自动保留，支持撤销和按需查看差异；有疑点的事实只提示，不强迫处理。
- 模型不能修改表单授权要素、已发布/归档只读稿；执行期间用户改过正文时，不用旧结果覆盖新编辑。
- 空白起草与修改现稿都直接进入文本框；仅审核/资料清单仍进侧栏，不替换正文。
- 这改变之前的“正式稿只由人接受提案”产品约定。用户确认后同步架构文档和验收契约，
  不用旧约定阻止用户的新产品选择，也不把小模型分阶段写作一并改掉。

## 实施时要明确的技术契约

1. 复用编辑器统一写值和撤销路径，不能为了绕过提案直接散落赋值 generated_markdown。
2. “不覆盖用户后续编辑”和重复交付去重必须在写入前校验；冲突时保留 AI 产物，不清空或强覆盖。
3. 自动写入后的会话状态、运行回执消费状态与版本留痕相互对应；重启恢复不能重复覆盖正文。
4. 事实疑点与技术/权限阻止写入的问题应结构化区分，不靠中文错误字符串猜类别。
5. 修改前版本、撤销、已保存/未保存稿件和撤销后再编辑的行为要有明确覆盖范围。
