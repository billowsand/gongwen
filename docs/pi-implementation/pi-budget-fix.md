# Pi 自动预算与旧起草设置脱钩

2026-11-02，接续 `not-submitted-fix.md` 的第二次真实失败。

## 根因与界面契约

「AI 管理 → 模型服务 → 最大输出 Token」原本服务旧文字起草，Pi 早期适配器复用了整份配置。
Pi 对自动窗口又硬编码回退 32768，没有使用项目已有的服务/模型窗口解析器。

本轮只读检查真实任务的 SQLite 用量与停止原因：稿件已写入、编辑并检查；最后三次输出为
10、1、1 token，停止原因为 length。SDK 在上下文使用约 28.7k 加 4096 安全余量后只能留下
1 token。单纯再提醒提交无法修复。上一轮要求用户修改输出上限的提示不成立。

Pi 不应要求用户理解或调整单次输出上限。实际模型仍有上下文和输出限制，由程序管理，不能无限生成。

## 改动

- `pi_chat` 清除旧起草的手动窗口，使用自动模式，并设置内部输出预算；用户现有小模型参数不变。
- `pi_model` 复用 `lmstudio::context::peek_window`：服务缓存优先，再按已维护的模型表、最后保守默认。
  不再把 DeepSeek Flash 一律当作 32k；不在主线程增加网络探测。
- Durable 自动压缩为响应预留最多 16k，按窗口比例缩小近期保留量（最多 4096），禁用额外后台压缩并发。
  修复原先保留 20000 导致长任务找不到切点的情况；仍由 Pi Durable 做压缩，不自建另一套摘要引擎。
- 失败提示删除让用户改输出长度、从头生成的说法。设置页明确旧参数不作用于 Pi，修正已过时的 Pi 试用说明。
- 用户点「接着写」时生成本次人工继续标识，先等待原 Durable 任务收尾再补交，避免并发。
  本次人工动作有新的两次补交额度，单次动作中的请求 ID 固定；普通数据库重开不重置旧额度。
  已有回执仍直接重放，不增加模型调用。旧工作稿和事实来源保留，正式稿仍经闸门和人工接受。
