# 交互优化路线图

> 接 `docs/ui-optimization-checklist.md`。那一份已基本做完，它管的是**静态视觉**——
> 选中态、图标、分组线、配色、空状态。这一份管**动态交互**：等待时给不给反馈、
> 一件事要点几下、做错了能不能退回来、有没有办法找到某个功能。
>
> 判据换了：不再问「好不好看」，只问三件事——
> **等待有没有反馈、重复动作有没有变快、走错路能不能退回来**。

---

## 零、先说结论：瓶颈已经不在像素

旧清单那一轮之后，静态观感的收益已经递减。现在真正拖慢人的是三处：

1. **模型在跑的时候，界面什么都不说。** `lmstudio.rs:201` 写死 `"stream": false`，
   `app/jobs.rs` 里每个任务都是 `thread::spawn` 一发不回头——没有取消通道。
   本地 14B 模型生成一节要几十秒到几分钟，这段时间里用户看到的是状态栏一行
   「正在列大纲…」，不知道进行到哪、不知道还要多久、想停也停不下来。
   **这是全应用等待最长、反馈最少的地方。**
2. **校对是全应用重复次数最多的动作，但它的路径最长。** 建议只活在右侧 300 点的
   抽屉里，正文上一个标记都没有；每处理一条都要「在抽屉里找 → 点定位 → 回正文
   看 → 回抽屉点采纳」。一篇稿子几十条，这个来回是主要成本。
3. **51 个命令散在 6 个分区卡里**（`draft_page/ribbon.rs`，六个 `ribbon_*` 函数），
   加 7 个导航页，没有任何搜索入口，也没有一张快捷键清单。

下面按这三处展开。

---

## 一、P0：等待要有反馈，且随时可以停

### 1.1 模型输出流式化

- **现状**：`lmstudio.rs:149` `generate_with_options` 请求体里 `"stream": false`，
  整段生成完才一次性返回。起草、逐节生成、仿写、知识库问答、逐句复核全走这条路。
- **改法**：请求带 `stream: true`，按 SSE 逐块解析，边收边往提案区/大纲小节/问答
  气泡里追加。不改任何落地逻辑——**流式只影响"看得见"，闸门与事实比对仍然在
  整段收完之后跑**，红线一条不动。
- **为什么排第一**：它不新增任何功能，只是把已经在发生的事显示出来；而它覆盖的
  是应用里最长的那几段等待。

### 1.2 每个长任务都要能取消

- **现状**：`app/jobs.rs` 的八处 `thread::spawn` 都没有取消位。点错了文种、选错了
  模型、材料贴漏了一段，只能等它跑完。
- **改法**：任务持一个 `AtomicBool`，界面上的「停止」按下即置位；worker 在每个
  chunk 边界检查，退出时丢弃结果不回传。流式化之后这件事几乎是白送的——
  chunk 边界天然就是检查点。**建议 1.1 与 1.2 一起做，分开做要改两遍同一处。**

### 1.3 状态栏一行放不下这么多事

- **现状**：`status` 是一个 `String`，所有任务轮流往上写。`app/jobs.rs:503` 的注释
  自己写明了后果：「放进 `knowledge_error` 而不是 `status`：status 紧接着会被索引
  进度覆盖」——**这是绕开问题，不是解决问题**。
- **改法**：状态栏留一个「当前任务」位（任务名 + 进度 + 停止按钮），多任务时显示
  「N 项进行中」，点开是一张任务列表。知识库索引已有 `(done, total, title)` 三元组
  （`jobs.rs:369`），把它抬成所有任务的通用形状即可。

### 1.4 错误不该只在状态栏闪一下

- **现状**：导出失败已经挂进审校抽屉了（`draft_page/editor.rs:395`，有红框、能看
  全文），这是对的做法；但模型连不上、TeX 编译失败、导入失败、索引失败仍然各写
  各的——有的进 `status` 一闪而过，有的进各自的 `*_error` 字段。
- **改法**：统一成一处通知区：右下角吐司（自动淡出）+ 可回看的历史列表。
  判据很简单——**用户可能需要把这段错误抄给别人看，它就不能只出现三秒**。

## 二、P0：把校对循环的路径砍短

这一节是清单里性价比最高的部分：三项改动都不新增功能，只是把已有的东西放到
手边。

### 2.1 建议在正文里就地标出来

- **现状**：`draft_page/revise.rs` 的建议卡片只在右抽屉里，正文没有任何标记。
  用户必须靠「定位」按钮来回跳。
- **关键事实**：`highlight.rs` 的 `MarkdownHighlighter::layout` **已经接受两组
  span**——`anchor`（预览点中的段落）和 `search_matches`（查找命中），并且按
  （文本, 宽度, 锚点, 命中）四元组缓存。**再加一组 revision spans 就行**，
  按 severity 画不同颜色的波浪线（必错红、疑似橙、提示灰）。
- **顺带**：点正文里的波浪线 → 右抽屉滚到并高亮那张卡片，反向也通。现在只有
  卡片 → 正文单向。
- **成本**：改动集中在一个函数加一条缓存键，是这份清单里最小的一项；体感提升
  却最大——**用户终于能在正文里看见"这篇稿子哪儿有问题"，而不是在侧边栏里读
  一份清单。**

### 2.2 键盘逐条过稿

- **现状**：每条建议都要鼠标往返右抽屉。
- **改法**：F8 / Alt+↓ 跳下一条（同时滚动正文并选中该 span），Enter 采纳，
  Del 忽略，Shift+Enter 永久忽略。校对是一次几十遍的重复动作，**这类动作的
  设计目标是让手不离键盘**。
- 参照：Word 的 F7 拼写检查、IDE 的 F8 next problem，用户对这套键位已有肌肉记忆。

### 2.3 两套撤销栈互不知情（这条更像缺陷）

- **现状**：`revise.rs:90` 的 `accept_revision` 直接改 `self.doc.generated_markdown`，
  绕过 TextEdit；而编辑器里 egui 自带的 Ctrl+Z 按文本快照回退。于是：
  采纳一条建议后按 Ctrl+Z，**正文退回去了，但 `RevisionSet.applied` 仍记着这条
  已采纳、埋点也已经记了一笔**；此时再点抽屉里的「撤销上一处」，
  `revision.rs:533` 的 `undo_last` 会发现那一处文本已经变了并拒绝执行
  （测试 `undo_refuses_after_the_user_edited_that_spot` 锁的正是这个行为）。
  用户看到的是「撤销按钮坏了」。
- **改法**：让 Ctrl+Z 在「最近一次动作是采纳建议」时转交给 `undo_revision()`，
  否则才交给 TextEdit；或者更彻底——采纳也走编辑器的输入通道，只留一条撤销栈。
- **为什么算 P0**：一个能把状态搞到自相矛盾的撤销，比没有撤销更伤信任。

### 2.4 建议列表要能筛、能折、能整类处理

- **现状**：`revisions_ui` 是一条平铺列表，只有「采纳全部必错」一个批量口子。
- **改法**：按级别分段（必错 / 疑似 / 提示，各自可折叠并显示条数）、按 `group`
  二级折叠、「只看这一组」筛选、「这一整组都忽略」。
- **依据**：词表 141 条 + 20 条文档规则 + 3 个模型检查器，长稿一次几十条建议。
  现有的「永久忽略」是按条记的（`revise.rs:137`），但用户真正想表达的常常是
  「这一整类我不需要」——**给不了整类的出口，他就去关掉整个面板**，这正是
  `proofread_rules.rs` 开头论证过的那个取舍。

## 三、P1：让人找得到功能

### 3.1 命令面板（Ctrl+Shift+P）

- 一个搜索框，输中文命令名直达：「花脸稿」「提交版本」「导出 PDF」「切换主题」
  「打开知识库」。命中行右侧顺带显示该命令的快捷键——**这同时解决了快捷键
  没人知道的问题**。
- 对一个有 51 个功能区按钮 + 7 个导航页的桌面应用，这是单位成本最低的可发现性
  改进：不动现有任何布局，纯增量。

### 3.2 快捷键补齐 + 一张清单

- **现状**（`app/session.rs:478-620`）：已有 Ctrl+S 保存、Ctrl+B 加粗、Ctrl+N 新建、
  Ctrl+W 关标签、Ctrl+Tab 切标签、Ctrl+1..9 直达标签、Ctrl+F 查找、Ctrl +/-/0 字号、
  macOS 的最小化与全屏。
- **缺**：标题层级（Ctrl+Alt+1/2/3）、导出（Ctrl+E）、打印（Ctrl+P）、
  提交版本、切换预览模式（源码/预览/对照）、以及 2.2 的那组校对键位。
- **更缺的是清单**：全仓库搜不到一处展示快捷键的帮助界面。菜单项已经开始标
  快捷键了（旧清单 2.1 已完成），把它补全并加一页「键盘快捷键」。

### 3.3 文件拖放

- **现状**：`dropped_files` / `hovered_files` 全仓库一处未用；词库树里的拖拽
  （`app/vocabulary.rs:1052`）是内部排序，与文件无关。导入文档、挂 PDF 附件、
  插入图片**三条路全部只能走文件对话框**。
- **改法**：拖 Word/Markdown 进窗口 → 新建稿件或在光标处插入（按落点区分）；
  拖 PDF 进稿件 → 成为附件；拖图片进编辑器 → 插到光标处。
  拖拽悬停时画落点提示框。
- 这是桌面应用的默认预期，缺了会被当成「这软件有点旧」。

### 3.4 模型服务的首次配置引导

- **现状**：标准词库已有完整的首次建库引导（`app/vocabulary.rs:423`，且
  `app.rs:350` 还专门处理了老用户不误弹的问题）——这套做法是对的。但**模型服务
  没有对应的东西**：新用户打开起草页点「生成」，得到的只是一行连接失败。
- **改法**：检测到未配置时，在起草页 AI 区给一张引导卡：LM Studio 与 Ollama 两条
  路各三步，附「探测本机服务」一键按钮（探测逻辑 `jobs.rs:122` 已有）。
  **不做成模态向导**——照抄建库引导的做法：可跳过、可重开、不锁功能。

## 四、P2：空间与密度

| # | 事项 | 现状与改法 |
|---|---|---|
| 4.1 | **两个右抽屉挤中央区** | 版本历史与审校提示各占 240~460 点（`draft_page/page.rs:33,47`），同时开时中央区被压得很窄。改法：窄窗口下两个抽屉自动合并成一个带两个标签的抽屉；或记住「同时只开一个」的偏好 |
| 4.2 | **稿件表格 11 列** | 旧清单 2.6 的遗留项，当时明确写了「改动面大，留作后续」。改法：列显隐开关 + 记住选择，默认收起「归档 / 知识库 / 更新时间」 |
| 4.3 | **要素面板全有全无** | `form_collapsed` 只有展开与收起两态（`page.rs:57`）。改法：收起后保留一条窄竖条，上面按版头/主体/版记三段标缺项红点，点一下临时浮出该段——缩略导航图（旧清单 4.5）已经有这三段的概念，复用它 |
| 4.4 | **图片没有尺寸控制** | markdown 只写 `![alt](src)`（`images.rs`），插进去多大就是多大。改法：选中图片后给一条浮动工具条调宽度百分比，写成导出器能认的扩展语法 |
| 4.5 | **检查器缺「它会报什么」** | 设置页与校对词表页已有采纳率和「建议停用」提示（`app/settings.rs:462`），但用户判断要不要开一条规则时看不到样例。改法：每条规则挂一正一反两个例句——`revise-cases.tsv` 里本来就是这个形状的数据 |

## 五、建议不做

- **再来一轮配色 / 圆角 / 间距的视觉调整。** 旧清单那一轮已经做完，`theme.rs`
  2500 行里动效节奏、失焦弱化、行淡入都相当成熟（旧清单 3.8 专门叮嘱过别碰）。
  现在的瓶颈在交互路径长度，不在像素。
- **可拖拽自定义布局 / 停靠面板系统。** egui 里成本高、回归面大，而这个应用的
  布局对应的是一条固定工作流（填要素 → 起草 → 校对 → 导出），不需要用户自己拼。
- **把功能区改成别的形态**（侧边栏、命令栏）。分区卡加二级按钮是 Word 的形状，
  用户已经认得；真正的问题是「找不到某个命令」，那是命令面板（3.1）解决的，
  不是换一种排布能解决的。

---

## 六、如果只做三件

1. **建议就地标注（2.1）** —— 改动最小，体感最大，`highlight.rs` 的插槽已经在那儿了。
2. **键盘逐条过稿（2.2）+ 撤销栈合一（2.3）** —— 把重复次数最多的动作变快，
   并且把那个会自相矛盾的撤销修掉。
3. **流式输出 + 取消（1.1 + 1.2）** —— 把最长的一段等待从「黑箱」变成「看得见、
   停得住」。

三件都不新增任何功能，都是把已经做好的能力放到手边。
