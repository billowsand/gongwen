## 一、核实：现在到底有几套东西

### 1.1 三个模型设置与真实归属

| 设置项 | config 字段 | 解析函数 | 实际是谁 |
| --- | --- | --- | --- |
| 智能写作（Pi） | `pi_model` | `pi_chat()`（`src/models/config.rs:265`） | Pi 写作、风格学习；不回落 |
| **辅助模型** | `draft_model` | `draft_chat()`（`:247`） | 本地对话模型的**基座**：数据接口 AI、知识库问答、旧编排辅助步骤、任务助手 |
| **文字复核** | `revise_model` | `revise_chat(false)`（`:313`） | 逐句查错；未启用/未选模型时回落到辅助模型 |
| 知识库检索 | `rag.embedding` / `rag.rerank` | `resolved_rag()`（`:433`） | 只做 embedding / rerank，不生成文字 |

关键结构（这是很多困惑的根源）：

```text
draft_model ──draft_chat()────────────────────► 辅助模型
     │
     ├─revise_chat(false)──►文字复核：选了复核模型用复核，否则回落辅助模型
     │
     └─revise_chat(true)==assist_chat()──►智能体辅助：同样「复核优先，否则辅助模型」

revise_chat() 第一行就是 draft_chat()?（config.rs:314）
   ⇒ 辅助模型没配，文字复核即使单独选了模型也解析不出来（报「还没有选择起草模型」）
```

「辅助模型」这块 UI 绑定的就是 `draft_model`（`src/app/ai_manage.rs:564`），而
`revise_chat` 又把它当作所有本地对话解析的前置条件。名字叫「辅助」，实际是「基座」。

## 二、「复核」和「文字复核」是什么关系

不是同一个东西，只是名字撞了：

1. **文字复核**：独立设置项，逐句查语病，温度 0，产出「修订建议」逐条确认后才改正文；
   有自己的开关、送检范围、检查器与采纳统计（`ai_manage.rs:690-786`）。
2. **辅助模型文案里的「复核」**：指旧智能体编排里的核对/出题类辅助步骤（`ModelRole::Assist`）。
   它走 `assist_chat() = revise_chat(true)`，配了文字复核模型就**优先用复核模型**，
   没配才用辅助模型。
3. 两层共用一个解析函数 `revise_chat(assist)`，所以「文字复核」的模型选择会顺手改掉
   旧辅助步骤和任务助手的模型；反过来「辅助模型」又是整条链的基座。

**结论**：这两个概念必须拆开。文字复核只保留「复核」语义；辅助步骤归到写作模型或明确的小模型通道；
不要再让一个设置项同时当基座、当复核模型、当兜底。

## 三、要素抽取目前用在哪（核实）

- **入口**：旧流程 `src/agent/ops/prepare.rs:63,106-135` 的 `clarify` 步骤，模型只判
  「原文写没写、原样摘名」，摘录核对、词库解析、字段分类、出题都由
  `element_fields::plan` 确定性完成。
- **落地**：写明的直接经 `Event::FieldSuggestions` 挂建议卡；拿不准的出 `Target::Field` 选择题
  （多选、人员随单位过滤）；答题只进黑板，**用户点采纳才走唯一写值入口
  `element_fields::apply_field`**（红线 2），支持全部采纳 / 替换 / 过期仍采纳 / 整表撤销。
- **范围**：15 个内置技能里只有 5 个有 `step: clarify`（research-draft、material、imitate、
  reply-letter、policy-report，最后一个因文种过滤实际不生效）；复函的「主送取来函落款」
  是技能里自带的提示词节，不是代码特例。
- **新 Pi 路径没有它**：Pi 只有只读 `doc_elements`（`src/pi_agent/tools.rs:756-793`）与
  `form_facts`；缺要素只能写「【待核实：…】」。迁移文档明确「旧程序要素抽取 → 建议卡 →
  逐题确认」未接（`docs/pi-skill-migration.md:32,80`）。
- **现状**：新任务入口已关，要素抽取目前只在「恢复旧检查点、回答旧挂起题、采纳旧建议卡」
  三种情况下执行，是遗留在产代码里的旧路径。
- **价值**：动笔前补齐主送、抄送、发文单位、承办单位、联系人、呈报领导、落款单位；
  2026-09 实测 DeepSeek / MiniMax 14/20 → 20/20、17/20 → 20/20（v0.9.3）。
- **不要混淆**：任务助手「从文字填写 / 批量整理」是另一条独立通道
  （`src/task_assistant/extract.rs` 两套提示词 + 任务库表），与公文要素抽取互不调用。

## 五、统一设计

### 5.1 原则

1. **一个编排内核**：Pi 是唯一会多步执行、调工具、写文件、交付的 AI；旧 `agent` 引擎退役。
2. **一层确定性服务**：词库、知识库、稿件库、接口定义、校验、`element_fields`、建议卡——
   模型只做判断，程序做校验与落库。
3. **区分「模型」与「内核」**：知识库问答、数据接口试调、任务识别是一次性补全，
   用写作模型即可，**不要为了统一把它们塞进 Pi 的 host/workspace 流程**；它们不是第二套智能体。
4. **两个模型用途**：写作模型（Pi）+ 小模型（文字复核；可选承担任务识别）。
   取消「辅助模型」这一模糊设置。

### 5.2 目标归属

| 功能 | 目标通道 | 编排 |
| --- | --- | --- |
| 写作/修改/仿写/研报/复函/提炼/风格学习 | 写作模型 | Pi 内核（不变） |
| 写作内知识库检索 | 写作模型（重排解耦） | Pi 工具（不变） |
| 知识库页问答 | 写作模型 | 一次性调用（保留页面交互） |
| 数据接口 AI 试调/用例/出问法/文档识别/接入助手 | 写作模型 | 一次性调用 / 接入助手 |
| 数据接口写作时调用 | 写作模型 | **新增 Pi 工具**（api_search / api_call） |
| 要素抽取 | 写作模型 | **新增 Pi 工具**（建议回执）或确认退役 |
| 文字复核 | 小模型（唯一专用） | 不变 |
| 任务助手识别/填表 | 待拍板：写作模型 或 小模型 | 一次性调用 |
| 旧会话续跑 | 旧配置 | 只读保留到旧引擎退役 |

### 5.3 模型设置收敛

- 保留三块：**写作模型（Pi）**、**文字复核（小模型）**、**知识库检索（embedding / rerank）**。
- 删除「辅助模型」设置项；`draft_model` 字段保留只读兼容，启动迁移时映射到写作模型。
- 一次性调用的生成参数不开放旋钮：窗口自动、输出按任务给固定上限（问答短、工具选择温度更低），
  只在代码里定，不新增设置。
- 文字复核不再依赖「辅助模型」基座（`revise_chat` 去掉对 `draft_chat` 的硬依赖）；
  逐句复核接上自己的备用模型（现在那条备用是漏接的）。

### 5.4 三个关键改造点

1. **Pi 检索重排解耦**（P0）：`PiToolContext::new` 不再 `assist_chat()` 优先；
   改用写作模型，或给知识库检索一个独立的「重排用模型」（默认跟随 rerank 配置）。
2. **数据接口进 Pi**（P1/P2）：把 `apidef::tooling` 的 `api_search` / `api_call` 注册成 Pi 领域工具，
   复用参数 schema 校验、只读白名单与证据登记；同时解决「本任务能用哪些接口」的授权口径
   （Pi 目前没有按技能限制工具的机制，风格任务与常规任务是两套工具集，需扩展）。
   旧 `http.call` 工具族随旧引擎退役。
3. **要素抽取二选一**（P3）：
   - A. **Pi 工具化**：新增 `suggest_fields`（摘录 → 确定性 `plan()` 校验 → 词库/原文核对 →
     `Event::FieldSuggestions` → 现有建议卡 → 用户采纳走 `apply_field`），红线 2 不变；
   - B. **退役**：Pi 用 `doc_elements` + `ask_user` + 「【待核实】」，承认表单由用户自己填。
   方案 A 补回能力但工作量最大；B 最简单但等于接受 Pi 迁移后的能力回退。

### 5.5 红线不变

正文仍只能经规定入口写入；授权类要素仍不出题不建议；确定性闸门仍是裁判。
本次统一只改「模型通道与功能归属」，不放开权限、不改交付判定。

## 七、风险与反向意见

- **成本/延迟**：Pi 模型若是远程大模型，问答、任务识别、接口试调都会变贵。两种取舍：
  ①接受（设置最少）；②保留「小模型」一项，明确只用于复核 + 任务识别。
- **能力门槛**：Pi 模型必须支持工具调用；知识库问答本身不需要，但数据接口进 Pi 后需要。
- **并发**：Pi 全局同一时间只允许一轮，不适合承载高频问答；问答保持一次性调用绕开这个限制。
- **离线**：Pi host 随包约 162 MB；一次性调用不经过 host，不增加包体。
- **不要为统一而统一**：一次性补全任务（问答、试调、识别）塞进 Pi 内核，只会换来更长的链路、
  更贵的调用和新的恢复状态，不换来能力。
