# 公文助手功能路线图

> 写于 v0.4.1 之后。依据是对现有代码的通读：`docs/ai-architecture.md` 的五阶段
> 已走到阶段 4，六个文种、三个模型检查器、二十条文档规则、修订总线、SOP 状态机、
> 花脸稿、稿件库、知识库、公文词表都已落地。
>
> **补记**：这份功能路线暂不推进——下一程的重心放在界面与人机交互，
> 见 `docs/interaction-roadmap.md`。本文保留，作为「考虑过、暂缓」的备查记录。
>
> 这份清单只回答一个问题：**下一步做什么最值**。判据三条——
> 用户天天会碰到、确定性手段做得了、不与「单机离线、AI 不写正文」的定位冲突。

---

## 一、现状盘点：已经很厚的地方，和明显薄的地方

**厚**：校对（词表 + 20 条文档规则 + 3 个模型检查器 + 修订总线 + 埋点）、
排版与导出（TeX/DOCX/PDF/花脸稿/打印，三平台离线可用）、稿件库与版本、
知识库检索与问答、公文词表与输入法码表。

**薄**，按薄的程度排：

1. **文种**。六个里真正的法定文种只有「公函」一个。日常发文量最大的通知、
   请示、批复、报告只能套「普通公文」硬凑，会议纪要根本没有。
   `TemplateKind` 是硬编码的六项枚举（`models.rs:6`），加一个文种要改六处。
2. **全篇性检查**。所有检查器的输入粒度都是句子或段落。自称前后不一致、
   简称没定义、标题年份与文号年份对不上、引错文号——这些是公文里真正会出事故
   的一类，而现在一条都没查。`revise_model.rs` 的注释里已经写明「全篇性问题
   单句里根本看不出来」，但全篇这一层始终没建。
3. **文号**。机关代字、年份、序号三个字段全靠手填，没有台账、没有防重、
   没有连号。这是每个办公室都在用 Excel 另记一本的东西。
4. **来文侧**。`doc_import` 能把 Word 转成 markdown，但仅此而已——来文的主送、
   事由、被引文号没有回流到要素表。「收到一份来文要复函」是最高频的起草场景，
   现在等于从空白开始。

## 二、优先级清单

优先级判据：**P0 = 成本低且确定性高，做了立刻少一类事故**；
**P1 = 成本中等但覆盖最高频场景**；**P2 = 值得做，但要先有人真的需要**；
**P3 = 想清楚再动**。

### P0：阶段 2 的尾巴 —— 代码里已经记着的待办

这四项的共同点是「模型学不会、规则一定对」，而且判据都已在代码注释里论证过，
不必重新论证，照着做即可。

| # | 事项 | 依据 | 估计 |
|---|---|---|---|
| 1 | **敬称与自称改走规则** | `revise_model.rs:76` 已整类撤下模型实现，三轮实测三种滥用形态。用「贵/你/我+机关全称」由文种（上行/下行/平行）与隶属关系**确定性推导**，而文种在 `DraftInput.kind` 里是已知的 | 小 |
| 2 | **句末缺标点改走规则** | `revise_model.rs:92` 已从模型检查器删掉并记下待办：哪些行是正文段落（而非标题、附件名、落款），程序比模型清楚得多 | 小 |
| 3 | **数字用法规则组** | 架构文档路由表列为「规则为主」，但至今只有 `RULE-NUM-YEAR` 一条。按 GB/T 15835 补：成文日期用汉字、序数词、百分数、年份不省略、量词与阿拉伯数字的选用 | 中小 |
| 4 | **模型检查器 MDL-ADDRESS 复测或下架** | 敬称类撤下后，「口语称谓 + 个人称谓」两类一直默认关着。要么按 `revise-cases.tsv` 跑三轮复测后默认开，要么承认它价值不足直接删——**挂着一个谁都不开的检查器，等于把它的维护成本白付了** | 小 |

### P0：全篇一致性检查器（新增一类规则，价值最高的一块）

现有 `proofread_rules` 全部是单句或段落级判据。新增一类「跨句/全篇」规则，
输入是整篇正文 + `DraftInput` 要素，产出照旧是 `Revision`，界面不用动。

| 规则 | 判据 | 档 |
|---|---|---|
| 自称一致 | 全篇「我局/本局/我单位/本单位」混用 | 疑似 |
| 简称一致 | 「全称（以下简称"X"）」定义后，正文仍反复用全称；或未定义直接用简称 | 提示 |
| 年份一致 | 标题年份、文号〔年份〕、成文日期年份三者不一致 | 必错 |
| 数额一致 | 同一金额/数量在正文中前后不同（含「万元/元」换算） | 疑似 |
| 附件闭环 | 扩充现有 `RULE-ATTACH-REF`：正文引用的附件序号与附件说明逐项对号 | 必错 |
| 占位残留 | 导出前仍有「【待核实：…】」（SOP 已有此判据，但没有进导出闸门） | 必错 |

**年份一致与附件闭环敢进「必错」**，因为它们是纯比对，不存在判断余地；
其余进「疑似」或「提示」，理由与语感规则一致——有合法例外的不进必错。

### P0：引文与文号核查

公文里事故率最高的一类不是错别字，是**引错文件名或文号**。这件事可以做成
确定性比对，不需要模型：

- 正文里抽出 `《……》` 与 `〔年份〕第?号` 的组合（纯正则，无歧义）；
- 与**稿件库已发布件**和**知识库文档**比对：文件名对得上而文号对不上 → 必错，
  直接给出正确文号作为 `after`；库里根本没有 → 提示，建议标
  「【待核实：核对原文】」；
- 命中的引文顺手挂到知识库那一篇上，点一下能跳过去看原文。

零件全都现成（`rag` 的检索、`lexicon/scan` 的稿件遍历、`revision` 总线），
缺的只是这条比对逻辑本身。

---

### P1：文种扩展 —— 覆盖真正高频的场景

这是清单里价值最高、成本也最高的一项。分两步走，**顺序不能反**：

**第一步：模板可配置化（先做）。**
把 `TemplateKind` 的硬编码六项拆成「模板描述 = 要素清单 + 版式参数 + 提示词片段
+ 必填与校验规则」的数据结构，内置模板用它表达，用户可派生。
不先做这一步，每加一个文种都要同时改 `models.rs`、`prompt.rs`、`validator.rs`、
`export/latex`、`export/docx`、`proofread_rules` 六处——**加到第三个文种就会失控**，
这和阶段 0「先定契约再铺功能」是同一个道理。

**第二步：按使用频度补文种。**

| 文种 | 要点 | 价值 |
|---|---|---|
| 通知 | 下行文，力度词用「要」；印发式通知（转发正文另附）与指示性通知两种骨架 | 最高，日常发文量第一 |
| 请示 | 上行文，一文一事（`RULE-ONE-MATTER` 已有）、主送唯一、结语「妥否，请批示」 | 高 |
| 批复 | 针对请示，须引来文标题与文号——**与上面的引文核查天然配套** | 高 |
| 报告 | 上行文，不得夹带请示事项（可做成规则：报告里出现「请批准」即报疑似） | 高 |
| 会议纪要 | 独立版式：纪要版头、不加发文机关标志、出席/请假/列席栏、加盖纪要专用章 | 中高，且现有「会议议程」正好是它的上游 |

会议纪要的版式与其余五种差别最大，建议排在最后，当作模板可配置化的验收题——
**它跑通了，说明模板层真的抽对了**。

### P1：文号台账与自动编号

- 按「机关代字 + 年度」维护已用序号，新稿默认取下一个可用号；
- 重号直接报必错（这是行政事故，不是提示）；
- 台账页列出本年度已用号、缺号、作废号，可导出 Excel；
- 跨年自动归零，年度切换给确认而不是静默。

成本很低（稿件库加一张表 + 一个查询），但它替掉的是每个办公室另记的那本 Excel。

### P1：来文 → 复函链路

现有零件：`doc_import`（Word→markdown）、`ai_workbench` 的事实单抽取
（`ConfirmedFact`）、标准词库、知识库。缺的是把它们串起来：

1. 导入来文 → 抽取「来文单位、来文标题、来文文号、事由、办理时限」五个字段；
2. 逐项确认（沿用事实单的确认界面，不新造）→ 回填到新稿的主送、标题、
   正文首句「贵单位《……》（X字〔2026〕12 号）收悉」；
3. 来文原件自动挂成本稿附件，办结后一并归档。

**抽取用小模型 + 规则复核**，与架构文档路由表一致；五个字段全都可人工改，
模型抽错的代价是改一个字段，不是改正文。

### P2：值得做，但先确认真有需求

| 事项 | 说明 | 顾虑 |
|---|---|---|
| **稿件库正文全文检索** | 现在只搜标题、文号、备注（`manuscript_ui.rs:266`）。正文已在库里，加 FTS5 索引即可 | 成本低，随时可做 |
| **年度发文统计** | 发文量、文种分布、承办单位分布、平均办理时长；导出 Excel | 好看，但不确定有没有人真看 |
| **导出前涉密体检** | 扫描项目代号、人名、文号、修订痕迹残留、【待核实】残留，出一张清单再放行 | 与公文词表的黑名单共用一套名单 |
| **GB/T 9704 版式合规报告** | 版心、字号、行距、页码位置、成文日期与印章相对位置、附件说明位置，逐条报「符合/偏离」 | 现有导出本来就照国标排，这份报告的价值是**可向上举证**，不是发现问题 |
| **OFD 导出（GB/T 33190）** | 党政机关电子公文归档与交换的国标格式。结构上是 zip + xml，纯 Rust 写得出 | 工作量大（版式要重新映射一遍），且只有确有归档交换要求时才值 |
| **用印位与骑缝章** | 预留印章位、骑缝章跨页定位 | 只是版式支持，不碰电子签章 |
| **去套话 / 精简检查器** | 架构文档阶段 2 剩项。段级改写，改动幅度超出复核闸门的 ±40% 长度约束，**要单独一套闸门** | 闸门是难点，不是提示词 |
| **并列不足 / 过度** | 同上，架构文档已注明「要么单独闸门，要么只提示不给改法」。建议先只提示 | 低 |
| **篇章结构诊断** | 大模型读全文大纲，只出清单不改正文 | 与 SOP 的七步有重叠，想清楚它多给了什么再做 |

---

### P3：建议先不做

- **收文办理流转（登记/拟办/批示/承办/传阅）与多人会签**。这是另一个完整产品域，
  且只有多人协作才成立，与「单机、离线、数据不出本机」的定位直接冲突。真要做，
  它应该是另一个产品，不是本应用的一个页面。
- **电子签章**。涉及资质与第三方 UKey，不是技术问题。
- **云同步 / 账号体系**。同上，定位冲突。
- **模型自由调工具的 Agent**。架构文档阶段 4 已经论证过为什么选确定性状态机：
  可预期、可审计、可复现，这是公文场景要而通用 Agent 给不了的。

---

## 三、如果只做三件事

1. **全篇一致性检查 + 引文核查**（P0）——补上唯一还空着的检查维度，
   而且补的正是事故率最高的那一类。纯确定性，不依赖模型。
2. **模板可配置化，然后补通知、请示、批复、报告**（P1）——
   让这个工具覆盖日常发文的大头，而不只是公函。
3. **文号台账**（P1）——成本最低的那件，替掉一本 Excel。

三件做完，阶段 2 的尾巴（P0 前四项）顺手就带掉了——它们本来就是小改动。
