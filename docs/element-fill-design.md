# 公文要素填写框架：AI 按标准词库补全表单要素

> 2026-10-09 立项。需求经两轮选择题确认（见第一节）。本文是方案、分期与交接的唯一文档。

## 一、要解决的问题与已定的需求

**问题**（立项时的现状）：

1. AI 动笔前问的「六要素」（`agent/elements.rs`）和左侧要素表单是两套，互不相通：「何人」题选了
   「市数据局」，只作为一句备注交给起草，**不回填**表单的主送；反过来表单已经填了主送，AI 照样问「发给谁」。
2. 联系人、电话、呈报领导这些只能手打，没有词库选项；单位题只按职能匹配，不按材料里写明的名称去对词库。
3. `docs/ai-agent-workbench.md` 规划过的 `suggest_element` 和「要素建议卡」一直没做。
4. 「这个文种的表单要哪几项」只写在表单校验里（`draft_page/form.rs::check_form`），AI 那边没有统一清单。

**已定的需求**（2026-10-09 与用户确认）：

| 问题 | 结论 |
|---|---|
| AI 能补哪些要素 | 主送、抄送；呈报领导；承办单位、联系人、电话；发文单位、落款单位 |
| 碰不碰授权类 | 不碰：密级、文号（数字与年份）、份号、签发人、成文日期 |
| 选项从哪来 | ① 材料或要求原文里出现的名称，按规范名、对外名、简称、别名对上词库；② 按单位职能、人员简介匹配。**不接受词库以外的值进表单** |
| 何时问 | 动笔前，与六要素题同一批问；表单已经填了的不问 |
| 有把握的（原文写明、词库唯一对上）问不问 | **不出题**，直接进建议卡 |
| 点选之后怎么落表单 | **先出建议卡、再点采纳**：答题只是选定，采纳才写入表单 |
| 建议卡什么时候出现 | 答完题立刻出，不挡起草；答案同时交给起草，正文措辞跟着对上 |
| 表单已填但与材料不一致 | 不出题、不自动改；建议卡里列「替换」并标冲突，点采纳才换 |
| 发文单位、落款单位 | 改归描述类（修订红线 2）。采纳发文单位时，发函代字 / 呈批代字按表单原有规则自动带出——那是程序的确定性行为，不是 AI 建议；文号数字仍然不碰 |

## 二、红线 2 修订

> 修订前：授权类（密级、文号、份号、签发人、成文日期、印发机关）只读不写不建议；描述类（标题、主送、抄送、附件说明）可带出处建议。

修订后：

- **授权类**：密级与保密期限、文号（年份与数字）、份号、签发人、成文日期、版记印发机关与印发日期。
  AI 只读不写，也不给建议，不出题。
- **描述类**：标题、主送、抄送、附件说明，**以及发文单位、落款单位、呈报领导、承办单位、联系人、
  联系电话**。AI 可以建议，值都要注明出处。单位与人员必须是标准词库里的词条（出处写材料原文摘录或词库职能 / 简介），
  标题与附件说明取自材料原文；采纳要用户点。
- **代字**：发函代字、呈批代字随发文单位按表单规则带出（代字为空时才填），与人在下拉框里选发文单位是同一条代码路径。

要同步改的地方：`AGENTS.md` 三条红线之二、`docs/ai-architecture.md`、`docs/ai-agent-workbench.md` 第二节 D2、
`docs/decision-modules.md` 2.3 第 2 条。

## 三、设计

### 3.1 字段登记表（`src/element_fields.rs`，表单与 AI 共用）

一个枚举 + 一张表，回答「这个文种要哪些描述类要素、各自从哪取值、怎么读写」：

```rust
pub(crate) enum FieldId {
    IssuingUnit,      // 发文单位（公函、电话通知、红头呈批件；公函联合发文模式不参与）
    Recipient,        // 主送（公函、电话通知）
    CopiesTo,         // 抄送（公函）
    ReportingLeaders, // 呈报领导（白头件、红头呈批件）
    SigningUnit,      // 落款单位（白头件、红头呈批件）
    ResponsibleUnit,  // 承办单位（公函；红头呈批件取承办条目第一条）
    ContactPerson,    // 联系人（同上）
    ContactPhone,     // 联系电话：不单独出题，跟联系人从词库带出
}

pub(crate) enum Source {
    Units { multi: bool },              // 词库单位；主送、抄送可多选
    Persons { scope: PersonScope },     // 词库人员，按单位过滤（复用 units::UnitDisplay 的规则）
    PhoneOf(FieldId),                   // 跟着某个人员字段带出
}

pub(crate) enum PersonScope {
    Handlers,  // 承办联系人：responsible_people_of（含可承办上级单位的人员）
    Leaders,   // 呈报领导：leaders_of（落款单位及其上级的领导）
}
```

每个字段登记：中文名、适用文种、表单是否必填、`Source`、读值函数、写值函数。

- **读写只有一条路径**：抽出 `apply_field(draft, field, value, vocabulary)`，处理主送 / 抄送 / 发文三者互斥、
  代字带出、承办条目同步（`models::sync_joint_responsible`）。表单的下拉框改用它，采纳也用它——
  这样「AI 建议采纳后」与「人手工选」不会出现两种结果。第一期先做这步，表单行为不变。
- **授权类不进表**：再加一个测试，列出授权类对应的 `TemplateProfile` 字段，断言登记表的写值函数一个都不碰
  （对 `DraftInput` 做写入前后的差异比对）。
- 研究报告、会议议程、接听电话记录不在本框架内（议程的时间、地点、参会人员仍由六要素和模型提取）。

### 3.2 动笔前：识别、分类、出题（在 `ops/prepare.rs::clarify` 里，六要素检查之后）

**第一步：模型认角色，程序核摘录、查词库。** 同「六要素」的分工——模型只判断要求里谁是主送、谁是承办，
并原样摘出名称；摘录在原文里找不到的按没给处理，摘录在词库里查不到的不进表单。

新提示词「要素抽取」（技能里没写就用内置的一份），每个适用字段一行：

```
主送｜已给｜市数据局
联系人｜已给｜张三
抄送｜未提
```

原文 = 标题提示 + 要求 + 已确认信息 + `@` 引用的材料正文（取前若干字，防超长）。

**第二步：分类**（全部确定性，`element_fields::plan`）：

| 表单当前值 | 原文给出 | 词库匹配 | 去向 |
|---|---|---|---|
| 空 | 给了 | 唯一对上 | **建议卡**（不出题），出处「材料原文：……」 |
| 空 | 给了 | 对上多个（如「张处长」） | **出题**，对上的几个当选项，标推荐 |
| 空 | 给了 | 一个都对不上 | **出题**，选项按职能 / 简介匹配；题面说明「原文写的『××』词库里没有」 |
| 空 | 未提 | — | 必填字段：**出题**，选项按职能 / 简介匹配；非必填：不问 |
| 已填 | 给了，与表单一致 | — | 不动 |
| 已填 | 给了，不一致且唯一对上 | — | **建议卡「替换」**，标冲突 |
| 已填 | 未提 | — | 不动 |

细节：

- **人员随单位**：联系人题的选项只列承办单位的人（表单值，或本批建议 / 答案里的承办单位）；呈报领导只列落款单位
  及其上级的领导。承办单位也没定的，按简介匹配。电话不出题，从选中的人员带出。
- **多值字段**（主送、抄送）用多选题。现有的勾选（`Reply::Many`）只在清单确认里有，选择题批次里还没有：
  第二期给 `Question` 加 `multi` 标记，侧栏题目卡片按它画复选框，回答沿用 `Reply::Many`。
- **自己填写框保留**，但自己写的只作为起草备注，不进建议卡（词库外的值不进表单）。
- **和六要素去重**：把表单已填值、本批建议值写进「要素检查」的原文（「已填要素：主送 市数据局；联系人 张三」），
  让「何人」算作已给；字段题已经覆盖的「何人」不再出题（`Element::covers` 同一套去重）。
- **授权类不出题**：模型题里碰到授权类要素的仍按 `clarify::touches_authorized` 整题丢弃，规则不变。
- 题目数量计入动笔前那一批的上限；超出时必填字段优先。

**第三步：回答落地**（`engine::apply_answers`，新 `Target::Field(FieldId)`）：

- 选中的值 → 写进黑板的「要素建议」清单（来源「起草人从标准词库选定」），同时记一句已确认信息交给起草；
- 跳过 → 正文按「【待核实：主送】」占位，同六要素；
- 自己写 → 只记已确认信息。

`apply_answers` 照旧只改黑板；建议清单随挂起结果交给界面（与 `SwitchKind` 同样由界面线程执行，流程本身不碰 `DraftInput`）。

### 3.3 要素建议卡（侧栏，答完题立刻出）

```
┌ 要素建议 ───────────────────────── [全部采纳] ┐
│ 主送    （空）→ 市数据局                 [采纳] │
│         材料原文：「给市数据局发函」              │
│ 联系人  （空）→ 张三，电话 12345678       [采纳] │
│         起草人从标准词库选定                     │
│ 抄送    市应急局 → 市财政局   ⚠与表单不一致 [替换] │
│         材料原文：「抄送市财政局」                │
└────────────────────────────────────────────────┘
```

- 卡片挂在这一轮对话里，不挡流程，起草照常往下跑；
- **采纳**走 `apply_field`，写完重跑表单校验；已采纳的行显示「已采纳 · 撤销」，撤销恢复采纳前的值；
- **过期检测**：每条建议记下生成时的表单值，采纳时表单值已经变了（用户在表单里改过）就标「表单已改动」，
  不覆盖，需要再点一次「仍然采纳」；
- **采纳前再验一遍**：值必须仍在当前词库里（词库在等待期间被改过也拦得住），授权类字段不可能出现（类型上就排除）；
- 卡片随会话保存（`manuscript/ai_sessions.rs`），重开稿件还在；从检查点恢复不重复出卡。

### 3.4 不做的事

| 不做 | 理由 |
|---|---|
| 不经用户点选就写表单 | 红线 2：采纳要用户点；有把握的也只是不出题，仍要点采纳 |
| 词库以外的值进表单 | 用户已定；表单的下拉框本来也只认词库，两边保持一致 |
| 智能体循环里的 `suggest_element` 工具 | 第一版只在动笔前做；自主步骤要建议要素的需求出现了再加，届时复用同一个建议清单与卡片 |
| 记住上次的回答自动填 | 维持 `decision-modules.md` 2.2 的决定 |

## 五、已知风险

- **起草与表单可能不一致**：答案交给了起草，但用户没采纳建议卡，正文里的联系人和表单可能对不上。
  审核阶段的 `review_notes` 要加一条「正文联系人 / 主送与表单不一致」的提示（第三期一并做）。
- **小模型认错角色**：把抄送认成主送。摘录核对挡不住这种错，只能靠建议卡人工把关；分类表里「已填且不一致」只建议不改，
  所以认错的代价是多一行建议，不会改坏表单。
- **别名歧义**：「张处长」这类称谓对上多个人员时一律出题，不猜。
