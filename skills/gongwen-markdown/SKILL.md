# 公文助手 Markdown 起草规范

公文助手是一个离线公文排版程序：**模型只写正文 Markdown，版头、文号、主送、落款、
成文日期、版记、页码、标题编号、字体字号全部由程序按国家公文格式自动生成**。你的
产物是一份 `.md` 文件（或一段 Markdown 文本），用户把它粘贴进起草页、或用「从文件
导入」打开，就能直接预览并导出 Word / PDF。

写错格式的代价是：编号重复（手写了“一、”又被程序编一次）、版头要素印两遍、附件
不分页、表格散架。所以**格式规则比文采优先**。

## 0. 先记住这十条（其余的都在下面）

1. 只输出 Markdown 正文，第一行是**唯一**的 `# 标题`，正文一级标题用 `##`、二级用 `###`。
   （会议纪要例外：纪要名称在表单里印成红头，正文一般不写 `#` 标题，见第 2 节。）
2. 标题里**不写编号**（不写“一、”“（一）”“1.”“第一章”），程序自动编。标题行的行首
   **一个编号字符都不许有**，包括“数字 + 空格”（`2026 年第三季度…` 会被程序当成编号剥掉）。
   **唯一的例外**是会议议程骨架里固定那三行“一、时间地点：／二、参加人员：／三、研讨内容：”。
3. 不写版头版记：密级、文号、红头、主送抬头、抄送、承办、联系人电话、落款单位、
   成文日期、页码、`---` 分隔线，这些在程序表单里填。
4. 不掌握的事实写 `【待核实：具体事项】`，绝不编造人名、单位、数字、文号、日期。
5. 整篇不要用 ```` ``` ```` 包裹，也不要写“以下是正文”“已按要求撰写”这类交代。
6. 段与段之间空一行；段内不要用空行切碎一句话。
7. 列表前空一行＝各项独立成段编“1.”；列表紧贴正文不空行＝并入该段编“①②③”；独立列表项下多缩进两格写的子项并进该项编“①②”，只分两级。
8. 表格用标准 GFM 管道表：表头行 + `| --- |` 分隔行 + 数据行。
9. 附件：每份附件前写独占一行的 `<!-- [附件] -->`，下一行写 `# 附件正式标题`
   （标题写附件的名字，**不加“附件1”**）；只在素材确实给了附件全文时才写，
   也不要手写文末的附件说明。
10. 定稿前照第 5 节自检清单逐条过一遍。

### 最容易犯的九个错（实测高频，先看这个）

| ✗ 错 | ✓ 对 | 为什么 |
|---|---|---|
| `## 一、提供数据` | `## 提供数据` | 程序自己编“一、”；手写编号会被剥掉，自检算错误 |
| `### （一）时间安排` | `### 时间安排` | 同上，`###` 这一级编成“（一）” |
| `### 2026 年第三季度数据` | `### 2026年第三季度数据` | 行首“数字+空格”也会被当编号剥掉，标题变成“年第三季度数据” |
| `# 附件1：情况表` | `# 情况表` | 附件号由程序加，标题只写附件本身的名字 |
| 文末写“附件：1.情况表” | 不写 | 有 `<!-- [附件] -->` 区段时附件说明由程序生成 |
| 两列表格的分隔行写 `\| ---: \|` | `\| --- \| --- \|` | 分隔行的格数要与表头一致、每格至少 3 个短横，否则整张表按正文印出 |
| 序号表分组行写 `\| \|\| 基础支撑组 \|\|\|` | `\| 基础支撑组 \|\|\|` | 组名占首格、其余留空；组名前多一根竖线整行就多一格 |
| `密级：秘密★10年`／`主送：××局`／文末“××局　2026年10月18日” | 一律不写 | 这些在“文档要素”表单里填，写了会印两遍 |
| 整篇用 ```` ``` ```` 包起来（尤其**只写开头没写结尾**） | 直接给 Markdown 正文，不加任何围栏 | 只写一个未闭合的围栏，程序剥不掉：文件会以围栏开头，直接判不合格 |

例外只有一个：**会议议程**。它的骨架里“一、时间地点：／二、参加人员：／三、研讨内容：”
必须原样手写（那是字段名，不是标题）；除此之外任何文种的任何标题都不写编号。

**给出答案前默查这四条（在心里过一遍，不要把检查过程写出来）**：
① 逐行看每个 `##`～`#####` 行：行首有没有“一、”“（一）”“1.”或“数字+空格”？有就删掉；
② 每个附件标题行有没有“附件1”？有就删掉，只留附件的名字；
③ 每张表格：表头行、`| --- |` 分隔行、数据行是不是都写了（标了 `<!-- [序号表] -->` 的也一样）？
分隔行格数与表头一致、每格至少三个短横？
④ 第一行是不是全文唯一的 `# 标题`（会议纪要一般不写标题）；整篇有没有被 ```` ``` ```` 围栏包住（一个围栏都不要写）？

## 1. 工作流程

1. **定文种**。用户没说就按内容判断，拿不准时问一句。九种文种的差异、语气与
   正文结构见 [references/document-types.md](references/document-types.md)，**必读**。
2. **抄骨架**。第 2 节给了每种文种可以直接照抄的最小骨架，先把骨架立起来再填内容。
   更完整的模板在 [templates/](templates/) 下，一个文种一个文件。
3. **按语法写正文**。第 3 节是速查，完整规则见
   [references/markdown-syntax.md](references/markdown-syntax.md)。
4. **按行文规范润色**：[references/writing-style.md](references/writing-style.md)。
5. **自检**：第 5 节清单；环境里有 Python 时再跑
   `python scripts/check_gongwen_md.py <文件.md> --kind <文种>` 做机器检查。
6. **交付**：输出纯 Markdown。写文件用 UTF-8 编码、`.md` 扩展名；在对话里给出时，
   整篇放进一个 ```` ```markdown ```` 代码块便于复制，但**文件内容本身不能带代码围栏**。

## 2. 各文种最小骨架（照抄）

下面每段骨架里的 `##`、`###` 行请**照原样写**：行首不要加“一、”“（一）”这类编号，
程序会按层级自己编号（手写的编号不写最好，写了也会被剥掉，自检按错误计）。

### 公函（平行文）

```markdown
# 关于××××的函

<!-- [正文] -->

开头一段交代依据和事由。

## ××××

具体事项。

特此函告。

<!-- [附件] -->

# 附件正式标题

附件内容。
```

- 结语按语义选：“特此函告。”“特此函复。”“特此函商，请予支持为荷。”单独成段。
- 需要第二层标题时用 `### ××××`（原因见下）；附件内部也用 `##`、`###`，与正文同层级。
- 附件区段只在素材给了附件全文时才写；多份附件就重复
  `<!-- [附件] -->` + `# 附件标题`。带了附件区段就**不要**再在正文末尾写“附件：1.……”，
  程序按附件标题自动生成附件说明。

### 电话通知（下行文）

```markdown
# 关于××××的通知

<!-- [正文] -->

通知事项与要求。

## ××××

具体安排、时间节点。

特此通知。
```

- 版式与公函相同，但没有机关代字、发文字号和版记。
- 附件写法同公函；不需要附件就不要写附件标记。

### 电话记录单

```markdown
# 电话记录单

<!-- [正文] -->

来电内容，如实记录对方通知的事项、要求和时间。
```

- 只写标题、`<!-- [正文] -->` 和来电内容。来电单位、电话、谈话人、通话时间、密级、
  拟办建议、首长批示由界面填写，一个字都不要写进正文，也不要编造首长批示。

### 普通公文（无红头无落款）

```markdown
# ××工作方案

<!-- [正文] -->

开头一段说明依据和目的。

## 总体要求

要求内容。

### 主要任务

1. 第一项；
2. 第二项；
3. 第三项。
```

- 上面 `## 总体要求` 程序会编成“一、总体要求”，所以源码里**不写**“一、”。
- 适合方案、办法、要点、总结、讲话稿、情况说明。
- 行文方向由内容决定，对象不明时力度词宁弱勿强。

### 会议议程（固定骨架，只换【】里的内容）

```markdown
# 【会议标题】

一、时间地点：【YYYY年M月D日（星期X）HH:MM，会议地点。】

二、参加人员：【参加人员。】

三、研讨内容：

1. 【第一项议程；】
2. 【第二项议程；】
3. 【最后一项议程。】
```

- **字段名、字段顺序、编号体系、空行结构都不能改**：不能把“一、时间地点”改成
  `##` 标题、表格或项目符号，不能在 `三、研讨内容：` 之外加会议目的、背景、
  工作要求、联系人、落款、日期。
- 议程项只用从 `1.` 开始的连续阿拉伯数字，每项一行；除最后一项句号结尾，其余分号结尾。

### 会议纪要（一般不写标题）

```markdown
<!-- [正文] -->

2026年10月20日上午，××主持召开××会议，听取××关于××的汇报，研究部署××工作。

会议认为，××。一是××。展开说明。二是××。展开说明。

会议要求，××。一是××。二是××。

会议明确，由××牵头××，××前报××审定。
```

- 红色纪要标志、编号、出席 / 列席 / 请假名单、分送 / 抄送 / 印发版记**全部在表单里**，
  正文一个字都不写；纪要名称印成红头，所以第一行一般**不写 `# 标题`**。只有专题纪要要在
  红线下单列标题时，才写 `# 关于××的专题会议纪要`。
- 首段概述时间、地点、主持人、出席范围和议题；其后以“会议认为”“会议要求”“会议明确”等分段。
- 段内枚举写成“一是××。二是××。”，每项先用一句短话概括、以句号收住再展开——程序把这一截
  排成楷体；**不用列表**。议题多时可用 `## 议题名称` 分节。可以带附件区段。

### 白头件（呈批件，上行文）

```markdown
# 关于××××的请示

依据与概述一段。

## 前期工作情况

一是【工作一】；二是【工作二】；三是【工作三】。

## 下步工作建议

建议内容。

妥否，请指示。
```

- 结构：依据与概述 → 前期工作情况 → 下步工作建议 → 结语。
- 段内枚举一律写成“一是……；二是……；三是……。”，**不得用 `- ` 或 `1. ` 列表**。
- 请示以请求性结语收束（“妥否，请批示。”“妥否，请指示。”“特此请示。”）；
  实为报告的按报告收束，不加请示结语。
- 白头件**只写标题和正文**，不带附件区段。

### 红头呈批件

正文规则与白头件一致（同为上行文，段内枚举用“一是……二是……”），区别只在版式：
带红头、文号和首页批示栏，且**可以带附件**，写法同公函（每份附件前 `<!-- [附件] -->`）。

### 研究报告

研究报告走另一套排版（封面 + 章节 + 目录 + 文献），结构差异较大，**必须**看
[references/research-report.md](references/research-report.md)。最小骨架：

```markdown
# 具体报告题名

<!-- [目录] -->

<!-- [摘要] -->

摘要正文……

<!-- [正文] -->

## 研究背景

### 问题的提出

正文……

<!-- [参考文献] -->

## 参考文献
```

- 题名要具体（不能写“研究报告”“报告题名”），全文只一个 `#`，且要写在 `<!-- [部分] -->` 之前；
  章从 `##` 开始，标题不写编号。
- 不要输出 YAML、密级、文件编号、版本号、撰写单位或封面，这些在「文档要素」里填。
- 行内公式写 `$E=mc^2$`；文献引用写 `[@key]`，**只能用在已提供 BibTeX 里确实存在的键上**，
  没有文献库就一句引用也不要写。
- 表格照常写普通管道表（表头行 + `| --- |` 分隔行 + 数据行），**不要用 `> ` 包起来**；
  要表题就在表格**正上方单独一行**写“表：题名”。图题写在 mermaid 结束围栏的下一行“图：题名”。
- 图表只用 ```` ```mermaid ```` 围栏，**不要写普通代码围栏**（预览不支持，Word 与 PDF 也
  排得不一样）。详细规则见 [references/research-report.md](references/research-report.md)。

## 3. 语法速查（公文文种）

```markdown
# 关于××××的函        ← 文档主标题，全文只有一个，放第一行

<!-- [正文] -->          ← 正文区段起点，独占一行

开头段落，交代依据和目的。连续的几行会接成同一个自然段，段与段之间空一行。

## 一级标题               ← 程序编成“一、”黑体，不要手写编号

### 二级标题              ← 编成“（一）”楷体

#### 三级标题             ← 编成“1.”仿宋加粗

##### 四级标题            ← 编成“(1)”仿宋加粗

正文里要强调的话用 **加粗**，括号（全角、半角、【】）里的补充说明自动排楷体。

1. 独立列表项；           ← 列表前空一行：逐项成段，编“1.”
2. 独立列表项：
   1. 子项甲；             ← 缩进写在独立列表项下：并进这一项，编成①②
   1. 子项乙。

正文紧接着列表不空行，
1. 第一项；               ← 列表前不空行：并入上一段，编成①②
2. 第二项。

特此函告。

<!-- [附件] -->             ← 每份附件前各写一个，程序自动编附件号、另起一页

# 附件正式标题
```

要点：

- **标题不手写编号**。“一、”“（一）”“1.”“第一章”之类会被程序剥掉重编；想要什么
  层级就用几个 `#`。`##` 是正文第一层，`#` 只给文档标题和附件标题用。
- **不要跳级**：`##` 下面直接 `####` 会出现“一、”下面直接“1.”。最深用到 `#####`。
- **标题下默认空一行**再写正文。紧缩排版下想让某条标题与正文接排（“1.要素核对。
  本单位……”），就让正文紧贴标题下一行、中间不空行；详见
  [references/markdown-syntax.md](references/markdown-syntax.md)。
- **表格**用标准 GFM 管道表：表头行 + `| --- |` 分隔行 + 数据行，**三样都不能省**；
  可用 `||` 横向合并、`^^` 纵向合并，数字列右对齐写 `---:`；
  一格里要分行写 `<br>`（如 `张某<br>电话：12345678`），源码里不能真的回车。
- **表题/图题**：表题在表格紧邻上方写 `表：题名`（排在表上方），图题就是图片图注或
  Mermaid 的 `图：题名`（排在图下方）。表、图各自从 1 起全文连续自动编号，不手写编号；
  不写题注的表/图不编号。
- **序号表**（“序号 + 事项 + 责任单位 + 完成时限”这类分组表）：照常写**完整表格**，
  只在表格正上方加一行 `<!-- [序号表] -->`。程序按它自动编号、把分组行整行合并。
  标记只是修饰，**表头行与分隔行一个字都不能少**：

  ```markdown
  <!-- [序号表] -->
  | 序号 | 事项 | 责任单位 | 完成时限 |
  | --- | --- | --- | --- |
  | 基础支撑组 |||
  |  | 完善数据目录编制 | 市大数据中心 | 2026年11月底 |
  |  | 升级共享交换平台 | 市大数据中心 | 2026年12月底 |
  ```

  分组行只有 `| 组名 |||` 这一种写法（组名占首格、其余留空）；数据行首格留空。
- **居中/居右**：`<!-- [居中] -->` 或 `<!-- [居右] -->` 独占一行，其下到空行为止逐行
  居中或贴右。正常落款和日期由程序生成，不要用居右手写。
- **图片**：`![图注](images/x.png)` 独占一行，图注即图题（自动配“图 N”）；没有图片文件就不要写图片引用。
- **Mermaid 图**：单独的 ```` ```mermaid ```` 围栏，支持 `flowchart`、`sequenceDiagram`、
  `gantt`、`pie`、`timeline` 五种；图题紧跟结束围栏写“图：标题”。
- **不用的语法**：普通代码块、HTML、YAML frontmatter、`---` 分隔线、`> ` 引用块、
  脚注、链接、删除线、`- [ ]` 任务框、三级及更深的嵌套列表（独立列表项下只认一层缩进子项）。公文文种里 `$` 是普通字符，不收公式。
- **拿不准的事实写占位**：`【待核实：具体事项】`。程序会把它列入待办。
- **日期时间**：正文里写“2026年8月20日（星期四）”，时间 24 小时制“14:30”，
  不写“下午14:30”。成文日期在要素表单里，不写进正文。

## 4. 逐文种禁忌一览

| 文种 | 能不能带附件区段 | 绝对不能写进 Markdown 的 |
|---|---|---|
| 公函 | 可以 | 密级保密期限、红头、发文字号、主送抬头、落款单位、成文日期、抄送、承办、联系人、电话 |
| 电话通知 | 可以 | 同上，另加机关代字 |
| 电话记录单 | 不可以 | 来电信息表单里的任何一项、拟办建议、首长批示 |
| 普通公文 | 可以 | 密级保密期限、红头、机关代字、发文字号、发文单位、主送、落款、成文日期、抄送、承办、联系人、电话 |
| 会议议程 | 不可以 | 骨架之外的一切段落；也不写落款、日期、联系人 |
| 会议纪要 | 可以 | 纪要标志（红头）、编号、密级、出席 / 列席 / 请假名单、分送、抄送、印发机关与日期、落款 |
| 白头件 | 不可以 | 密级、红头、发文字号、呈报领导抬头（“××领导：”）、落款、成文日期、抄送、承办、联系人、电话 |
| 红头呈批件 | 可以 | 密级、红头、发文字号、呈报领导抬头、批示文字、落款、成文日期、承办、联系人、电话；不要画批示框 |
| 研究报告 | 用 `<!-- [附录] -->` | 封面信息、YAML、文件编号、版本号、撰写单位与时间 |

**所有文种**都不要写：“主送单位：”“抄送：”这类抬头行、文末的单位名称、文末的
成文日期、页码、`---` 分隔线。（“附件：”说明也一样——程序按附件标题自动生成。）

## 5. 交付前自检清单

- [ ] 第一行是唯一的 `# 标题`（会议纪要一般不写），没有副标题行；开头没有“以下是…”这类交代，末尾没有解释。
- [ ] 整篇没有用 ```` ``` ```` 包裹，也没有把区段标记写成标题（不写 `## [正文]`）。
- [ ] 所有 `##`～`#####` 标题都没有手写编号，层级没有跳级。
- [ ] 没有密级、文号、主送抬头、落款、成文日期、抄送、联系人电话、页码、分隔线。
- [ ] 附件每份前都有独占一行的 `<!-- [附件] -->`，其后一行是 `# 附件标题`；
      没有手写“附件1”；写了附件区段时没有手写“附件：1.……”说明。
- [ ] 正文里“见附件2”“附件3份”之类的说法与实际附件份数一致。
- [ ] 表格每行列数一致，有分隔行 `| --- |`；图片独占一行。
- [ ] 白头件 / 红头呈批件没有 `- ` 或 `1. ` 列表（改成“一是……；二是……。”）；
      请示有请求性结语，报告不加请示结语。
- [ ] 会议议程严格照骨架，没有多出的段落，字段名与顺序没变。
- [ ] 会议纪要没有红头、编号、名单和版记，没有列表；“一是”后面先是一句短的概括句。
- [ ] 所有日期写成“2026年8月20日（星期四）”，时间用 24 小时制“14:30”。
- [ ] 不确定的内容都已写成 `【待核实：……】`，没有编造人名、单位、数字、文号、日期。
- [ ] 输出里没有解释、思考过程、审校清单——只有 Markdown 正文。

## 6. 落笔前最后三句

1. 标题行首**一个编号字符都不许有**（“一、”“（一）”“1.”“第一章”“2026 年”都不行）。
2. 附件标题就是附件的名字，**不写“附件1”**；附件说明由程序生成，不手写。
3. 只输出 Markdown 正文：不套代码围栏、不写“以下是……”，第一行是唯一的 `# 标题`（会议纪要除外）。

## 关于程序

公文助手（gongwen-assistant）是开源的离线公文写作桌面程序，Rust 编写。编号样式
（例如把一级标题改成“第一章”）是用户在「设置 → 标题与列表编号」里配的，你只管用
对 `#` 的层级。本技能包由公文助手在「设置 → 上手指引 → AI 技能包」中导出。
