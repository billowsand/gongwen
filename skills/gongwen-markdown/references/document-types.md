# 八种文种的正文规则

公文助手里每篇稿子先选文种，文种决定版式与要素。**要素（版头、版记、落款等）由用户在
程序的“文档要素”表单里填，模型只写正文**。下面按文种列出：正文结构、必须遵守的写法，
以及**绝对不能写进 Markdown 的内容**（写了就会在成品里印两遍）。

所有文种通用：

- 第一行 `# 正式标题`，全文只此一个（附件标题除外）。
- 正文 `##` / `###` / `####` / `#####` 自动编号为 一、/（一）/ 1. /(1)，标题不手写编号。
- 不写“主送单位：”抬头、不在文末另起一行写单位名称或日期、不写分隔线和页码。
- 不掌握的事实写 `【待核实：……】`，不得编造。

---

## 1. 公函

平行文，用于商洽、征求意见、询问答复、请求批准、告知事项。

- 标题：“关于……的函”（复函用“关于……的复函”）。
- 正文：开头交代依据和事由 → 具体事项（可分 `##` 大节）→ 明确请求 → 结语。
- 结语按语义选：“特此函告。”“特此函复。”“特此函商，请予支持为荷。”
  “请予研究函复。”等，单独成段。
- 平行文语气：对方不是下属，用“请贵单位”“希望”“请予支持”，不用“要求”“责成”“务必”“严禁”。
- 附件：只有用户明确提供附件内容时才写附件区段；每份附件前 `<!-- [附件] -->`，
  下一行 `# 附件正式标题`。
- 附件说明：写了附件区段时，程序在正文之后、落款之前**自动生成附件说明**
  （单个附件印“附件：××”，多个附件印“附件1：××　2：××”），名称取自各附件的
  `#` 标题，**不要手写**。只有附件全文不在本稿里（例如用户另行
  提供的表格文件）时，才在结语后手写一段“附件：××表”。
- 正文引用“见附件2”时核对附件项目序号；“附件3份”是印制份数，不与附件种类数比较。另行随附的附件需人工核对。
- **不得出现**：密级和保密期限、发文机关标识（红头）、发文字号、主送单位抬头、落款单位、
  成文日期、抄送单位、承办单位、联系人、联系电话。

## 电话记录单

记录收到的电话通知，与本单位下发的「电话通知」并列。版式为来电记录表，不设红头、文号、主送或发文落款。
本单位名称、来电单位、电话、谈话人及职务、通话时间、密级、保密期限、拟办建议及承办联系信息由界面填写。
首长批示栏留空供人工填写。Markdown 只写 `# 电话记录单`、`<!-- [正文] -->` 与来电内容；如实保留原来通知的事项、要求和时间，不编造意见或首长决定。

## 2. 电话通知

版式与公函一致，但没有机关代字、发文字号和底部版记。下行文。

- 标题：“关于……的通知”。
- 正文：通知事项 → 执行要求 → 时间节点 →（联系方式由要素生成，不写）→ 结语“特此通知。”
- 下行文语气：对下级用“要”“切实”“确保”；结尾交代谁督促落实、有问题向谁反映。
- 附件写法同公函。
- **不得出现**：密级和保密期限、红头、机关代字、发文字号、主送单位抬头、落款单位、
  成文日期、抄送单位、承办单位、联系人、联系电话。

## 3. 普通公文

无红头、无发文单位、无主送、无落款、无版记，只排标题、正文和可选附件。
适合方案、办法、要点、总结、讲话稿、情况说明等。

- 标题按内容：“××工作方案”“关于××的情况说明”等。
- 行文方向由内容决定，对象不明时力度词宁弱勿强。
- 附件写法同公函。
- **不得出现**：密级和保密期限、红头、机关代字、发文字号、发文单位、主送单位、落款单位、
  成文日期、抄送单位、承办单位、联系人、联系电话。

## 4. 会议议程

**固定骨架，只替换【】里的内容**，不得改动字段名、字段顺序、编号体系和空行结构：

```markdown
# 【会议标题】

一、时间地点：【YYYY年M月D日（星期X）HH:MM，会议地点。】

二、参加人员：【参加人员。】

三、研讨内容：

1. 【第一项议程；】
2. 【第二项议程；】
3. 【最后一项议程。】
```

- 第一行只能是一个 `# ` 标题，不加副标题。
- “一、时间地点”“二、参加人员”“三、研讨内容”各占一行、顺序不变，**不能改成 `##` 标题、
  表格或项目符号**（这是会议议程里唯一允许手写“一、”的地方）。
- 时间地点写在同一行；日期具体到年月日和星期，时间 24 小时制。
- 议程只用从 `1.` 开始的连续阿拉伯数字，每项一行，可增减项数；不得用“（一）”或多级编号。
- 每项写清责任主体和动作；除最后一项句号结尾外，其余各项分号结尾。
- 不得增加会议目的、背景、工作要求、联系人、落款、日期、说明等骨架外段落。
- 素材缺时间、地点或参加人员时，原位写“【待核实：会议时间/会议地点/参加人员】”，
  不写“无”“未提供”。

## 5. 白头件（内部呈批件）

上行文，用于内部情况报告、请示、领导呈批。无红头。

- 标题：“关于……的请示”“关于……的报告”。
- 结构：依据与概述 → 前期工作情况 → 下步工作建议 → 按实际文种收束。
  大节用 `## 标题`（程序编“一、二、三”）。
- **段内枚举写成“一是……；二是……；三是……。”，不得使用 `- ` 或 `1. ` 列表。**
- 请示以请求性结语收束，可用“妥否，请批示。”“妥否，请指示。”“特此请示。”；情况报告按报告收束，不附加请示结语。呈批件是版式，不等于请示。
- 上行文语气：向上级提事项用“建议”“请”“恳请”，不用“要求”“务必”；谦辞在开头一次说完。
- 白头件**只写标题和正文**，不带附件区段。
- **不得出现**：密级和保密期限、红头、发文字号、主送单位或呈报领导抬头
  （如“××领导：”）、落款单位、成文日期、抄送单位、承办单位、联系人、联系电话。

## 6. 红头呈批件

带红头、文号和首页批示栏的内部呈批件。正文规则与白头件一致。

- 结构、枚举方式同白头件；结语按实际文种区分请示与报告。
- 可以带附件：每份附件前 `<!-- [附件] -->`，下一行 `# 附件正式标题`。
- **不得出现**：密级和保密期限、红头、发文字号、呈报领导抬头、批示文字、落款单位、
  成文日期、承办单位、联系人、联系电话；也不要画批示框。

## 7. 研究报告

按研究报告规范排封面、目录、章节、文献，与上面七种差别很大，单独见
[research-report.md](research-report.md)。

## 文种选择参考

| 用户说的 | 选 |
|---|---|
| 给平级或不相隶属单位发的函、商洽、征求意见、复函 | 公函 |
| 通知下级开会、报材料、执行事项 | 电话通知（或普通公文） |
| 方案、办法、总结、讲话稿、情况说明、工作要点 | 普通公文 |
| 开会议程、会议安排 | 会议议程 |
| 向本单位领导请示、报告、呈批 | 白头件；需要红头文号批示栏的用红头呈批件 |
| 调研报告、课题报告、咨询报告、方案论证、外文翻译 | 研究报告 |

用户若只想“写个通知”又没指定，普通公文最通用；拿不准就问。
